1.  [TinyURL] Design a URL shortening service. What are the
    requirements, data model, short-key generation strategy, and
    redirect flow? Level: Freshers / Junior

Answer: Design the service around a write path that creates a unique
short key and a read path that resolves that key to the original URL.
Store the mapping in a durable database, cache hot mappings, and put the
redirect service behind load balancers. The short key can be generated
from a unique numeric ID encoded with Base62. Define expiration, abuse
protection, analytics requirements, and availability targets before
choosing storage.

Example: Example: POST /shorten with a long URL returns
https://short.example/Ab3X9. GET /Ab3X9 looks up the key in cache first,
then durable storage, and returns a redirect.

Interview Tip: Do not jump directly to technologies. Start with
requirements, traffic/data estimates, APIs and core entities; then draw
the simplest architecture that satisfies them. State assumptions
explicitly, identify the first bottleneck, and explain trade-offs before
adding complexity.

What Interviewer Is Testing: Requirements clarification, capacity
estimation, API and data-model thinking, component selection,
scalability, reliability, consistency, failure handling, and the ability
to explain trade-offs clearly.

Key Points to Remember: • Start with functional and non-functional
requirements. • Estimate scale before selecting architecture or storage.
• Identify the source of truth for important state. • Define failure
behavior, retries, timeouts, and idempotency where relevant. • State
consistency, availability, latency, and durability trade-offs
explicitly.

Common Follow-up Questions: How would you generate IDs at multiple
regions? How would you prevent abuse and malicious redirects?

Common Mistakes: • Listing technologies without explaining why they are
needed. • Ignoring bottlenecks, failure modes, or operational limits. •
Assuming every component is infinitely scalable. • Giving precise
capacity numbers without stating assumptions. • Treating CAP, caching,
replication, or consistency as slogans instead of design trade-offs.

2.  [TinyURL] How would you generate unique short URLs using sequential
    IDs, Base62, or hashing? What collision issues arise? Level:
    Freshers / Junior

Answer: A sequential numeric ID followed by Base62 encoding is simple
and avoids collisions when the ID is unique. Hashing a long URL can
create collisions unless the hash is sufficiently controlled and
collision handling is added. Random keys also require uniqueness checks.
In an interview, compare predictability, key length, coordination, and
collision behavior rather than assuming hashing is automatically better.

3.  [TinyURL] A shortened URL becomes extremely popular. How would you
    keep redirects fast and protect the database? Level: Freshers /
    Junior

Answer: Treat a viral URL as a hot key. Cache the short-key-to-long-URL
mapping close to the redirect service, use CDN/edge caching where
appropriate, and protect the database with cache-aside or read-through
behavior. Replicas and horizontal scaling can absorb sustained load;
request coalescing can reduce a thundering herd when a hot cache entry
expires.

4.  [TinyURL] How would you handle duplicate long URLs, URL expiration,
    and deletion? Level: Freshers / Junior

Answer: Decide whether duplicate long URLs should return the same short
key or receive separate keys. If deduplication is required, enforce it
with a normalized URL representation plus a uniqueness constraint.
Expiration can be represented by an expiry timestamp, while deletion
should define whether the key is permanently invalid or reusable. Avoid
reusing keys casually because stale caches and old links can create
ambiguity.

6.  [Rate Limiter] How does a token-bucket algorithm work, and how does
    it handle bursts? Level: Freshers / Junior

Answer: A token bucket has a maximum capacity and a refill rate. Each
request consumes one or more tokens; if enough tokens exist, the request
is allowed, otherwise it is rejected or delayed. Because tokens
accumulate up to the bucket capacity, short bursts can be accepted while
the long-term average remains bounded.

7.  [Rate Limiter] Compare token bucket and leaky bucket. When would you
    choose each? Level: Freshers / Junior

Answer: Token bucket controls the allowed rate while permitting bounded
bursts; leaky bucket models a queue drained at a relatively fixed rate,
which smooths traffic. Choose token bucket when burst tolerance matters
and leaky-bucket-style shaping when a steadier output rate is more
important.

8.  [Rate Limiter] How would you implement a distributed rate limiter
    across multiple application servers? Level: Freshers / Junior

Answer: Use a shared state store or an algorithm designed for
distributed coordination so multiple application servers enforce the
same logical quota. Redis is common because atomic commands/Lua scripts
can update counters or token-bucket state. Define the consistency
expectation and behavior when the shared limiter is unavailable: fail
closed for sensitive APIs or fail open for lower-risk traffic.

9.  [Rate Limiter] Why might Redis be used for distributed rate
    limiting, and what happens if Redis is unavailable? Level: Freshers
    / Junior

Answer: Redis provides low-latency shared state and atomic operations
suitable for counters, token buckets, and sliding windows. If Redis
fails, the design needs an explicit policy: reject requests, temporarily
use local limits, or allow traffic with reduced protection. The correct
choice depends on the risk of abuse versus the risk of denying
legitimate traffic.

unavailable. A background worker can asynchronously delete or archive
expired objects, while reads still enforce expiration immediately. For
large systems, partition cleanup work by time ranges rather than
scanning the entire dataset.

14. [CAP] Explain CAP theorem using a distributed database during a
    network partition. Level: Freshers / Junior

Answer: CAP states that when a network partition prevents nodes from
communicating reliably, a distributed system cannot simultaneously
guarantee both strong consistency and availability for every operation.
During the partition, the design must choose which guarantee to
sacrifice for the affected operation. CAP is about partitioned
distributed systems; it is not simply a three-way feature checklist.

Example: Example: during a partition between replicas, a banking-style
balance update may reject writes rather than acknowledge conflicting
balances.

16. [Scaling] Explain vertical versus horizontal scaling and the main
    limitations of each. Level: Freshers / Junior

Answer: Vertical scaling increases the capacity of one machine;
horizontal scaling adds machines. Vertical scaling is operationally
simple but has hardware ceilings and can leave a large failure domain.
Horizontal scaling provides more capacity and resilience but introduces
distributed coordination, load balancing, data partitioning, and
operational complexity.

17. [Scaling] You have one backend server and traffic is growing. How
    would you scale it? Level: Freshers / Junior

Answer: First make the application stateless where practical, place it
behind a load balancer, and run multiple instances. Then scale the
database, introduce caching, move slow work to queues, add
observability, and partition services only when there is a clear
bottleneck. Scale based on measured CPU, memory, latency, database load,
and traffic rather than adding components prematurely.

Key Points to Remember: • Start with functional and non-functional
requirements. • Estimate scale before selecting architecture or storage.
• Identify the source of truth for important state. • Define failure
behavior, retries, timeouts, and idempotency where relevant. • State
consistency, availability, latency, and durability trade-offs
explicitly.

Common Follow-up Questions: What are the bottlenecks? What happens when
a dependency fails? What consistency and availability guarantees are
required?

Common Mistakes: • Listing technologies without explaining why they are
needed. • Ignoring bottlenecks, failure modes, or operational limits. •
Assuming every component is infinitely scalable. • Giving precise
capacity numbers without stating assumptions. • Treating CAP, caching,
replication, or consistency as slogans instead of design trade-offs.
