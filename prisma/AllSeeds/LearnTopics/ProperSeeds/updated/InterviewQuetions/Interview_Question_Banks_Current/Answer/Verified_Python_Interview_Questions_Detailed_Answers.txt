Question 1: What is the difference between a list and a tuple?

Answer: A list is mutable, while a tuple is immutable after creation.
Lists are suited to collections that need modification; tuples are
useful for fixed records and can be hashable when all their elements are
hashable. Both preserve order and can contain duplicate values.

Example: numbers = [1, 2, 3]; numbers.append(4) point = (10, 20) The
list can be changed; the tuple cannot be modified in place.

Question 2: What does dynamically typed mean in Python?

Answer: Python is dynamically typed because variable names are not
permanently associated with one declared type. The object referenced by
a name has a type, and that type is determined at runtime. A name can
later refer to an object of another type. Dynamic typing is different
from weak typing; Python still enforces type rules when operations are
performed.

Example: x = 10 x = ‘hello’ The same name refers first to an integer and
then to a string.

Question 3: Is Python compiled, interpreted, or both?

Answer: Python is commonly described as interpreted, but CPython first
compiles source code to bytecode and then executes that bytecode on the
Python virtual machine. The important interview point is that
compilation to bytecode does not make Python equivalent to a
traditionally ahead-of-time compiled language such as C. Other Python
implementations can use different execution strategies.

Example: Running a .py file with CPython normally involves
parsing/compilation to bytecode followed by execution by the
interpreter/VM.

Question 4: == vs is in Python?

Answer: == tests value equality, while is tests object identity—whether
two references point to the same object. Use == when comparing values
and is mainly for identity checks such as x is None. Do not rely on
implementation-specific interning or caching to make is work for
ordinary values.

Example: a = [1, 2]; b = [1, 2] a == b # True a is b # False

Question 5: How does Python pass arguments to functions?

Answer: Python uses call-by-sharing (also called object-reference
semantics): the function receives a reference to the same object bound
to the argument. Rebinding a parameter does not rebind the caller’s
variable, but mutating a shared mutable object is visible to the caller.
This explains why mutable and immutable arguments can appear to behave
differently.

Example: def add_item(items): items.append(‘x’) a = [] add_item(a) # a
is now [‘x’]

Question 6: What are mutable and immutable objects?

Answer: Mutable objects can be changed after creation; immutable objects
cannot be changed in place. Common mutable types include list, dict, and
set. Common immutable types include int, float, bool, str, and tuple
(although a tuple can contain mutable objects). Immutability is
important for hashing and for understanding whether a function mutates
shared state.

Example: items = [1, 2]; items.append(3) # mutation name = ‘Bob’; name
+= ’ Smith’ # creates a new string object

Question 7: Why are default mutable arguments dangerous?

Answer: Default argument expressions are evaluated once when the
function is defined, not each time it is called. If the default is
mutable, calls can accidentally share the same object and retain state
between calls. The standard safe pattern is to use None as the default
and create a new object inside the function.

Example: def add(x, items=None): if items is None: items = []
items.append(x) return items

Question 8: *args vs **kwargs?

Answer: *args collects extra positional arguments into a tuple. **kwargs
collects extra keyword arguments into a dictionary. They are useful for
flexible APIs and wrappers, but should not be used merely to hide
unclear function contracts.

Example: def log(*args, **kwargs): print(args) print(kwargs) log(1, 2,
level=‘INFO’)

Question 9: How do list comprehensions work?

Answer: A list comprehension creates a list from an iterable using an
expression and optional filtering condition. It is concise for
straightforward transformations, but nested or highly complex
comprehensions can reduce readability. It eagerly creates the resulting
list in memory.

Example: squares = [x * x for x in range(5) if x % 2 == 0] # [0, 4, 16]

Question 10: Generator expression vs list comprehension?

Answer: A list comprehension eagerly builds the complete list. A
generator expression produces values lazily as they are requested, so it
generally uses less memory for large or streaming workloads. A generator
can be consumed only as it yields values and does not provide normal
list operations such as indexing.

Example: sum(x*x for x in range(10_000_000)) The generator avoids
constructing a ten-million-element list.

Question 11: Iterator vs iterable?

Answer: An iterable is an object that can provide an iterator, usually
through __iter__(). An iterator represents the state of an ongoing
traversal and implements __next__(), raising StopIteration when
exhausted. Every iterator is iterable, but not every iterable is itself
an iterator.

Example: items = [1, 2, 3] it = iter(items) next(it) # 1 next(it) # 2

Question 12: What does yield do?

Answer: yield turns a function into a generator function. Instead of
returning once and ending, it produces a value and suspends execution,
preserving local state so execution can continue on the next iteration.
This is useful for streaming large or incremental results without
storing them all in memory.

Example: def numbers(): for i in range(3): yield i # values are produced
one at a time

Question 13: How would you read a large file without loading it into
memory?

Answer: Process the file incrementally, typically by iterating over the
file object line by line or by using a suitable chunk size. This keeps
memory usage roughly independent of the total file size. For very large
files, combine streaming with filtering, batching, and controlled output
writes.

Example: with open(‘events.log’, encoding=‘utf-8’) as f: for line in f:
process(line)

Question 14: Shallow copy vs deep copy?

Answer: A shallow copy creates a new outer container but keeps
references to nested objects. A deep copy recursively copies nested
objects as well. Shallow copying is usually cheaper and is enough when
nested objects are intentionally shared; deep copying is useful when
complete independence is required, but it can be expensive and may not
work meaningfully for every object.

Example: import copy b = copy.copy(a) # outer copy c = copy.deepcopy(a)
# recursive copy

Question 15: How does Python garbage collection work?

Answer: CPython primarily uses reference counting to reclaim objects
whose reference count reaches zero, plus a cyclic garbage collector to
detect reference cycles that reference counting alone cannot reclaim.
Other Python implementations can use different memory-management
strategies. Garbage collection is automatic, but resource management
such as files and sockets should not be left to garbage collection; use
explicit cleanup or context managers.

Example: a = []; a.append(a) del a # A reference cycle may require the
cyclic GC to reclaim it.

Question 16: What is reference counting?

Answer: In CPython, each object maintains a reference count. When the
count reaches zero, the object’s memory can generally be reclaimed
immediately. Reference counting alone cannot collect cycles because
objects in a cycle can keep references to each other even when no
outside references remain, which is why CPython also has cyclic garbage
collection.

Example: a = [] b = a del a # The list still has a reference through b.

Question 17: What is the GIL?

Answer: In standard CPython builds, the Global Interpreter Lock (GIL) is
a lock that historically allows only one thread at a time to execute
Python bytecode in a process. It simplifies parts of CPython’s memory
management and affects CPU-bound multithreaded programs. I/O-bound
threads can still overlap effectively because threads can release the
GIL while waiting on many I/O operations. Python versions/builds can
evolve, so answers should specify the implementation/version when
discussing GIL behavior.

Example: Two CPU-heavy Python threads in one traditional CPython process
generally do not provide true parallel execution of Python bytecode,
while threads waiting on network I/O can overlap.

Question 18: How does the GIL affect CPU-bound threads?

Answer: For CPU-bound pure-Python work in traditional CPython, the GIL
prevents multiple threads from executing Python bytecode simultaneously
within one process, so adding threads often does not provide linear CPU
scaling and may add scheduling overhead. CPU-bound work can instead be
parallelized with multiprocessing or suitable native/vectorized code
that releases the GIL.

Example: Splitting a CPU-heavy calculation across four Python threads
may not make it four times faster; separate processes can use multiple
CPU cores.

Question 19: When would you use multiprocessing?

Answer: Use multiprocessing when work is CPU-bound and can be divided
into independent tasks, especially when native parallelism across CPU
cores is needed in traditional CPython. Processes have separate memory
spaces, so communication and data transfer cost more than threads. It is
less attractive for tiny tasks or workloads dominated by shared mutable
state.

Example: Use a process pool to calculate independent batches of image
transformations or numerical computations across CPU cores.

Question 20: Threading vs multiprocessing vs asyncio?

Answer: Threading is useful for overlapping blocking I/O within one
process and sharing memory conveniently, but CPU-bound Python code is
constrained by the traditional CPython GIL. Multiprocessing provides
separate processes and can use multiple CPU cores, at the cost of higher
memory and communication overhead. asyncio uses cooperative scheduling
with async/await and is effective for high-concurrency non-blocking I/O
when the libraries used are asyncio-compatible. The workload and
ecosystem should determine the choice.

Example: HTTP service with async-compatible clients: asyncio. Blocking
I/O with existing synchronous libraries: threads may be simpler.
CPU-heavy independent tasks: processes.

Question 21: What is a decorator?

Answer: A decorator is a callable that takes a function or class and
returns a modified or wrapped callable. It is commonly used for
cross-cutting behavior such as logging, authorization, timing, caching,
and retries without changing the wrapped function’s core implementation.
functools.wraps should normally be used so metadata such as the original
function’s name and docstring is preserved.

Example: from functools import wraps def log_calls(fn): @wraps(fn) def
wrapper(*args, **kwargs): print(fn.__name__) return fn(*args, **kwargs)
return wrapper

Question 22: How do you write a decorator that accepts arguments?

Answer: A decorator with arguments needs one additional function layer:
the outer function receives the decorator configuration, the middle
function receives the target function, and the inner wrapper executes
the function. functools.wraps should be applied to the wrapper.

Example: def repeat(n): def decorate(fn): @wraps(fn) def wrapper(*args,
**kwargs): for _ in range(n): fn(*args, **kwargs) return wrapper return
decorate

Question 23: What is a context manager?

Answer: A context manager defines setup and cleanup behavior around a
block of code. It implements __enter__ and __exit__, or can be created
conveniently with contextlib.contextmanager. Context managers are ideal
for resources that must be released reliably, including files, locks,
database transactions, and temporary state.

Example: with open(‘data.txt’) as f: data = f.read() # the file is
closed when the block exits

Question 34: How would you implement binary search?

target: lo = mid + 1 else: hi = mid - 1 return -1

Question 70: How would you handle concurrent updates to shared state?

Answer: First determine whether shared mutable state can be eliminated
or partitioned. If it must be shared between threads, protect critical
sections with appropriate synchronization such as locks or thread-safe
queues. For processes, use suitable inter-process primitives or external
durable storage. In distributed systems, coordinate through the database
or another shared consistency mechanism rather than relying on a Python
lock that exists in only one process.

Question 71: How would you choose between threads and asyncio for an
I/O-heavy service?

Answer: Choose asyncio when the service has high concurrency, the I/O
libraries are async-compatible, and cooperative scheduling provides a
clear benefit. Choose threads when existing blocking libraries are
easier to use and concurrency requirements are moderate. Consider
operational simplicity, cancellation behavior, connection-pool support,
and team familiarity—not just raw throughput.

Example: An async HTTP service making thousands of concurrent requests
through an async client is a strong asyncio use case; a small service
using a blocking SDK may be simpler with a thread pool.

Question 72: How would you investigate high CPU in a Python process?

Answer: Confirm the process is responsible for the CPU and identify
whether the load is application CPU, native extension work, or system
overhead. Capture a profile or sampling stack, inspect hot functions and
request/task volume, and compare with recent code or workload changes.
Look for accidental busy loops, expensive serialization, inefficient
algorithms, excessive logging, or contention. Mitigate first if
production impact is severe, then fix and benchmark.

Example: If profiling shows JSON serialization consumes most CPU after a
traffic increase, optimize payload size or serialization strategy rather
than changing unrelated business logic.

Question 73: How would you investigate increasing latency after a
deployment?

Answer: Compare latency before and after deployment by endpoint,
percentile, instance, and dependency. Check traces, CPU/memory, database
queries, external API timings, queue depth, connection pools, and
error/retry rates. Compare configuration and code changes, and use a
rollback or feature flag when the regression is significant. After
identifying the bottleneck, reproduce it under representative load and
verify the fix.

Example: If p95 latency rises immediately after deployment and traces
show database time doubled, compare the generated SQL/query plan before
and after the release.
