1. WHAT SPRING AI IS
============================================================

Spring AI is a Spring ecosystem project designed to make it easier for Java and
Spring developers to build applications that use AI models.

The central problem is not simply "how do I call an LLM?"

A real application often needs to connect:

    User
      |
      v
    Spring application
      |
      +---- AI model
      |
      +---- company database
      |
      +---- APIs
      |
      +---- documents
      |
      +---- vector database
      |
      +---- tools and business services

Spring AI provides abstractions so that application code does not have to be
completely tied to one AI provider.

For example, an application can use a ChatModel abstraction instead of directly
building every integration around one vendor SDK.

WHY THIS MATTERS

Without an abstraction layer, an application can become tightly coupled to:

    Provider-specific request classes
    Provider-specific response classes
    Provider-specific configuration
    Provider-specific streaming APIs
    Provider-specific tool-calling mechanisms

Spring AI attempts to put a common Spring-friendly API in front of these
capabilities.

The official reference describes the project's central integration problem as:

    Connecting enterprise data and APIs with AI models.

IMPORTANT MINDSET

Spring AI is not itself an AI model.

It is an application framework and abstraction layer that helps Spring developers
work with AI models and AI application patterns.

============================================================
2. SPRING AI ARCHITECTURE AND DESIGN PHILOSOPHY
============================================================

Spring AI follows several important design ideas.

1. PORTABILITY

The same conceptual API can be used with multiple model providers.

Example:

    ChatClient
        |
        v
    ChatModel abstraction
        |
        +---- OpenAI
        +---- Anthropic
        +---- Google
        +---- Mistral
        +---- Ollama
        +---- Bedrock
        +---- other providers

The exact model capabilities can differ, but the application can keep a
provider-neutral programming model for common operations.

2. COMPOSABILITY

Spring AI features can be combined.

A single application can use:

    ChatClient
        +
    Chat memory
        +
    RAG
        +
    Tool calling
        +
    Observability

3. SPRING BOOT INTEGRATION

Configuration and dependency management follow familiar Spring Boot patterns.

4. MODEL-SPECIFIC ESCAPE HATCHES

Portability does not mean every provider-specific feature disappears.

When an application needs provider-specific functionality, Spring AI allows
developers to access model-specific options and capabilities.

============================================================
3. SUPPORTED AI MODEL TYPES
============================================================

Spring AI works with several categories of AI models.

CHAT MODELS

Input usually consists of messages or prompts.

Output is generated conversational content.

Typical use:

    Question -> Chat model -> Answer

EMBEDDING MODELS

Input is converted into numerical vectors.

Typical use:

    Document -> embedding vector -> vector database

IMAGE MODELS

Generate images from prompts.

Typical use:

    Text description -> image model -> generated image

TRANSCRIPTION MODELS

Convert audio to text.

Typical use:

    Audio -> speech-to-text model -> text

TEXT-TO-SPEECH MODELS

Convert text to spoken audio.

Typical use:

    Text -> TTS model -> audio

MODERATION MODELS

Can be used to assess generated or submitted content according to a model's
moderation capabilities.

============================================================
4. PROVIDER PORTABILITY
============================================================

A major Spring AI idea is to separate:

    Application-level AI logic
from
    Provider-specific implementation.

Suppose an application has:

    String answer = chatClient.prompt()
        .user("Explain dependency injection")
        .call()
        .content();

The application is expressing what it wants to do.

The actual model provider can be configured separately.

This makes it easier to:

    - switch models
    - compare providers
    - use different models for different tasks
    - implement fallback strategies
    - test against local models
    - reduce vendor lock-in

PORTABILITY HAS LIMITS

Different models support different capabilities.

For example:

    Model A -> text only
    Model B -> text + image
    Model C -> text + image + audio
    Model D -> local execution

Therefore, portable application code should rely on capabilities common to the
chosen models, while provider-specific features should be isolated.

    5. Inject ChatClient or another Spring AI abstraction.
    6. Call the AI service.

7. DEPENDENCY MANAGEMENT AND BOM
============================================================

Spring AI provides a Bill of Materials (BOM).

The purpose of a BOM is to keep compatible versions of Spring AI modules aligned.

Conceptually:

    spring-ai-bom
         |
         +---- model module
         +---- vector store module
         +---- supporting modules

Using the BOM avoids manually assigning unrelated versions to every Spring AI
dependency.

For production projects, version management should be deliberate and consistent.

============================================================
8. AI MODELS
============================================================

An AI model is a computational system trained to recognize patterns and generate
or transform information.

For application developers, the important question is not only:

    "Which model is smartest?"

It is:

    "Which model is appropriate for this workload?"

Consider:

    - input modality
    - output modality
    - reasoning quality
    - latency
    - cost
    - context window
    - tool support
    - structured output support
    - streaming
    - deployment model
    - privacy requirements

============================================================
9. PROMPTS
============================================================

A prompt is the input given to an AI model.

A prompt can contain more than one piece of text.

Common message roles include:

    System
    User
    Assistant
    Tool-related messages

SYSTEM MESSAGE

Defines behavior or context.

Example:

    You are a Java expert.
    Explain concepts using simple examples.

USER MESSAGE

Contains the user's actual request.

Example:

    Explain dependency injection.

The model combines these messages according to the provider's API semantics.

============================================================
10. PROMPT TEMPLATES
============================================================

Prompt templates allow dynamic values to be inserted into reusable instructions.

Example:

    "Explain {topic} for a {experienceLevel} developer."

Runtime values:

    topic = "Spring Security"
    experienceLevel = "beginner"

Rendered prompt:

    Explain Spring Security for a beginner developer.

Spring AI uses StringTemplate for prompt template functionality.

WHY TEMPLATES HELP

Without templates, applications often create strings manually.

With templates:

    fixed instruction
        +
    runtime variables
        =
    consistent prompt

This improves maintainability and makes prompts easier to reuse.

============================================================
11. MESSAGES AND MESSAGE ROLES
============================================================

Spring AI represents model input using messages.

A message contains content and a role/type.

The role tells the model how the message should be interpreted.

For example:

    System:
        You are a helpful Java assistant.

    User:
        Explain Spring AI.

    Assistant:
        Previous generated response.

This structure becomes particularly important for:

    - conversation history
    - multimodal input
    - tool calling
    - chat memory
    - RAG

============================================================
12. TOKENS AND CONTEXT WINDOWS
============================================================

AI models process tokens rather than raw human words.

A token can represent part of a word, a complete word, punctuation, or another
piece of text depending on the tokenizer.

TOKEN USAGE MATTERS FOR THREE REASONS

1. Cost

Many hosted models charge according to input/output token usage.

2. Context limits

A model can process only a bounded amount of context per request.

3. Performance

Very large prompts can increase latency and processing cost.

Example:

    User question
        +
    system instructions
        +
    chat history
        +
    retrieved documents
        +
    tool results
        =
    total context

If everything is included blindly, the application can exceed the model's
context window.

This is one reason RAG retrieval and document chunking are important.

============================================================
13. EMBEDDINGS
============================================================

An embedding is a numerical representation of information.

Example:

    "Spring Boot is a Java framework."

might be transformed conceptually into:

    [0.12, -0.48, 0.91, ... ]

The vector itself is not meant to be read by humans.

Its purpose is to represent semantic characteristics in a mathematical space.

SIMILARITY

Suppose:

    Document A = "Spring Boot REST API"
    Query      = "How do I create REST endpoints?"

Their embeddings may be relatively close because their meanings are related.

This enables semantic search.

EMBEDDING DIMENSION

The number of values in the vector is its dimensionality.

Example:

    [0.1, 0.4, -0.2, ...]
     <---- many dimensions ---->

The dimensionality must be compatible with the vector-store configuration.

IMPORTANT

An embedding model is not the same as a chat model.

Chat model:

    prompt -> generated response

Embedding model:

    text/document -> vector

============================================================
14. STRUCTURED OUTPUT
============================================================

AI models commonly return text.

But applications often need an actual Java object.

Example desired result:

    class Product {
        String name;
        double price;
    }

A model might return:

    {
      "name": "Laptop",
      "price": 999.0
    }

That response is initially text.

The application still needs to convert it into:

    Product

Spring AI provides structured output converters for this purpose.

Important implementations include:

    BeanOutputConverter
    MapOutputConverter
    ListOutputConverter

STRUCTURED OUTPUT IS NOT MAGIC

A model can still generate malformed or unexpected output.

Therefore applications should consider:

    - schema constraints
    - validation
    - conversion failures
    - retries
    - model support
    - error handling

============================================================
15. BRINGING YOUR DATA AND APIS TO AI
============================================================

A pretrained model does not automatically know the current contents of your
private database.

For example:

    Company database
        |
        X
        |
    Public model knowledge

The application must explicitly provide access.

Three broad strategies are:

    1. Fine-tuning
    2. Prompt augmentation / context injection
    3. Tool calling

Fine-tuning changes model behavior through additional training.

Prompt augmentation supplies relevant data as context.

Tool calling allows the model to request application-controlled operations.

============================================================
16. FINE-TUNING VS PROMPT AUGMENTATION VS RAG
============================================================

FINE-TUNING

Use when changing model behavior or specialization is the objective.

It is not simply a database lookup mechanism.

PROMPT AUGMENTATION

Place relevant information into the model's context.

Problem:

    Context windows are limited.

RAG

Retrieve only relevant pieces of information and place them into the prompt.

This is often much more practical for frequently changing business knowledge.

============================================================
17. RETRIEVAL AUGMENTED GENERATION
============================================================

RAG stands for Retrieval Augmented Generation.

Basic flow:

    Documents
       |
       v
    Read
       |
       v
    Split
       |
       v
    Embed
       |
       v
    Vector Store
       |
       |  similarity search
       v
    Relevant documents
       |
       v
    Prompt + context
       |
       v
    Chat Model
       |
       v
    Answer

The model generates the answer using retrieved context.

WHY RAG WORKS

Instead of giving the model an entire document collection, retrieve the pieces
that are most relevant to the user's question.

============================================================
18. TOOL CALLING
============================================================

Tool calling allows an AI model to request application-defined operations.

Examples:

    getWeather(city)
    findCustomer(id)
    getAccountBalance(id)
    searchProducts(query)
    sendEmail(to, body)

The model does not directly receive unrestricted access to the underlying API.

The application owns tool execution.

Typical flow:

    User request
       |
       v
    ChatClient
       |
       v
    AI model
       |
       | "I need tool X with arguments Y"
       v
    Spring AI tool mechanism
       |
       v
    Application function
       |
       v
    Tool result
       |
       v
    AI model
       |
       v
    Final response

This pattern is a foundation for agentic applications.

============================================================
19. EVALUATING AI RESPONSES
============================================================

An AI application should not assume every generated response is correct.

Evaluation can consider:

    - relevance
    - coherence
    - factual correctness
    - alignment with the user's request
    - grounding in supplied data

Spring AI provides an Evaluator API for response evaluation strategies.

Evaluation becomes particularly important for:

    - RAG
    - customer-facing assistants
    - document Q&A
    - compliance-sensitive systems
    - production AI systems

22. CHATMODEL AND STREAMINGCHATMODEL
============================================================

23. PROMPT, MESSAGE, CHATOPTIONS AND CHATRESPONSE
============================================================

PROMPT

Represents the model input.

It contains messages and optional chat options.

MESSAGE

Represents one unit of conversational input/output.

CHATOPTIONS

Contains portable generation parameters such as:

    model
    temperature
    max tokens
    top-p
    top-k
    stop sequences
    frequency penalty
    presence penalty

Not every provider necessarily implements every option identically.

CHATRESPONSE

Represents the standardized model response.

It can contain one or more generations and metadata.

============================================================
33. CHATCLIENT API
============================================================

ChatClient is a higher-level, fluent API for communicating with chat models.

It is intentionally similar in style to Spring developers' experience with
WebClient or RestClient.

Simple example:

    @RestController
    class AiController {

        private final ChatClient chatClient;

        AiController(ChatClient.Builder builder) {
            this.chatClient = builder.build();
        }

        @GetMapping("/ai")
        String ask(String question) {
            return chatClient.prompt()
                    .user(question)
                    .call()
                    .content();
        }
    }

This is one of the most useful entry points for normal Spring AI applications.

============================================================
34. CREATING CHATCLIENT
============================================================

Spring Boot can auto-configure a ChatClient.Builder when the required model
integration is present.

You can then build:

    ChatClient client = builder.build();

The client can also be created programmatically when more control is needed.

============================================================
35. USER AND SYSTEM MESSAGES
============================================================

ChatClient supports structured prompt construction.

Example:

    chatClient.prompt()
        .system("You are a Java expert.")
        .user("Explain Spring AI.")
        .call()
        .content();

The system message establishes behavior.

The user message supplies the task.

============================================================
36. RUNTIME PROMPT CUSTOMIZATION
============================================================

A reusable client can have default configuration.

Individual calls can add or override:

    system instructions
    user content
    advisor parameters
    tools
    model options

This is useful for applications serving many different request types.

============================================================
37. SYNCHRONOUS CALLS
============================================================

The normal synchronous pattern is:

    .call()
    .content()

The application waits for the model response and then continues.

This is simple and suitable for:

    REST endpoints
    background jobs
    command-line applications
    non-streaming workflows

============================================================
38. STREAMING RESPONSES
============================================================

Streaming returns generated content progressively.

This is useful for:

    chat interfaces
    long answers
    interactive assistants

Conceptually:

    request
      |
      v
    model
      |
      +--> token/content chunk
      +--> token/content chunk
      +--> token/content chunk
      +--> ...
      |
      v
    complete response

============================================================
39. MULTIPLE CHAT MODELS
============================================================

An application may need several models.

Examples:

    Model A -> complex reasoning
    Model B -> inexpensive classification
    Model C -> fast response
    Model D -> specialized coding

Use cases include:

    - task-based routing
    - fallback
    - A/B testing
    - user-selected models
    - specialized workloads

The application should make model selection explicit rather than assuming every
model has identical capabilities.

============================================================
40. CHAT MEMORY
============================================================

Chat memory stores conversation history.

Without memory:

    User: My name is Alex.
    Assistant: Nice to meet you.
    User: What is my name?

The model may not know the previous message unless history is supplied.

With memory:

    conversation id
        |
        v
    stored messages
        |
        v
    current request
        |
        v
    model

Spring AI provides ChatMemory abstractions.

============================================================
41. CHAT MEMORY REPOSITORIES
============================================================

The current documentation describes MessageWindowChatMemory as a built-in
implementation.

It maintains a bounded message window.

The memory repository abstraction can be backed by different storage mechanisms,
including implementations for:

    In-memory
    JDBC
    Cassandra
    Neo4j
    MongoDB
    Redis

The choice depends on whether memory should survive application restarts and
whether the application is distributed.

============================================================
42. RAG THROUGH CHATCLIENT
============================================================

ChatClient can combine advisors for memory and RAG.

Conceptual example:

    ChatClient
       |
       +---- MessageChatMemoryAdvisor
       |
       +---- QuestionAnswerAdvisor
       |
       +---- ChatModel

The memory advisor can supply conversation context.

The RAG advisor can retrieve relevant documents.

The model then receives a richer prompt.

============================================================
43. LOGGING AND ADVISORS
============================================================

Advisors can be used to observe or transform requests.

A logging advisor can help inspect:

    request
    response

However, production logging must be designed carefully because prompts and
responses can contain sensitive information.

============================================================
44. PROMPT ENGINEERING FUNDAMENTALS
============================================================

Prompt engineering means designing model instructions intentionally.

Good prompts generally provide:

    context
    task
    constraints
    expected output
    relevant data

Weak:

    "Explain Java."

Better:

    "Explain Java dependency injection to a developer with two years of
     experience. Use one simple example, one production example, and list
     three common mistakes."

The goal is not merely making prompts longer.

The goal is making them clearer and more useful.

============================================================
45. PROMPT TEMPLATES
============================================================

Templates separate stable instructions from changing values.

Example:

    Explain {topic} for a {level} developer.

This allows one template to serve:

    Java / beginner
    Spring AI / intermediate
    RAG / advanced

46. STRUCTURED OUTPUT CONVERTERS
============================================================

Structured output converters help transform model-generated text into useful
application structures.

Available converter concepts include:

    BeanOutputConverter
    MapOutputConverter
    ListOutputConverter

A converter typically combines:

    output-format instructions
       +
    model response
       +
    conversion logic

============================================================
47. BEANOUTPUTCONVERTER
============================================================

BeanOutputConverter targets a Java type.

Example:

    class Movie {
        String title;
        int year;
    }

The converter can provide format instructions based on the target structure
and convert compatible model output into a Java object.

This is useful when AI output feeds directly into business logic.

============================================================
48. MAPOUTPUTCONVERTER
============================================================

MapOutputConverter is useful when the application wants structured key/value

Conceptually:

    model text
       |
       v
    JSON object
       |
       v
    Map<String, Object>

============================================================
49. LISTOUTPUTCONVERTER
============================================================

ListOutputConverter is useful when the model should produce a list.

Example request:

    "Return five Java topics."

Desired application representation:

    List<String>

The application still needs to handle conversion failures.

============================================================
50. SCHEMA-ORIENTED OUTPUT
============================================================

When structured data is required, applications should think in terms of a
contract.

For example:

    Product:
        name: string
        price: number
        available: boolean

This is more reliable than simply telling the model:

    "Give me JSON."

Structured output mechanisms can provide stronger formatting guidance, but
model output should still be validated.

============================================================
51. RELIABILITY CONSIDERATIONS
============================================================

Never assume generated output is automatically trustworthy.

Possible failures:

    malformed JSON
    missing field
    wrong type
    extra field
    hallucinated value
    incomplete response

Production applications should validate structured results before using them.

52. ADVISORS API

Examples:

    memory

Instead of putting all logic inside a controller, advisors let the behavior

57. MESSAGECHATMEMORYADVISOR

This advisor retrieves conversation history and adds it to the prompt.

58. VECTORSTORECHATMEMORYADVISOR

This advisor uses a vector store as a memory mechanism.

This is useful when the conversation history becomes large and relevance-based

59. QUESTIONANSWERADVISOR

============================================================
65. WHAT TOOL CALLING MEANS
============================================================

Tool calling allows a model to request application-defined functions.

It changes the application from:

    "AI only generates text"

to:

    "AI can request controlled operations."

Examples:

    Query a database
    Search a product catalog
    Check weather
    Create an order
    Retrieve account information

The application remains responsible for execution.

============================================================
66. TOOL CALLING ARCHITECTURE
============================================================

Spring AI 2.x makes the tool-calling loop a first-class component of the
ChatClient advisor chain.

High-level flow:

    1. Define tools.
    2. Register tools with ChatClient.
    3. Send request.
    4. Model decides whether to call a tool.
    5. ToolCallingManager executes the selected callback.
    6. Tool result is added to the conversation.
    7. Model receives the result.
    8. Loop continues until no more tool calls are requested.

============================================================
67. DEFINING TOOLS WITH @TOOL
============================================================

A method can be exposed as a tool using @Tool.

Example:

    class WeatherTools {

        @Tool(description = "Get current weather for a city")
        public String getWeather(String city) {
            return weatherService.fetch(city);
        }
    }

The description is important.

The model uses the description to understand when the tool should be called.

============================================================
68. @TOOLPARAM
============================================================

Tool parameters should also be described when necessary.

Example:

    @Tool(description = "Get weather for a city")
    public String getWeather(
        @ToolParam(description = "City name") String city) {

        return weatherService.fetch(city);
    }

A well-described parameter helps the model construct correct tool arguments.

============================================================
69. METHODTOOLCALLBACK
============================================================

MethodToolCallback provides programmatic control over method-backed tools.

It is useful when:

    - the source method is not yours
    - registration is dynamic
    - tool definitions need to be constructed at runtime

============================================================
70. FUNCTIONTOOLCALLBACK
============================================================

FunctionToolCallback can expose:

    Function
    Supplier
    Consumer
    BiFunction
    lambdas
    method references

Example concept:

    FunctionToolCallback.builder(
        "currentWeather",
        weatherService::getWeather
    )
    .description("Get the weather")
    .inputType(WeatherRequest.class)
    .build();

============================================================
71. TOOLCALLBACK BEANS
============================================================

ToolCallback objects can be Spring beans.

This allows normal Spring dependency injection and configuration.

The tool can then be explicitly supplied to ChatClient.

============================================================
72. PASSING TOOLS TO CHATCLIENT
============================================================

Tools can be supplied for one request:

    chatClient.prompt(...)
        .tools(weatherTools)
        .call();

Or configured as defaults:

    ChatClient.builder(chatModel)
        .defaultTools(weatherTools)
        .build();

Per-call tools are useful when only certain operations should be available for
a specific request.

============================================================
73. DEFAULT TOOLS VS PER-CALL TOOLS
============================================================

Default tools are available to every request created from that client.

This is convenient for safe, frequently needed tools.

However, destructive or high-risk operations should generally not be globally
available.

Examples of high-risk operations:

    deleteCustomer()
    transferMoney()
    cancelOrder()
    sendExternalEmail()

These should have explicit authorization and careful registration.

============================================================
74. TOOL CALLING LOOP
============================================================

The loop is:

    Request
       |
       v
    Model
       |
       +---- normal response ----> finish
       |
       +---- tool request
                |
                v
           execute tool
                |
                v
           tool result
                |
                v
              model
                |
             repeat

This loop can continue more than once.

============================================================
75. TOOL RESULTS AND MODEL ITERATION
============================================================

The model receives the tool result as additional conversation context.

It can then:

    - answer the user
    - call another tool
    - revise the reasoning
    - request additional information

This is the basis of multi-step agentic behavior.

============================================================
76. SECURITY BOUNDARIES
============================================================

A critical security principle:

The model does not receive unrestricted access to your application APIs.

The application owns the execution mechanism.

Still, the application must validate:

    tool arguments
    authorization
    tenant boundaries
    user permissions
    destructive actions
    external side effects

Never assume that because a model requested a tool, the action is automatically
authorized.

    streaming behavior
    structured output behavior
    model-specific limitations

78. WHAT A VECTOR DATABASE IS
============================================================

A vector database stores vector representations and supports similarity search.

Traditional database query:

    WHERE name = 'Spring'

Vector search:

    Find vectors most similar to the query vector.

This is useful when exact keyword matching is insufficient.

119. DOCUMENT SPLITTING
============================================================

Bad:

    split randomly in the middle of a paragraph
    split in the middle of code
    split tables incorrectly

Better:

    preserve semantic boundaries first
    then enforce manageable chunk sizes

The goal is:

    enough context
    without wasting tokens

       +---- chunk 3
       +---- ...

127. RAG QUALITY AND FAILURE MODES
============================================================

Common RAG failures:

1. Wrong chunk size
2. Poor embedding model
3. Missing metadata
4. Incorrect similarity threshold
5. Too many retrieved documents
6. Too few retrieved documents
7. Duplicate chunks
8. Stale documents
9. Query wording mismatch
10. Poor source cleanup

RAG quality is therefore an engineering problem, not just a model-selection
problem.

128. WHAT MCP IS
============================================================

MCP stands for Model Context Protocol.

It standardizes how AI applications interact with external tools and resources.

Think of MCP as a protocol boundary between:

    AI application
        |
        v
    standardized MCP interface
        |
        +---- tools
        +---- resources
        +---- prompts
        |
        v
    external system

Spring AI supports both consuming MCP servers and exposing Spring services
through MCP.

============================================================
137. STDIO
============================================================

STDIO is process-based communication.

It is useful for local MCP servers that run alongside or are launched by a
client process.

Because it is not network-accessible in the same way as an HTTP endpoint,
its security model differs from network transports.

============================================================
138. SSE
============================================================

Server-Sent Events can be used for HTTP-based MCP communication.

The current Spring AI documentation notes that SSE-based server configuration
has been superseded in some 2.0 server scenarios by Streamable HTTP.

============================================================
139. STREAMABLE HTTP
============================================================

Streamable HTTP provides an HTTP-based MCP transport suitable for networked
applications.

Spring AI supports it through WebMVC and WebFlux starter configurations.

============================================================
140. STATELESS STREAMABLE HTTP
============================================================

Stateless transport is useful when the server architecture should avoid
maintaining protocol session state in the same way as a stateful server.

223. SPRING AI INTERVIEW CONCEPTS
============================================================

Q: What is Spring AI?

A:
Spring AI is a Spring ecosystem project that provides abstractions and
integrations for building AI applications with models, vector stores, tools,
RAG, memory, observability and related capabilities.

Q: What is ChatClient?

A:
A fluent higher-level API for interacting with chat models.

Q: ChatClient vs ChatModel?

A:
ChatModel is a lower-level model abstraction. ChatClient provides a more
convenient application-level fluent API and integrates naturally with advisors,
tools and memory.

Q: What is an embedding?

A:
A numerical vector representation used to capture semantic relationships.

Q: Why is a vector database used in RAG?

A:
It allows similarity-based retrieval of relevant document chunks.

Q: What is RAG?

A:
Retrieval Augmented Generation retrieves relevant external information and
adds it to the model context before generation.

Q: What is tool calling?

A:
A mechanism where a model requests application-defined functions and the
application executes them and returns the results.

Q: Does the model directly execute a Java method?

A:
No. The application owns tool execution. The model requests a tool call and
the application executes the corresponding tool.

Q: What is an Advisor?

A:
A reusable component that can inspect, transform or augment AI requests and
responses.

Q: What is MCP?

A:
A standardized protocol for connecting AI applications with external tools,
resources and prompts.

Q: Why is chunking important in RAG?

A:
Because retrieval operates on stored document pieces. Poor chunks can lose
meaning or return irrelevant context.

224. IMPORTANT COMPARISONS
============================================================

CHATMODEL vs CHATCLIENT

ChatModel:
    lower-level
    direct model interaction
    more control

ChatClient:
    fluent API
    higher-level application abstraction
    easy advisor/tool/memory integration

CHAT MODEL vs EMBEDDING MODEL

Chat:
    generates responses

Embedding:
    generates vectors

RAG vs FINE-TUNING

RAG:
    retrieves external/current information at request time

Fine-tuning:
    changes model behavior/weights through additional training

VECTOR DATABASE vs RELATIONAL DATABASE

Vector database:
    similarity-oriented retrieval

Relational database:
    structured transactional/query-oriented storage

TOOL CALLING vs RAG

RAG:
    retrieves information

Tool calling:
    executes application operations or retrieves dynamic data

MEMORY vs RAG

Memory:
    preserves conversation context

RAG:
    retrieves external knowledge

MCP vs TOOL CALLBACK

ToolCallback:
    Spring AI's application-level tool execution abstraction

MCP:
    standardized protocol for exposing/consuming tools and resources across
    application boundaries

FINAL MENTAL MODEL
============================================================

The easiest way to understand Spring AI is to see it as a collection of layers.

LAYER 1 — MODEL

    Chat
    Embedding
    Image
    Audio

LAYER 2 — APPLICATION API

    ChatClient
    Prompt
    Message
    Options
    Response

LAYER 3 — CONTEXT

    Memory
    RAG
    VectorStore
    Advisors

LAYER 4 — ACTIONS

    Tools
    Tool calling
    MCP

LAYER 5 — DATA ENGINEERING

    DocumentReader
    DocumentTransformer
    DocumentWriter
    ETL
    Chunking
    Embeddings
    Vector storage

LAYER 6 — OPERATIONS

    Observability
    Metrics
    Tracing
    Evaluation
    Security

The complete picture is:

    USER
      |
      v
    SPRING BOOT APPLICATION
      |
      v
    CHATCLIENT
      |
      +-------------------+
      |                   |
      v                   v
    ADVISORS            TOOLS
      |                   |
      +----+--------------+
           |
           v
        CONTEXT
        /     \
     MEMORY    RAG
                |
                v
           VECTOR STORE
                |
                v
          RETRIEVED DATA
                |
                v
           CHAT MODEL
                |
                v
             ANSWER

And when the model needs to perform an action:

    CHAT MODEL
        |
        v
    TOOL CALL
        |
        v
    APPLICATION
        |
        v
    EXTERNAL API / DATABASE / SERVICE
        |
        v
    TOOL RESULT
        |
        v
    CHAT MODEL
        |
        v
    FINAL ANSWER

The central engineering principle is:

    The model generates intelligence,
    the application controls the system,
    retrieval supplies knowledge,
    tools provide actions,
    memory supplies conversation context,
    and observability/evaluation make the system measurable and safer.
