==============================================================================
1. INTRODUCTION TO SPRING BOOT
==============================================================================

----------------------------------------------------------------------
1.1 WHAT IS SPRING BOOT?
----------------------------------------------------------------------
Spring Boot is a Java-based framework built on top of the Spring Framework. Its main purpose is to make it easier to create stand-alone, production-ready Spring applications with less manual configuration.

The important word is simplification. Traditional Spring applications can require developers to configure many pieces themselves. Spring Boot provides sensible defaults, auto-configuration, starter dependencies, embedded servers, and production-oriented features so that the developer can concentrate more on application behavior.

Think of it this way:

Traditional approach:
    Choose libraries -> configure them -> configure the server -> wire components -> run application

Spring Boot approach:
    Choose starters -> write application code -> Boot configures common infrastructure -> run application

Spring Boot does not replace Spring Core. It builds on the Spring ecosystem and makes common Spring application setup much easier.

A Spring Boot application can be packaged and run as an executable JAR. For web applications, an embedded server such as Tomcat can be included so the application can start without requiring a separately installed servlet container.

----------------------------------------------------------------------
1.2 FEATURES OF SPRING BOOT
----------------------------------------------------------------------
AUTO-CONFIGURATION
Spring Boot examines the application classpath and configuration and automatically configures many common components. For example, adding web-related dependencies allows Boot to prepare the application for web development.

STARTER DEPENDENCIES
A starter groups dependencies for a common purpose. Instead of manually adding many related libraries, the application can depend on a starter such as spring-boot-starter-web or spring-boot-starter-data-jpa.

STAND-ALONE APPLICATIONS
Applications can run independently, commonly with an embedded server. A packaged application can be started with a command such as:

    java -jar app.jar

OPINIONATED DEFAULTS
Spring Boot follows conventions and provides default choices for common scenarios. You can override these choices when your application needs different behavior.

PRODUCTION-READY FEATURES
Spring Boot Actuator provides endpoints and infrastructure for health checks, metrics, environment information, and other operational needs.

REDUCED BOILERPLATE
The combination of starters, auto-configuration, annotations, and sensible defaults reduces repetitive setup code.

CONFIGURATION FLEXIBILITY
Application behavior can be configured with application.properties, application.yml, environment variables, command-line arguments, and profiles.

NO XML REQUIRED FOR COMMON SETUPS
Spring Boot encourages Java configuration and annotations, although the exact configuration style depends on the application.

----------------------------------------------------------------------
1.3 ADVANTAGES AND USE CASES
----------------------------------------------------------------------
Advantages include rapid development, embedded servers, simplified dependency management, easier microservice development, production-oriented features, flexible configuration, and integration with the wider Spring ecosystem.

Typical use cases include:
- REST APIs
- Microservices
- Enterprise web applications
- Cloud-oriented backend services
- Rapid prototypes
- E-commerce systems
- Banking and financial systems
- Healthcare systems
- Travel and booking platforms
- Learning management systems
- Logistics and supply-chain systems
- CMS and HR/payroll systems
- IoT backend services

The key idea is that Spring Boot is useful whenever a Java application needs a structured application framework with dependency management, web support, data access, security, testing, and operational tooling.

----------------------------------------------------------------------
1.4 SPRING BOOT VS SPRING FRAMEWORK
----------------------------------------------------------------------
Spring Framework provides the underlying ecosystem and core capabilities such as dependency injection and application infrastructure. Spring Boot focuses on simplifying the setup and operational packaging of Spring applications.

A useful comparison:

Spring Framework:
- More manual configuration is possible.
- Dependency choices are managed more directly by the developer.
- External server setup may be required depending on the application.
- Production monitoring usually requires additional setup.

Spring Boot:
- Auto-configuration reduces setup work.
- Starters simplify dependency selection.
- Embedded servers support stand-alone web applications.
- Actuator provides production-oriented endpoints.
- Executable JAR packaging is a common deployment model.

Do not think of this as “Spring versus Boot.” Spring Boot is built around Spring capabilities and makes common Spring development faster and more convention-driven.

----------------------------------------------------------------------
1.5 SPRING BOOT ARCHITECTURE
----------------------------------------------------------------------
The guide describes the main architectural building blocks as Spring Core, auto-configuration, starter dependencies, Spring Boot CLI, embedded servers, and Spring Boot Actuator.

At the application level, a common request flow looks like:

    Client
       |
       | HTTP request
       v
    Controller
       |
       v
    Service layer
       |
       v
    Repository / data access
       |
       v
    Database

Dependency injection connects the components. The controller handles the web request, the service contains business rules, and the repository/data-access layer communicates with the database.

The architecture diagram in the this guide also shows the client -> controller -> service -> model/database relationship and dependency injection between application components. The important lesson is separation of responsibilities rather than putting all logic into one controller.

2. GETTING STARTED
==============================================================================

----------------------------------------------------------------------
2.1 SETTING UP A SPRING BOOT PROJECT
----------------------------------------------------------------------
The this guide introduces Spring Initializr as the starting point for creating a Spring Boot project. It also identifies Maven and Gradle as common build tools.

Typical project choices include:
- Build tool: Maven or Gradle
- Language: Java, Kotlin, or Groovy
- Project metadata: group and artifact
- Spring Boot version
- Dependencies required by the application

The important concept is that the build tool manages dependencies and packaging. Spring Initializr creates a project structure and build configuration so the developer can start writing application code quickly.

----------------------------------------------------------------------
2.2 PROJECT STRUCTURE OVERVIEW
----------------------------------------------------------------------
A typical Spring Boot project separates source code from resources and tests.

A common structure is:

src/
  main/
    java/
      ... application packages ...
    resources/
      application.properties or application.yml
  test/
    java/
      ... test classes ...

target/
  ... build output ...

A layered application may contain packages such as:
- controller: HTTP endpoints
- service: business logic
- repository or dao: persistence logic
- model/entity: application and database objects

The exact package names can vary. The important point is to keep responsibilities understandable and keep the main application class in a package that allows component scanning to discover the application components.

----------------------------------------------------------------------
2.3 APPLICATION ENTRY POINT: @SpringBootApplication
----------------------------------------------------------------------
@SpringBootApplication is the main convenience annotation used at the application entry point. The guide explains it as a combination of:

    @Configuration
    @EnableAutoConfiguration
    @ComponentScan

Example:

@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

Conceptually:
- @Configuration tells Spring that the class can provide configuration.
- @EnableAutoConfiguration enables Boot's automatic configuration mechanism.
- @ComponentScan tells Spring to discover component classes in the relevant package hierarchy.

SpringApplication.run(...) starts the Spring application context and begins application startup.

----------------------------------------------------------------------
2.4 RUNNING THE APPLICATION
----------------------------------------------------------------------
The application can be started from an IDE, through the build tool, or from a packaged JAR.

For a packaged application, the guide uses:

    java -jar target/myapp.jar

During startup, Spring creates the application context, discovers configuration and components, creates beans, wires dependencies, and starts required infrastructure such as the embedded web server when the application is a web application.

When startup succeeds, the console normally contains startup messages showing that the application has started and, for web applications, the server has been initialized.

3. CORE CONCEPTS
==============================================================================

----------------------------------------------------------------------
3.1 SPRING BOOT ANNOTATIONS
----------------------------------------------------------------------
Spring Boot applications use annotations to describe components, configuration, web endpoints, dependency injection, and other behavior. The important skill is knowing the role of an annotation rather than simply knowing its name.

----------------------------------------------------------------------
@SpringBootApplication
----------------------------------------------------------------------
This is the application entry point and combines configuration, auto-configuration, and component scanning.

Interview point:
Q: What does @SpringBootApplication contain?
A: @Configuration + @EnableAutoConfiguration + @ComponentScan.

----------------------------------------------------------------------
@Component
----------------------------------------------------------------------
@Component marks a class as a Spring-managed component. It is a general-purpose stereotype used when a class does not more specifically represent a service, repository, or controller.

Example:

@Component
public class PriceCalculator {
    public double calculate(double price) {
        return price * 1.18;
    }
}

Once discovered by component scanning, Spring can create and manage this object as a bean.

----------------------------------------------------------------------
@Service
----------------------------------------------------------------------
@Service is a specialization of @Component intended for service-layer classes. The service layer is where business rules are normally placed.

Example:

@Service
public class OrderService {
    public void processOrder() {
        // business logic
    }
}

Using @Service communicates intent. Another developer can immediately understand that the class represents business operations rather than HTTP handling or persistence.

----------------------------------------------------------------------
@Repository
----------------------------------------------------------------------
@Repository identifies a data-access component. It is commonly used for classes or interfaces responsible for persistence operations. The guide also highlights exception translation into Spring's data-access exception hierarchy.

Example:

@Repository
public class ProductRepository {
    public void save(Product product) {
        // persistence logic
    }
}

In Spring Data applications, repository interfaces such as JpaRepository are commonly used instead of writing every CRUD operation manually.

----------------------------------------------------------------------
@Controller
----------------------------------------------------------------------
@Controller is used in Spring MVC for web controllers that commonly return view names.

Example:

@Controller
public class HomeController {
    @GetMapping("/")
    public String index(Model model) {
        model.addAttribute("message", "Welcome");
        return "index";
    }
}

The returned value represents a view name that a view resolver can use to locate a template.

----------------------------------------------------------------------
@RestController
----------------------------------------------------------------------
@RestController is used for REST APIs. The guide describes it as:

    @Controller + @ResponseBody

The important difference is that the returned object is written to the HTTP response body and can be serialized into formats such as JSON.

Example:

@RestController
@RequestMapping("/users")
public class UserController {
    @GetMapping
    public List<User> getUsers() {
        return userService.getAll();
    }
}

A common interview question is: “What is the difference between @Controller and @RestController?” The short answer is that @Controller is commonly used for MVC views, while @RestController is designed for response bodies in REST-style APIs.

----------------------------------------------------------------------
@Autowired AND @Qualifier
----------------------------------------------------------------------
@Autowired asks Spring to inject a suitable bean. Injection can be performed through a constructor, setter, or field. The guide includes all three forms and uses constructor injection as an example.

Constructor injection:

@Service
public class OrderService {
    private final PaymentService paymentService;

    @Autowired
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

The dependency is explicit and the field can remain final.

@Qualifier becomes important when more than one bean matches the same dependency type.

@Component("dieselEngine")
class DieselEngine implements Engine { }

@Component("petrolEngine")
class PetrolEngine implements Engine { }

Then:

@Autowired
@Qualifier("dieselEngine")
private Engine engine;

Spring now knows which Engine implementation should be injected.

----------------------------------------------------------------------
@Configuration AND @Bean
----------------------------------------------------------------------
@Configuration marks a class that contains configuration and bean definitions.

@Bean is placed on a method to tell Spring that the object returned by the method should be managed as a bean.

Example:

@Configuration
public class AppConfig {

    @Bean
    public UserRepository userRepository() {
        return new InMemoryUserRepository();
    }

    @Bean
    public UserService userService() {
        return new UserServiceImpl(userRepository());
    }
}

Use @Component when Spring can discover a class directly. Use @Bean when you want to create or configure an object explicitly, including objects from third-party libraries that you cannot annotate yourself.

----------------------------------------------------------------------
3.2 DEPENDENCY INJECTION (DI)
----------------------------------------------------------------------
Dependency Injection means an object receives the objects it depends on instead of constructing those dependencies itself.

Without DI:

public class OrderService {
    private PaymentService paymentService = new PaymentService();
}

The class decides exactly which implementation to construct. That creates stronger coupling.

With DI:

public class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

Spring can supply the dependency when it creates OrderService.

Why DI matters:
- Loose coupling
- Easier unit testing
- Better maintainability
- Easier replacement of implementations
- Clearer dependencies
- Better alignment with dependency inversion principles

THREE COMMON FORMS
1. Constructor injection — dependencies are passed through the constructor and are commonly preferred for required dependencies.
2. Setter injection — dependencies are supplied through setters and can be useful for optional dependencies.
3. Field injection — Spring injects directly into fields; it is concise but hides dependencies and is less convenient for isolated unit testing.

----------------------------------------------------------------------
3.3 INVERSION OF CONTROL (IoC)
----------------------------------------------------------------------
IoC is the broader principle behind the container-managed model. Instead of application code controlling every object creation and dependency relationship, the Spring container takes responsibility for creating and wiring managed objects.

High-level flow:
1. You define components and configuration.
2. Spring scans the application and discovers relevant beans.
3. Spring creates bean instances.
4. Spring resolves dependencies.
5. Spring injects those dependencies.
6. Spring manages the bean lifecycle.

DI is one way IoC is implemented. A useful interview distinction is:

IoC = principle
DI = technique used to achieve IoC

The Spring container is therefore central to both concepts.

4. CONFIGURATION
==============================================================================

----------------------------------------------------------------------
4.1 application.properties VS application.yml
----------------------------------------------------------------------
Both formats can express Spring Boot configuration.

Properties style:

server.port=8081
spring.datasource.url=jdbc:mysql://localhost:3306/db
spring.datasource.username=root
spring.datasource.password=pass

YAML style:

server:
  port: 8081
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/db
    username: root
    password: pass

Properties uses key=value pairs. YAML represents nested configuration hierarchically using indentation.

The choice is mostly about readability and team pguide. YAML can make deeply grouped settings easier to visualize, while properties is very direct for individual values.

----------------------------------------------------------------------
4.2 EXTERNAL CONFIGURATION
----------------------------------------------------------------------
Spring Boot supports configuration from several external sources. The guide emphasizes command-line arguments, environment variables, configuration files, and profile-specific files.

Example environment variable:

SPRING_DATASOURCE_URL=jdbc:mysql://localhost:3306/db

This corresponds conceptually to:

spring.datasource.url

Example command-line override:

java -jar myapp.jar --server.port=9090 --logging.level.root=DEBUG

The major benefit is separation of code from environment-specific values. The same application artifact can be deployed to different environments without changing source code.

----------------------------------------------------------------------
4.3 PROFILES
----------------------------------------------------------------------
Profiles allow an application to use different beans or settings for different environments such as development, testing, and production.

Common files:

application-dev.properties
application-prod.yml

A profile can be activated using:

spring.profiles.active=dev

or through a command-line argument:

java -jar app.jar --spring.profiles.active=prod

@Profile can conditionally activate configuration or beans.

@Configuration
@Profile("dev")
public class DevConfig {
    @Bean
    public String dataSource() {
        return "H2 In-Memory DB for Dev";
    }
}

The key idea is: one codebase, different environment behavior.

----------------------------------------------------------------------
4.4 @Value VS @ConfigurationProperties
----------------------------------------------------------------------
@Value is convenient when you need one or a few individual configuration values.

@Value("${server.port}")
private int port;

It can also define a fallback:

@Value("${custom.message:Default Message}")
private String message;

@ConfigurationProperties is better suited to a group of related settings.

Example configuration:

app:
  name: MyApp
  version: 1.0

A properties class can bind the group:

@Component
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    private String name;
    private String version;
}

Mental model:

@Value -> “Give me this one value.”
@ConfigurationProperties -> “Bind this configuration section into an object.”

The grouped approach is especially useful when configuration grows and needs stronger structure and validation.

5. SPRING BOOT STARTERS
==============================================================================

----------------------------------------------------------------------
5.1 WHAT ARE STARTERS?
----------------------------------------------------------------------
A starter is a predefined dependency bundle for a particular capability. Instead of manually selecting every library required for web development, JPA, security, testing, and similar features, a starter gives the project a convenient dependency entry point.

Example:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Benefits:
- Less dependency configuration
- Easier project setup
- Related libraries are brought together
- Version management is simplified by the Spring Boot dependency setup

A starter does not mean “one library does everything.” It is a convenient way to bring in a compatible set of dependencies for a common use case.

----------------------------------------------------------------------
5.2 COMMON STARTERS
----------------------------------------------------------------------
spring-boot-starter-web
Used for web applications and REST APIs. The guide identifies Spring MVC, Jackson, and an embedded Tomcat as important pieces.

spring-boot-starter-data-jpa
Used for relational database access with Spring Data JPA. The guide identifies Spring Data JPA, Hibernate, and Spring ORM.

spring-boot-starter-security
Adds Spring Security support for authentication and authorization.

spring-boot-starter-test
Provides common testing tools such as JUnit, Mockito, Spring Test, and AssertJ.

Other starters mentioned include Thymeleaf, Mail, Actuator, and Validation.

Interview tip: Be able to explain why you would choose a starter rather than listing individual dependencies from memory.

6. WEB DEVELOPMENT WITH SPRING MVC
==============================================================================

----------------------------------------------------------------------
6.1 CREATING REST APIS
----------------------------------------------------------------------
A REST controller maps HTTP requests to Java methods.

Example:

@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return new User(id, "John Doe");
    }
}

The request:

GET /api/users/10

matches /{id}, and Spring binds 10 to the id method parameter.

A typical layered API is:

HTTP request
    -> Controller
    -> Service
    -> Repository
    -> Database

Keeping database operations out of the controller helps maintain a clean separation of responsibilities.

----------------------------------------------------------------------
6.2 REQUEST PARAMETERS: @PathVariable, @RequestParam, @RequestBody
----------------------------------------------------------------------
@PathVariable extracts a value from the URL path.

GET /users/42

@GetMapping("/users/{id}")
public User get(@PathVariable Long id) { ... }

@REQUESTPARAM extracts query parameters.

GET /users?role=admin

@GetMapping("/users")
public List<User> find(@RequestParam String role) { ... }

@REQUESTBODY converts the HTTP request body into a Java object.

POST /users
Content-Type: application/json

{
  "name": "Alice"
}

@PostMapping("/users")
public ResponseEntity<String> create(@RequestBody User user) { ... }

Simple memory rule:
@PathVariable -> value inside the path
@RequestParam -> value after ?
@RequestBody -> data sent inside the request body

----------------------------------------------------------------------
6.3 ResponseEntity AND HTTP STATUS CODES
----------------------------------------------------------------------
ResponseEntity gives explicit control over the response body, headers, and HTTP status.

Example:

@GetMapping("/{id}")
public ResponseEntity<User> getUser(@PathVariable Long id) {
    User user = userService.findById(id);
    if (user == null) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).build();
    }
    return ResponseEntity.ok(user);
}

The important lesson is that APIs should communicate outcome through appropriate HTTP status codes, not only through a text message.

Common examples:
200 OK -> successful request
201 Created -> resource created
400 Bad Request -> invalid client input
401 Unauthorized -> authentication is required or failed
403 Forbidden -> caller is not allowed
404 Not Found -> requested resource does not exist
500 Internal Server Error -> unexpected server-side problem

----------------------------------------------------------------------
6.4 EXCEPTION HANDLING
----------------------------------------------------------------------
@ExceptionHandler handles a particular exception. @ControllerAdvice allows exception handling to be centralized across controllers.

Example:

@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<String> handleUserNotFound(UserNotFoundException ex) {
        return ResponseEntity
            .status(HttpStatus.NOT_FOUND)
            .body(ex.getMessage());
    }
}

Without centralized handling, every controller may repeat the same try/catch and response-building logic. Global handling creates consistent API behavior.

----------------------------------------------------------------------
6.5 CONTENT NEGOTIATION
----------------------------------------------------------------------
Content negotiation allows the response representation to depend on the client's requested media type.

For example, an endpoint can declare JSON and XML representations:

@GetMapping(value = "/info",
    produces = {MediaType.APPLICATION_JSON_VALUE,
                MediaType.APPLICATION_XML_VALUE})
public User getInfo() {
    return new User(1L, "Alice");
}

If the client sends an Accept header requesting application/json, the response can be JSON. If it requests application/xml and the application supports the representation, XML can be selected.

The key concept is that the same logical resource can have more than one representation.

7. DATA ACCESS
==============================================================================

----------------------------------------------------------------------
7.1 SPRING DATA JPA
----------------------------------------------------------------------
Spring Data JPA reduces persistence boilerplate by providing repository abstractions and query support.

The typical relationship is:

Entity -> represents persisted data
Repository -> performs data access
Service -> applies business rules
Controller -> exposes API

@Entity marks a class as a persistent entity.

@Entity
public class User {
    @Id
    @GeneratedValue
    private Long id;
    private String name;
}

The repository can extend JpaRepository:

public interface UserRepository extends JpaRepository<User, Long> {
    List<User> findByName(String name);
}

Spring Data can derive queries from method names. This avoids writing repetitive CRUD implementation code.

----------------------------------------------------------------------
7.1.1 CRUD REPOSITORIES
----------------------------------------------------------------------
CrudRepository provides common CRUD operations. JpaRepository builds on the repository abstraction and provides JPA-oriented capabilities.

Typical operations include:
- save
- findById
- findAll
- deleteById
- delete

The developer describes the repository contract and Spring Data provides the implementation infrastructure.

This is one of the major productivity benefits of Spring Data: a repository interface can provide useful database operations without a large hand-written DAO class.

----------------------------------------------------------------------
7.1.2 CUSTOM QUERIES WITH @Query
----------------------------------------------------------------------
When a derived method name is not sufficient, @Query can define a query explicitly.

Example:

@Query("SELECT u FROM User u WHERE u.name LIKE %:name%")
List<User> searchByName(@Param("name") String name);

The guide describes support for JPQL and native SQL. The important distinction is that JPQL works with entity concepts and fields, while a native query can express database-specific SQL when required.

----------------------------------------------------------------------
7.1.3 PAGINATION AND SORTING
----------------------------------------------------------------------
Returning thousands of records in one request is inefficient. Pagination breaks a large result set into smaller pages.

Example:

Page<User> page = userRepository.findAll(
    PageRequest.of(0, 10, Sort.by("name"))
);

Here:
- 0 is the page index.
- 10 is the page size.
- Sort.by("name") requests ordering by name.

The practical benefit is lower memory use, smaller responses, and more predictable API behavior.

----------------------------------------------------------------------
7.2 JDBC WITH SPRING BOOT
----------------------------------------------------------------------
JdbcTemplate provides more direct control over SQL. It is useful when you want to write SQL explicitly instead of relying on JPA entity mapping.

Example:

@Repository
public class UserDao {
    private final JdbcTemplate jdbcTemplate;

    public List<User> getUsers() {
        return jdbcTemplate.query(
            "SELECT * FROM users",
            (rs, rowNum) -> new User(
                rs.getLong("id"),
                rs.getString("name")
            )
        );
    }
}

JPA is generally more abstraction-oriented. JdbcTemplate is more SQL-oriented.

Interview comparison:
JPA -> entity/object model, repository abstraction, less SQL for common operations.
JDBC -> direct SQL control, explicit result mapping, useful when fine-grained SQL is important.

----------------------------------------------------------------------
7.3 MONGODB / NOSQL
----------------------------------------------------------------------
The guide includes MongoDB integration through spring-boot-starter-data-mongodb.

A MongoDB document can be represented with @Document:

@Document
public class Product {
    @Id
    private String id;
    private String name;
}

A repository can extend MongoRepository:

public interface ProductRepository extends MongoRepository<Product, String> {
    List<Product> findByName(String name);
}

The conceptual difference from JPA is that MongoDB is document-oriented rather than relational. The repository abstraction still provides a familiar application-level pattern.

----------------------------------------------------------------------
7.4 TRANSACTIONS WITH @Transactional
----------------------------------------------------------------------
A transaction groups related database operations so that they behave as one logical unit.

Example:

@Transactional
public void registerUser(User user) {
    userRepository.save(user);
    // additional database operations
}

The key idea is atomicity: if a sequence of related operations cannot be completed successfully, the transaction can be rolled back according to the transaction configuration and failure conditions.

The guide also mentions:

@Transactional(readOnly = true)

for read-focused operations.

Interview example:
Imagine transferring money:
1. Deduct from account A.
2. Add to account B.

If step 1 succeeds and step 2 fails, the system must avoid leaving the database in an inconsistent state. Transaction boundaries help solve this kind of problem.

8. DATABASE CONFIGURATION
==============================================================================

----------------------------------------------------------------------
8.1 H2 IN-MEMORY DATABASE
----------------------------------------------------------------------
H2 is an in-memory relational database used in the guide for development and testing. With an in-memory URL, the database exists in memory and is lost when the application stops.

Example configuration:

spring.datasource.url=jdbc:h2:mem:testdb
spring.datasource.driver-class-name=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=
spring.h2.console.enabled=true

The guide also shows the H2 console URL:

http://localhost:8080/h2-console

H2 is useful when you want a lightweight database without maintaining a separate database server during local development or tests.

----------------------------------------------------------------------
8.2 MYSQL / POSTGRESQL
----------------------------------------------------------------------
The guide provides examples for MySQL and PostgreSQL datasource configuration.

MySQL:

spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=your_password
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true

PostgreSQL:

spring.datasource.url=jdbc:postgresql://localhost:5432/mydb
spring.datasource.username=postgres
spring.datasource.password=your_password

The application needs the appropriate JDBC driver dependency. Spring Boot uses the datasource properties to create the database connection infrastructure.

----------------------------------------------------------------------
8.3 CONNECTION POOLING WITH HIKARICP
----------------------------------------------------------------------
Opening a new database connection for every request is expensive. A connection pool keeps a collection of reusable database connections.

The guide identifies HikariCP as the default connection pool and shows settings such as:

spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=5
spring.datasource.hikari.idle-timeout=30000

Mental model:

Without pooling:
request -> open connection -> query -> close connection

With pooling:
request -> borrow connection -> query -> return connection to pool

Pooling improves efficiency because established connections can be reused.

----------------------------------------------------------------------
8.4 schema.sql AND data.sql
----------------------------------------------------------------------
The guide describes placing SQL initialization scripts in src/main/resources/.

schema.sql -> creates database objects such as tables.
data.sql -> inserts initial data.

Example:

CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100)
);

Then:

INSERT INTO users (name) VALUES ('John Doe'), ('Alice');

This approach is especially useful for predictable development/test initialization.

==============================================================================
9. VALIDATION
==============================================================================

----------------------------------------------------------------------
9.1 BEAN VALIDATION
----------------------------------------------------------------------
Validation prevents invalid input from entering application logic.

The guide lists annotations such as:
@NotNull -> value cannot be null
@NotBlank -> string cannot be null/empty/blank
@Email -> value should satisfy email-format validation
@Size(min, max) -> length or collection-size constraint
@Min / @Max -> numeric limits

Example:

public class User {
    @NotBlank
    private String name;

    @Email
    private String email;

    @Min(18)
    private int age;
}

The main idea is declarative validation: the rules are written next to the fields instead of being repeated manually throughout controllers.

----------------------------------------------------------------------
9.2 @Valid AND @Validated
----------------------------------------------------------------------
@Valid is commonly used on controller parameters to trigger validation.

@PostMapping
public ResponseEntity<String> addUser(
        @Valid @RequestBody User user) {
    return ResponseEntity.ok("User is valid");
}

If the input violates the constraints, validation fails before the normal method logic completes.

@Validated is useful at the class level for method validation and for validation groups.

Example:

@Validated
@Service
public class PaymentService {
    public void process(@Min(100) int amount) {
        // process payment
    }
}

Interview distinction:
@Valid -> triggers standard bean validation on an object or parameter.
@Validated -> Spring-specific variant that also supports validation groups and method-level validation scenarios.

----------------------------------------------------------------------
9.3 CUSTOM VALIDATORS
----------------------------------------------------------------------
Built-in annotations cannot express every business rule. For custom rules, define a custom constraint annotation and a ConstraintValidator implementation.

Example annotation:

@Constraint(validatedBy = UsernameValidator.class)
@Target({FIELD})
@Retention(RUNTIME)
public @interface ValidUsername {
    String message() default "Invalid username";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

Validator:

public class UsernameValidator
        implements ConstraintValidator<ValidUsername, String> {

    @Override
    public boolean isValid(
            String value,
            ConstraintValidatorContext context) {
        return value != null
            && value.matches("^[a-zA-Z0-9_]{5,20}$");
    }
}

Then:

@ValidUsername
private String username;

The pattern is:
Define rule -> implement validator -> attach annotation -> validation runs automatically.

10. SECURITY
==============================================================================

----------------------------------------------------------------------
10.1 SPRING SECURITY BASICS
----------------------------------------------------------------------
Spring Security provides authentication and authorization support for web applications, APIs, and microservices.

The guide shows that adding spring-boot-starter-security enables security infrastructure. It describes the default behavior as securing endpoints, providing a login mechanism, and generating a password that is logged at startup.

The key lesson is that security should be explicit and intentional. Do not assume an endpoint is safe merely because the controller works correctly.

----------------------------------------------------------------------
10.2 AUTHENTICATION VS AUTHORIZATION
----------------------------------------------------------------------
Authentication answers:
“Who are you?”

Authorization answers:
“What are you allowed to do?”

Example:
A user logs in with credentials. Authentication establishes the user's identity. After that, authorization rules determine whether the user can access /admin/**.

The guide shows rules such as:

.requestMatchers("/admin/**").hasRole("ADMIN")
.requestMatchers("/user/**").hasAnyRole("USER", "ADMIN")
.anyRequest().authenticated()

This creates a clear access policy.

----------------------------------------------------------------------
10.3 PASSWORD ENCODING
----------------------------------------------------------------------
Passwords should not be stored as plain text. The guide uses PasswordEncoder with BCrypt.

@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

String encoded = passwordEncoder.encode("mypassword");

The important distinction is between a raw password supplied by a user and the encoded representation stored by the application.

During login, the system should verify the supplied password against the stored encoded value rather than storing or comparing raw passwords directly.

----------------------------------------------------------------------
10.4 JWT TOKEN-BASED SECURITY
----------------------------------------------------------------------
JWT is presented in the guide as a common approach for stateless REST API security.

High-level flow:
1. Client sends credentials.
2. Server authenticates the user.
3. Server issues a JWT.
4. Client sends the token with later requests.
5. Server validates the token and establishes authentication.

Typical header:

Authorization: Bearer <token>

The guide illustrates a JWT filter extending OncePerRequestFilter and reading the Authorization header before continuing the filter chain.

The most important concept is that authentication state is carried in the token rather than requiring a traditional server-side session for every API request.

----------------------------------------------------------------------
10.5 ROLE-BASED ACCESS CONTROL
----------------------------------------------------------------------
Role-based access control restricts operations based on roles or authorities.

Example:

@GetMapping("/admin/dashboard")
@PreAuthorize("hasRole('ADMIN')")
public String adminDashboard() {
    return "Admin area";
}

Method-level security is enabled in the guide using @EnableMethodSecurity.

Think in layers:
Authentication -> identify the caller
Authorization -> check permissions
RBAC -> express permissions through roles such as USER or ADMIN

11. TESTING
==============================================================================

----------------------------------------------------------------------
11.1 UNIT TESTING WITH JUNIT
----------------------------------------------------------------------
A unit test focuses on a small piece of behavior, often one class or method, without loading the entire application.

Example:

class CalculatorService {
    int add(int a, int b) {
        return a + b;
    }
}

@Test
void testAdd() {
    CalculatorService calc = new CalculatorService();
    assertEquals(5, calc.add(2, 3));
}

The test is fast because it creates the object directly and does not require the Spring application context.

----------------------------------------------------------------------
11.2 MOCKING WITH MOCKITO
----------------------------------------------------------------------
Mockito allows a test to replace a real dependency with a controlled mock.

Suppose OrderService depends on PaymentService. A unit test for OrderService should not need a real payment system.

@Mock
PaymentService paymentService;

@InjectMocks
OrderService orderService;

when(paymentService.pay()).thenReturn(true);

assertTrue(orderService.placeOrder());

The mock lets the test control the dependency's behavior. This makes the test deterministic and focused on the class being tested.

----------------------------------------------------------------------
11.3 INTEGRATION TESTING
----------------------------------------------------------------------
Integration tests verify that multiple application components work together. The guide uses @SpringBootTest to load the application context.

Example:

@SpringBootTest
class UserServiceIntegrationTest {
    @Autowired UserService userService;

    @Test
    void testFindUser() {
        User user = userService.findById(1L);
        assertNotNull(user);
    }
}

The trade-off is that integration tests are usually slower than isolated unit tests because more infrastructure is involved.

----------------------------------------------------------------------
11.4 @WebMvcTest
----------------------------------------------------------------------
@WebMvcTest focuses on the web layer. It is useful when you want to test controller behavior without loading the complete application context.

Example:

@WebMvcTest(UserController.class)
class UserControllerTest {
    @Autowired
    MockMvc mockMvc;

    @Test
    void testGetUser() throws Exception {
        mockMvc.perform(get("/users/1"))
               .andExpect(status().isOk());
    }
}

The guide notes that service dependencies can be mocked for controller-focused tests.

Mental model:
@WebMvcTest -> controller/web behavior
@DataJpaTest -> repository/data behavior
@SpringBootTest -> broad application integration

----------------------------------------------------------------------
11.5 @DataJpaTest
----------------------------------------------------------------------
@DataJpaTest focuses on the JPA repository layer.

Example:

@DataJpaTest
class UserRepositoryTest {
    @Autowired
    UserRepository userRepository;

    @Test
    void testSaveUser() {
        User user = new User("John");
        User saved = userRepository.save(user);
        assertNotNull(saved.getId());
    }
}

The guide notes the use of an H2 in-memory database and transaction rollback after tests. This makes repository tests isolated and repeatable.

12.1 SLF4J AND LOGBACK
----------------------------------------------------------------------
SLF4J is a logging facade. It provides a common logging API while allowing the underlying logging implementation to vary. The guide identifies Logback as the default implementation in Spring Boot.

14. ERROR HANDLING
==============================================================================

----------------------------------------------------------------------
14.1 DEFAULT ERROR HANDLING
----------------------------------------------------------------------
Spring Boot provides default error handling. For REST-style requests, an error response can contain fields such as timestamp, status, error, and path. Traditional web applications can show a default error page.

Example shape:

{
  "timestamp": "...",
  "status": 404,
  "error": "Not Found",
  "path": "/api/users/100"
}

The purpose of the default mechanism is to provide a consistent fallback when an exception or error is not handled by application-specific logic.

----------------------------------------------------------------------
14.2 CUSTOM ERROR PAGES
----------------------------------------------------------------------
For browser-oriented applications, the guide describes custom HTML error pages under error-specific resource paths such as:

/resources/public/error/404.html
/resources/public/error/500.html

This allows the application to provide a user-friendly page instead of a generic error page.

----------------------------------------------------------------------
14.3 GLOBAL EXCEPTION HANDLING
----------------------------------------------------------------------
@ControllerAdvice and @ExceptionHandler can centralize error handling across controllers.

Example:

@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<String> handleNotFound(
            ResourceNotFoundException ex) {
        return new ResponseEntity<>(
            "Resource not found: " + ex.getMessage(),
            HttpStatus.NOT_FOUND);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<String> handleGeneral(Exception ex) {
        return new ResponseEntity<>(
            "Internal error",
            HttpStatus.INTERNAL_SERVER_ERROR);
    }
}

Best-practice concepts from the guide:
- Use appropriate HTTP status codes.
- Log useful exception information.
- Do not expose sensitive stack traces to clients.
- Keep error responses consistent.
- Customize error attributes when necessary.

16. CACHING
==============================================================================

----------------------------------------------------------------------
16.1 @Cacheable AND @CacheEvict
----------------------------------------------------------------------
Caching stores frequently used results so the application does not need to perform the expensive operation repeatedly.

Enable caching:

@EnableCaching

Cache a method:

@Cacheable("products")
public Product getProductById(Long id) {
    return productRepository.findById(id).orElse(null);
}

First request for an id:
method executes -> database lookup -> result stored in cache

Later request for the same key:
cache lookup -> cached result returned

@CacheEvict removes cached data when the underlying data changes.

@CacheEvict(value = "products", key = "#id")
public void deleteProduct(Long id) {
    productRepository.deleteById(id);
}

Important concept: a cache improves read performance only when its data remains sufficiently fresh for the application's requirements.

----------------------------------------------------------------------
16.2 CACHE PROVIDERS
----------------------------------------------------------------------
The guide mentions:

Ehcache -> Java/in-memory caching
Caffeine -> fast Java-based caching
Redis -> external/distributed cache

Caffeine example:

spring.cache.type=caffeine
spring.cache.caffeine.spec=maximumSize=1000,expireAfterAccess=5m

Redis example:

spring.cache.type=redis
spring.redis.host=localhost
spring.redis.port=6379

A local in-memory cache is simple and fast, but each application instance has its own cache. A distributed cache such as Redis can be shared by multiple instances.

Interview question:
Why use Redis instead of only an in-memory cache in a multi-instance system?
Because a shared external cache can provide common cached state across application instances.

17. SCHEDULING AND ASYNCHRONOUS EXECUTION
==============================================================================

----------------------------------------------------------------------
17.1 @SCHEDULED
----------------------------------------------------------------------
@Scheduled runs methods periodically or according to a schedule.

Enable scheduling:

@EnableScheduling

Fixed rate:

@Scheduled(fixedRate = 5000)
public void reportStatus() {
    // every 5 seconds according to the scheduling rule
}

Fixed delay:
The next execution is scheduled after the previous execution completes and the configured delay passes.

Cron:

@Scheduled(cron = "0 0 9 * * ?")
public void dailyTask() {
    // daily task
}

Common use cases include cleanup jobs, periodic synchronization, report generation, and scheduled health/maintenance work.

----------------------------------------------------------------------
17.2 @ASYNC
----------------------------------------------------------------------
@Async allows a method to execute asynchronously using a separate thread managed by Spring's async infrastructure.

Enable it:

@EnableAsync

Use it:

@Async
public void sendEmail(String to) {
    // time-consuming work
}

A controller can call the method and return a response without waiting for the entire background operation to finish.

Important rule highlighted in the guide: async methods must be called through another Spring-managed bean rather than through a direct self-invocation in the same class, because the proxy-based interception mechanism is involved.

Use asynchronous execution carefully. Background work introduces concurrency, thread-pool considerations, error-handling concerns, and ordering questions.

18. MESSAGING

----------------------------------------------------------------------
18.1 RABBITMQ
----------------------------------------------------------------------
RabbitMQ is presented as a message broker using AMQP for asynchronous message delivery.

Producer example:

rabbitTemplate.convertAndSend("myQueue", message);

Consumer example:

@RabbitListener(queues = "myQueue")
public void receive(String message) {
    System.out.println("Received: " + message);
}

Conceptually:
Producer -> Broker/Queue -> Consumer

The producer does not need to perform the consumer's work immediately. This helps decouple components and supports asynchronous processing.

----------------------------------------------------------------------
18.2 APACHE KAFKA
----------------------------------------------------------------------
Kafka is presented as a distributed event-streaming platform suitable for high-throughput and fault-tolerant messaging.

Producer:

kafkaTemplate.send("myTopic", message);

Consumer:

@KafkaListener(topics = "myTopic", groupId = "my-group")
public void listen(String message) {
    // process event
}

A useful conceptual difference from a traditional queue mindset is that Kafka is commonly organized around topics and consumer groups, with events retained according to broker configuration and consumption tracked through offsets.

----------------------------------------------------------------------
18.3 JMS
----------------------------------------------------------------------
JMS is a Java messaging API. The guide uses an Artemis starter and JmsTemplate/JmsListener examples.

Producer:

jmsTemplate.convertAndSend("queue.sample", msg);

Consumer:

@JmsListener(destination = "queue.sample")
public void receive(String msg) {
    // process message
}

The common pattern remains the same:
application -> messaging infrastructure -> another consumer.

19. FILE UPLOAD AND DOWNLOAD
==============================================================================

----------------------------------------------------------------------
19.1 MULTIPART FILE UPLOAD
----------------------------------------------------------------------
Spring Boot can receive uploaded files through MultipartFile.

Example endpoint shape:

@PostMapping("/upload")
public ResponseEntity<String> handleFileUpload(
        @RequestParam("file") MultipartFile file) throws IOException {

    String uploadDir = "uploads/";
    Path path = Paths.get(uploadDir + file.getOriginalFilename());
    Files.createDirectories(path.getParent());
    Files.write(path, file.getBytes());

    return ResponseEntity.ok("File uploaded successfully");
}

The client sends multipart/form-data. Postman can test this by choosing form-data and adding a field named file.

The important pieces are:
MultipartFile -> receives the uploaded content
Path/Files -> stores the file
ResponseEntity -> communicates success/failure

----------------------------------------------------------------------
19.2 DOWNLOAD AND SECURITY
----------------------------------------------------------------------
A download endpoint can return a Resource and set Content-Disposition so the browser treats the response as a downloadable file.

Conceptual flow:
1. Receive filename.
2. Resolve storage path.
3. Check whether the file exists.
4. Create a Resource.
5. Set content type and download headers.
6. Return the resource.

The guide specifically highlights security checks:
- Validate file type.
- Enforce file size limits.
- Sanitize filenames and paths.
- Prevent directory traversal.

Example size settings:

spring.servlet.multipart.max-file-size=5MB
spring.servlet.multipart.max-request-size=10MB

Do not trust the original filename from a client as a safe filesystem path.

22.1 MICROSERVICES WITH SPRING BOOT
----------------------------------------------------------------------
Spring Boot combined with Spring Cloud can support distributed systems and common microservice patterns.

The guide introduces:

- Eureka service discovery

  |
  v

  |
  +------> Product Service

----------------------------------------------------------------------
22.1.1 SPRING CLOUD
----------------------------------------------------------------------
Spring Cloud is presented as a collection of tools for distributed-system patterns such as configuration, discovery, routing, load balancing, and resilience.

The important learning point is that microservices create problems that a single application does not have: locating services, handling network failures, managing configuration across many services, and routing requests.

----------------------------------------------------------------------
22.1.2 EUREKA SERVICE DISCOVERY
----------------------------------------------------------------------
Service discovery allows services to find each other without hard-coding every service address.

Conceptually:

Product Service -> registers with Eureka
Order Service   -> registers with Eureka
Client/Gateway  -> asks Eureka where Product Service is

The guide shows Eureka Server and Eureka Client examples.

The benefit is that service instances can be discovered dynamically rather than relying only on fixed hostnames and ports.

----------------------------------------------------------------------
22.1.3 SPRING CLOUD GATEWAY / ZUUL
----------------------------------------------------------------------
A gateway provides a single entry point for external clients and can route requests to internal services.

Example route concept:

Path=/products/**
    -> http://localhost:8081

The guide describes Spring Cloud Gateway as the modern replacement for Zuul in its discussion.

Gateway responsibilities can include routing and, depending on configuration, cross-cutting concerns such as authentication, rate limiting, or request transformation.

----------------------------------------------------------------------
22.1.4 CIRCUIT BREAKER AND RESILIENCE4J
----------------------------------------------------------------------
Distributed calls can fail because another service is unavailable, slow, or overloaded. A circuit breaker prevents repeated failing calls from causing a wider cascade of failures.

The guide shows Resilience4j and a fallback method:

@CircuitBreaker(name = "productService", fallbackMethod = "fallback")
public String getProduct() {
    return restTemplate.getForObject(
        "http://product-service/api", String.class);
}

public String fallback(Throwable t) {
    return "Fallback response";
}

Mental model:
Normal -> repeated failures -> circuit opens -> calls fail fast/fallback -> after recovery conditions, calls can resume.

The purpose is resilience, not hiding every failure. The fallback should represent a meaningful degraded behavior.

----------------------------------------------------------------------
22.1.5 CONFIG SERVER
----------------------------------------------------------------------
A centralized configuration server can provide configuration to multiple services.

Conceptual architecture:

Git/config repository
        |
        v
   Config Server
     /           v         v
Service A   Service B

The guide shows a Config Server backed by a Git repository and client-side import configuration.

Benefits include centralized configuration management and reduced duplication across services. Secrets still require careful handling and should not simply be committed to an ordinary source repository.

----------------------------------------------------------------------
22.2 APPLICATION EVENTS
----------------------------------------------------------------------
ApplicationEventPublisher and event listeners support event-driven communication inside the application.

Define an event:

public class UserCreatedEvent extends ApplicationEvent {
    private String email;

    public UserCreatedEvent(Object source, String email) {
        super(source);
        this.email = email;
    }
}

Publish:

publisher.publishEvent(new UserCreatedEvent(this, email));

Listen:

@EventListener
public void handleUserCreated(UserCreatedEvent event) {
    System.out.println("User created: " + event.getEmail());
}

The advantage is loose coupling. The code that creates the user does not need to directly call every secondary action that should happen after user creation.

----------------------------------------------------------------------
22.3 CREATING CUSTOM STARTERS
----------------------------------------------------------------------
A custom starter packages reusable application infrastructure so that another project can add one dependency and receive the associated auto-configuration.

The guide outlines these steps:
1. Create a separate starter module.
2. Include spring-boot-autoconfigure.
3. Register auto-configuration using the mechanism appropriate to the Spring Boot generation described by the project.
4. Provide an auto-configuration class.
5. Publish/use the starter as a dependency.

Example idea:

@Configuration
public class MyAutoConfiguration {
    @Bean
    public MyService myService() {
        return new MyService();
    }
}

The real value is packaging reusable configuration rather than forcing every application to repeat the same setup.

1. What is Spring Boot?
Answer: A Java framework built on Spring that simplifies application development through auto-configuration, starters, embedded servers, and production-oriented features.

2. What is @SpringBootApplication?
Answer: A convenience annotation combining @Configuration, @EnableAutoConfiguration, and @ComponentScan.

3. What is dependency injection?
Answer: Supplying an object's dependencies from outside instead of having the object create them itself.

4. What is IoC?
Answer: A principle where control of object creation and dependency management is transferred to a container/framework.

5. @Component vs @Service vs @Repository?
Answer: All are component stereotypes, but they communicate different responsibilities: generic component, business/service layer, and data-access layer.

6. @Controller vs @RestController?
Answer: @Controller commonly works with MVC views; @RestController is intended for REST responses and effectively includes response-body behavior.

7. @Autowired vs @Qualifier?
Answer: @Autowired performs dependency injection; @Qualifier selects a particular bean when multiple candidates exist.

8. @Bean vs @Component?
Answer: @Component is placed on a class for component scanning; @Bean is placed on a configuration method to explicitly register the returned object as a bean.

9. What is a Spring Boot starter?
Answer: A convenient dependency bundle for a common capability such as web, JPA, security, or testing.

10. What is auto-configuration?
Answer: Spring Boot automatically configures common infrastructure based on the application's dependencies and configuration.

11. @Value vs @ConfigurationProperties?
Answer: @Value is convenient for individual values; @ConfigurationProperties is designed for structured groups of related settings.

12. What are Spring Profiles?
Answer: A way to activate environment-specific configuration and beans, such as dev, test, and prod.

13. @PathVariable vs @RequestParam?
Answer: @PathVariable reads a value embedded in the URL path; @RequestParam reads a query parameter.

14. Why use ResponseEntity?
Answer: To explicitly control HTTP response status, headers, and body.

15. What is @ControllerAdvice?
Answer: A centralized mechanism for controller-related cross-cutting concerns, commonly global exception handling.

16. What is Spring Data JPA?
Answer: An abstraction that simplifies JPA-based persistence through repositories and query support.

17. JpaRepository vs JdbcTemplate?
Answer: JpaRepository provides an object/entity-oriented repository abstraction; JdbcTemplate gives more direct SQL control.

18. Why use @Transactional?
Answer: To define a transactional boundary around related operations so they can be treated as one logical database unit.

19. What is connection pooling?
Answer: Reusing database connections instead of opening a new connection for every operation.

20. What is the difference between authentication and authorization?
Answer: Authentication identifies the user; authorization determines what the user can access.

21. What is JWT?
Answer: A token format commonly used to carry authentication-related claims between a client and server in stateless API designs.

22. Why use BCrypt?
Answer: To store passwords in an encoded/hashed form rather than plain text.

23. @SpringBootTest vs @WebMvcTest?
Answer: @SpringBootTest loads a broad application context for integration-style testing; @WebMvcTest focuses on the web layer.

24. What is Mockito used for?
Answer: Creating controlled mock dependencies so a unit test can isolate the class under test.

25. What is Actuator?
Answer: Spring Boot's operational/monitoring feature set, including endpoints for health and metrics.

26. What is caching?
Answer: Reusing previously computed/fetched results to reduce expensive repeated work.

27. @Cacheable vs @CacheEvict?
Answer: @Cacheable stores/reuses method results; @CacheEvict removes cache entries.

28. @Scheduled vs @Async?
Answer: @Scheduled controls when a method runs; @Async changes execution so work can run asynchronously.

29. Why use messaging?
Answer: To decouple producers and consumers and support asynchronous/event-driven processing.

30. Why use a gateway in microservices?
Answer: To provide a controlled entry point for routing requests to internal services and handling cross-cutting concerns.

31. What problem does service discovery solve?
Answer: It allows services to locate available service instances without hard-coding every address.

32. What is a circuit breaker?
Answer: A resilience pattern that prevents repeated failing calls from continuously consuming resources and allows fallback/degraded behavior.

==============================================================================
PRACTICAL PROJECT FLOW
==============================================================================
A typical Spring Boot backend can be understood as a chain of responsibilities:

1. Client sends HTTP request.
2. Controller receives and validates the request.
3. Controller calls the service.
4. Service applies business rules.
5. Service calls repository/data-access code.
6. Repository communicates with the database.
7. Service returns the result.
8. Controller builds the HTTP response.
9. Exception handling converts failures into consistent error responses.
10. Logging records important events.
11. Actuator/metrics provide operational visibility.
12. Security controls who can access each endpoint.
13. Caching can reduce repeated expensive reads.
14. Messaging can move long-running or event-driven work out of the request path.

A clean architecture therefore keeps each layer focused instead of allowing controllers to contain database queries, business rules, validation, security decisions, and infrastructure code all at once.

INTERVIEW ANSWER PATTERN
------------------------
When asked about a Spring Boot feature, answer in this order:

1. Definition in one sentence.
2. Why it exists.
3. How it works at a high level.
4. Small code example.
5. Real-world use case.
6. Important trade-off or common mistake.
7. Related interview comparison.

Example:

“What is @Transactional?”

One sentence:
It defines a transaction boundary around a method or operation.

Why:
To keep related database operations consistent.

How:
Spring manages the transaction around the method invocation.

Example:
A transfer updates two accounts inside one transaction.

Use case:
Financial transfer, order creation, inventory updates.

Trade-off:
Long-running transactions can hold database resources for too long.

Comparison:
@Transactional vs manually controlling transaction boundaries.

This answer structure demonstrates understanding instead of memorization.

IMPORTANT SOURCE-BASED NOTES

These notes preserve the topic coverage and examples represented in the this guide while rewriting the explanations into a more continuous, study-oriented form.

Some examples in the guide are intentionally simple demonstrations rather than complete production applications. For example, a file upload example writes directly to a local uploads directory, and a security example uses in-memory users to demonstrate authorization. Treat these as learning examples and focus on the underlying concept.

The guide also contains examples from different Spring Boot/API styles. When studying, concentrate first on the concept being demonstrated—dependency injection, request mapping, security rules, repository abstraction, transaction boundaries, testing scope, and so on—then learn the exact API syntax used by the Spring Boot version used in your project.
