Purpose

This document expands the supplied 120-question QA/software-testing

1.  [REPORTED] What is the difference between QA and QC? Level: Fresher
    / Entry-Level

Answer: Quality Assurance (QA) is the broader, process-oriented activity
focused on preventing defects by improving how software is developed and
tested. Quality Control (QC) is more product-oriented and focuses on
identifying defects in the delivered product through activities such as
testing and inspection. Testing is therefore an important QC activity,
while QA also includes process improvement.

Example: Example: Create a representative positive case, a negative
case, a boundary case, and a failure/recovery case, then verify both the
observable result and relevant side effects.

Interview Tip: Answer in a structured way: clarify the requirement,
identify risk, explain the test approach, describe evidence, and state
how you would communicate the result. For scenario questions, prioritize
rather than claiming that everything can be tested equally.

What Interviewer Is Testing: Testing fundamentals, analytical thinking,
risk assessment, defect investigation, communication, technical
judgment, automation awareness, and the ability to make practical
quality decisions.

Key Points to Remember: • Understand requirements and business risk
before writing tests. • Cover positive, negative, boundary, integration,
and failure scenarios as relevant. • Use evidence: logs, traces,
screenshots, test data, environment details, and reproducible steps. •
Do not hide uncertainty; document assumptions and investigate unknowns.
• Automate where repetition and stability justify the maintenance cost.
• For release decisions, communicate residual risk instead of giving
unsupported guarantees.

Common Follow-up Questions: • What edge cases would you test? • How
would you prioritize these tests? • How would you automate this
scenario? • What evidence would you collect if the issue is
intermittent? • How would you decide whether the risk is acceptable for
release?

Common Mistakes: • Listing hundreds of test cases without
prioritization. • Confusing severity with priority or retesting with
regression. • Treating automation as a replacement for all manual
testing. • Adding retries to hide flaky tests instead of investigating
them. • Making release decisions without considering business impact and
residual risk.

2.  [REPORTED] What is the difference between verification and
    validation? Level: Fresher / Entry-Level

Answer: Verification asks whether we are building the product correctly:
reviews, inspections, static analysis, and checking work products
against specifications. Validation asks whether we built the right
product: executing the software and checking that it satisfies user and
business needs. A useful interview summary is ‘verification is about
conformance; validation is about fitness for use.’

3.  [REPORTED] What is the difference between severity and priority?
    Give an example of a high-severity, low-priority defect and a
    low-severity, high-priority defect. Level: Fresher / Entry-Level

Answer: Severity describes the technical or business impact of a defect;
priority describes how urgently the defect should be addressed. A
high-severity, low-priority example could be a crash in a rarely used
internal report. A low-severity, high-priority example could be a
spelling error in a public legal/compliance notice. The exact
classification depends on product context.

Example: Example: A checkout crash affecting every customer is high
severity and high priority. A broken image on an internal admin page may
be lower severity and priority; the exact classification depends on
business impact.

4.  [COMMON] What is the difference between SDLC and STLC? Level:
    Fresher / Entry-Level

Answer: SDLC describes the broader software development life cycle:
requirements, design, development, testing, deployment, and maintenance.
STLC focuses specifically on testing activities such as requirement
analysis, test planning, test design, environment/data preparation,
execution, defect reporting, and closure. STLC operates within the
overall SDLC.

5.  [COMMON] What are the different levels of software testing? Level:
    Fresher / Entry-Level

Answer: Common levels are unit testing, integration testing, system
testing, and acceptance testing. Unit testing validates small
components; integration testing checks interactions between components;
system testing validates the complete application; acceptance testing
checks whether the product meets business/user acceptance criteria. The
exact terminology can vary by organization.

6.  [COMMON] What is the difference between functional and
    non-functional testing? Level: Fresher / Entry-Level

Answer: Functional testing checks what the system does against expected
behavior. Non-functional testing checks qualities such as performance,
security, usability, reliability, accessibility, and scalability. For
example, verifying that checkout calculates tax correctly is functional;
verifying that checkout responds within an agreed latency target under
load is non-functional.

9.  [COMMON] What is a defect or bug? What information should a good bug
    report contain? Level: Fresher / Entry-Level

Answer: A good defect report should contain a concise title,
environment/build, preconditions, exact reproduction steps, test data,
expected result, actual result, severity/priority, reproducibility,
evidence such as screenshots/logs/video, and relevant IDs. The report
should make the defect reproducible without requiring the developer to
guess the missing context.

10. [COMMON] Explain the defect life cycle. Level: Fresher / Entry-Level

Answer: A typical lifecycle is New/Open → Assigned → In Progress →
Fixed/Resolved → Retest → Closed. If the problem remains, it can be
Reopened; other outcomes may include Duplicate, Rejected/Not a Bug,
Cannot Reproduce, Deferred, or Won’t Fix. Exact states differ by
organization.

11. [COMMON] What is regression testing? Level: Fresher / Entry-Level

Answer: Regression testing checks that existing behavior has not been
unintentionally broken by a change. It is broader than simply retesting
the changed defect. Regression scope should be driven by the changed
code, dependencies, risk, and affected user journeys.

13. [REPORTED] What is the difference between smoke testing and sanity
    testing? Level: Fresher / Entry-Level

enough for deeper testing. Sanity testing is a focused check of a
particular area after a change or fix. Organizations use the terms
somewhat differently, so state the convention being used.

logic. It complements, rather than replaces, black-box testing.

16. [COMMON] What is exploratory testing? Level: Fresher / Entry-Level

Answer: Exploratory testing combines learning, test design, and
execution instead of following only prewritten cases. The tester
investigates risks, unusual workflows, and unexpected behavior while
continuously adapting based on findings. Good exploratory testing is
still structured through a charter, notes, evidence, and time-box.

Example: Example: Create a representative positive case, a negative
case, a boundary case, and a failure/recovery case, then verify both the

29. [COMMON] What is the difference between a defect, error, failure and
    mistake? Level: Fresher / Entry-Level

Answer: A mistake is a human action that introduces an incorrect result.
An error is the incorrect state or reasoning introduced by that mistake.
A defect is a flaw in a work product such as code or requirements. A
failure is observable incorrect behavior when the software executes.
Terminology varies across testing standards, so explain the relationship
rather than treating the words as universal synonyms.

     SDET / QA Lead

Answer: Make the disagreement evidence-based: expected behavior, actual
evidence, customer impact, severity, probability, workaround, and test
confidence. Present options and residual risks to the release
decision-maker. QA owns quality evidence and risk communication, not
unilateral business authority.

Example: Example: Create a representative positive case, a negative
case, a boundary case, and a failure/recovery case, then verify both the
observable result and relevant side effects.

Interview Tip: Answer in a structured way: clarify the requirement,
identify risk, explain the test approach, describe evidence, and state
how you would communicate the result. For scenario questions, prioritize
rather than claiming that everything can be tested equally.

What Interviewer Is Testing: Testing fundamentals, analytical thinking,
risk assessment, defect investigation, communication, technical
judgment, automation awareness, and the ability to make practical
quality decisions.

Key Points to Remember: • Understand requirements and business risk
before writing tests. • Cover positive, negative, boundary, integration,
and failure scenarios as relevant. • Use evidence: logs, traces,
screenshots, test data, environment details, and reproducible steps. •
Do not hide uncertainty; document assumptions and investigate unknowns.
• Automate where repetition and stability justify the maintenance cost.
• For release decisions, communicate residual risk instead of giving
unsupported guarantees.

Common Follow-up Questions: • What edge cases would you test? • How
would you prioritize these tests? • How would you automate this
scenario? • What evidence would you collect if the issue is
intermittent? • How would you decide whether the risk is acceptable for
release?

Common Mistakes: • Listing hundreds of test cases without
prioritization. • Confusing severity with priority or retesting with
regression. • Treating automation as a replacement for all manual
testing. • Adding retries to hide flaky tests instead of investigating
them. • Making release decisions without considering business impact and
residual risk.

data/environments, parallelize safe automation, reduce redundant gates,

116. [COMMON] How would you decide what should be covered by contract
     tests, integration tests and end-to-end tests? Level: Advanced /
     Senior QA / SDET / QA Lead

without requiring the entire system. Integration tests verify real
component interactions; end-to-end tests validate critical business
journeys across the stack. Put checks at the lowest layer that gives
sufficient confidence and keep expensive E2E coverage focused.

prevention, queue behavior, and restoration of normal traffic. Test both
immediate failure and recovery because many bugs appear only during
transition back to healthy state.

119. [COMMON] How would you test a rollback after a failed production
     deployment? Level: Advanced / Senior QA / SDET / QA Lead

Answer: Validate that the previous application version can run with the
current data/schema, that traffic can be switched back safely, and that
partial writes/events do not create inconsistent state. Database
migrations often require backward-compatible expand-and-contract
techniques because code rollback alone may not be sufficient.
