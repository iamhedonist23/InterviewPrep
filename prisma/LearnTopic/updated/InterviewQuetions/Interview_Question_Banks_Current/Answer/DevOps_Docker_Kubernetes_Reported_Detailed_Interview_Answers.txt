1.  [REPORTED] Question / Topic: “What do you mean by CI - CD, why is
    that required?” Company: Fortinet Role: SDE 1/2 - DevOps Source:
    Candidate interview report on LeetCode. Evidence: turn0search18

Answer: CI (Continuous Integration) is the practice of frequently
integrating code changes into a shared repository with automated build
and test validation. CD can mean Continuous Delivery, where validated
changes are kept ready for release, or Continuous Deployment, where
qualifying changes are automatically deployed to production. CI/CD
reduces integration risk, shortens feedback cycles, and makes releases
repeatable. A strong DevOps answer should connect CI/CD to source
control, automated tests, artifact creation, security checks, deployment
environments, approvals, rollback, and observability.

Example: Developer pushes code → CI builds → automated tests/security
checks → image/artifact is published → CD deploys to staging →
validation/approval → production deployment → monitoring and rollback if
needed.

Interview Tip: Answer the exact reported question first. Then explain
the mechanism, production relevance, and one concrete example. For task
questions, describe the implementation steps, validation, failure cases,
and security/operational considerations.

tool names, can reason about production behavior, and can troubleshoot
or implement the solution when asked.

Key Points to Remember: Keep definitions precise; distinguish tools from
concepts; explain ownership, state, networking, security, reliability,
and automation where relevant; and never claim a command or architecture
is universal when it depends on the environment.

Common Follow-up Questions: How does it work internally? Why would you

2.  [REPORTED] Question / Topic: “How would you go about setting up a
    git repository? Where to place the gitignore files, readme file
    etc.” Company: Fortinet Role: SDE 1/2 - DevOps Source: Candidate
    interview report on LeetCode. Evidence: turn0search18

Answer: A Git repository stores a project’s version history, branches,
tags, and configuration. A clean repository normally contains source
code, a README explaining setup and usage, and a .gitignore that
excludes generated files, local configuration, secrets, IDE metadata,
and build artifacts. Sensitive values should never be committed; use
secret-management facilities instead. A typical setup is git init,
create README.md and .gitignore, git add, git commit, then add the
remote and push.

Example: my-app/ ├── src/ ├── tests/ ├── README.md ├── .gitignore └──
.github/workflows/ci.yml

10. [REPORTED] Question / Topic: “Are you using the Helm chart?”
    Company: HCL Technologies Role: Azure L3 Support DevOps Source:
    GeeksforGeeks candidate interview report. Evidence: turn0search15

Answer: A Helm chart is a package of Kubernetes manifests plus
templates, default values, metadata, and supporting files. Helm renders
templates using values and creates or updates a Kubernetes release.
Charts help package an application consistently across environments
while allowing configuration differences through values. The key
distinction is that Helm is a packaging/release-management tool;
Kubernetes itself remains responsible for running the resulting
resources.

Example: helm template myapp ./chart -f values-prod.yaml # renders
Kubernetes manifests from the chart and values

17. [REPORTED] Question / Topic: “What is Terraform State Management?”
    Company: Crest Data Systems Role: DevOps Source: GeeksforGeeks
    candidate interview report. Evidence: turn0search17

Answer: Terraform state maps the resources declared in configuration to
real infrastructure and records attributes Terraform needs to plan
changes. For teams, state should normally be stored in a secure remote
backend with appropriate access control and state locking where
supported. If state is lost, do not blindly recreate resources: first
preserve the configuration and infrastructure, recover state from
backend/versioned backups if available, or reconstruct state by
importing existing resources. Secrets can also appear in state, so state
requires security controls.

Example: terraform plan reads configuration + current state + provider
data; if the state file is lost, recover a backend backup or import
existing infrastructure instead of immediately recreating production
resources.

Interview Tip: Answer the exact reported question first. Then explain
the mechanism, production relevance, and one concrete example. For task
questions, describe the implementation steps, validation, failure cases,
and security/operational considerations.

tool names, can reason about production behavior, and can troubleshoot
or implement the solution when asked.

71. [REPEATED] Question / Topic: Prometheus / Grafana / monitoring.

Evidence: HashedIn by Deloitte, Target, CrickBuzz.

============================================================ H. SOURCE
VERIFICATION

Answer: Prometheus collects time-series metrics by scraping configured
endpoints or receiving metrics through supported mechanisms. Grafana
queries Prometheus and turns the resulting time series into dashboards
and alerts. A complete setup therefore needs a reachable metrics
endpoint, Prometheus scrape configuration, retention/storage
considerations, Grafana data-source configuration, and useful
dashboards. Monitoring is only valuable when metrics represent
meaningful service health and actionable signals.

Example: Prometheus scrapes /metrics from an application; Grafana uses
Prometheus as a data source to display request rate, error rate, and
latency.

Interview Tip: Answer the exact reported question first. Then explain
the mechanism, production relevance, and one concrete example. For task
questions, describe the implementation steps, validation, failure cases,
and security/operational considerations.

What Interviewer Is Testing: Whether you understand the concept beyond
tool names, can reason about production behavior, and can troubleshoot
or implement the solution when asked.

Key Points to Remember: Keep definitions precise; distinguish tools from
concepts; explain ownership, state, networking, security, reliability,
and automation where relevant; and never claim a command or architecture
is universal when it depends on the environment.

Common Follow-up Questions: How does it work internally? Why would you
choose it? What happens if it fails? How would you troubleshoot it? How
would you secure it? How would you make the setup production-ready?

Common Mistakes: Giving a memorized one-line definition, listing tools
without explaining usage, ignoring failure recovery, exposing secrets,
or confusing Docker/containerization, Kubernetes/orchestration, CI/CD,
and IaC.
