1.  [REPORTED] Question : How do you retain the selected state when an
    Activity is recreated after a configuration change? Level : Junior /
    Entry-Level

Answer : When an Activity is recreated after a configuration change such
as rotation, the Activity instance is destroyed and a new instance is
created. UI state that exists only in views or Activity fields can
therefore be lost. The usual Android approach is to separate durable UI
state from the Activity instance and restore it through the appropriate
state mechanism.

For small transient values, onSaveInstanceState() can save data in a
Bundle, which Android supplies to the recreated Activity. For screen
state that should survive configuration changes and is owned by the
UI/business layer, a ViewModel is normally preferred because the
ViewModel survives Activity recreation. For larger or
process-recreation-sensitive state, persistent storage such as
SavedStateHandle, Room, or DataStore may be appropriate depending on the
requirement.

The key is to distinguish configuration-change survival from
process-death survival. A ViewModel helps with configuration changes but
should not be treated as permanent persistence.

Example :

    class DetailsActivity : AppCompatActivity() {
        private lateinit var viewModel: DetailsViewModel

        override fun onCreate(savedInstanceState: Bundle?) {
            super.onCreate(savedInstanceState)
            viewModel = ViewModelProvider(this)[DetailsViewModel::class.java]

            savedInstanceState?.getString("selectedSector")?.let {
                viewModel.selectSector(it)
            }
        }

        override fun onSaveInstanceState(outState: Bundle) {
            outState.putString("selectedSector", viewModel.selectedSector.value)
            super.onSaveInstanceState(outState)
        }
    }

For production code, the exact state mechanism should match whether the
state must survive configuration change, process death, or app restart.

2.  [REPORTED] Question : How do Fragment lifecycle transitions work
    across different navigation scenarios? Level : Junior / Entry-Level

Answer : A Fragment has its own lifecycle that is coordinated with, but
distinct from, its host Activity. A typical Fragment moves through
states such as onAttach(), onCreate(), onCreateView(), onViewCreated(),
onStart(), and onResume(), and reverses through onPause(), onStop(),
onDestroyView(), and onDestroy() as appropriate.

Navigation matters because the Fragment’s view lifecycle can end while
the Fragment object itself remains in the FragmentManager back stack.
That is why view-related resources and view binding should normally be
released in onDestroyView() rather than onDestroy().

For nested fragments, back-stack operations, configuration changes, and
transitions, the exact callbacks depend on what is being added, removed,
hidden, shown, or replaced. A strong answer therefore explains the
lifecycle as a state transition rather than memorizing callback order.

Example :

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->
                    render(state)
                }
            }
        }
    }

6.  [REPORTED] Question : What does the suspend keyword/operator mean in
    Kotlin? Level : Mid-Level

Answer : A suspend function is a Kotlin function that may suspend
execution without blocking the underlying thread while waiting for a
result. It can be called from another suspend function or from a
coroutine.

Suspension is not the same as creating a background thread. A suspend
function can run on the current thread until it reaches a suspension
point, and its dispatcher determines where coroutine work executes. For
example, a network call implemented as a suspend function can suspend
while waiting for I/O and then resume later.

The suspend modifier therefore describes how a function participates in
Kotlin’s coroutine model; it does not by itself mean “run on a
background thread”.

Example :

    suspend fun loadProfile(): Profile {
        return api.getProfile()
    }

Calling loadProfile() suspends the calling coroutine while the
suspendable operation is in progress; it does not inherently create a
new thread.

7.  [REPORTED] Question : How would you solve a state-related bug in an
    Android application? Level : Mid-Level

Answer : First identify which state is wrong, who owns it, and whether
there are multiple competing sources of truth. In a Compose/MVVM
application, UI state should normally have a clear owner, often a
ViewModel, while Composables render that state and emit user events.

I would reproduce the issue, inspect state transitions, check whether
state is being overwritten by multiple collectors or asynchronous
operations, and verify lifecycle behavior. Then I would establish a
single source of truth, make state updates explicit, and add a
regression test.

For asynchronous state, I would also check cancellation, stale
responses, configuration changes, and whether a collector is observing
the correct lifecycle.

Example :

    data class UiState(
        val selectedId: String? = null,
        val loading: Boolean = false,
        val error: String? = null
    )

    class ScreenViewModel : ViewModel() {
        private val _state = MutableStateFlow(UiState())
        val state = _state.asStateFlow()

        fun select(id: String) {
            _state.update { it.copy(selectedId = id) }
        }
    }

The ViewModel owns the state, while the Composable renders it and sends
user actions back.

10. [REPORTED TOPIC] Question : What are log interceptors and how would
    you use them in an Android networking stack? Level : Mid-Level

Answer : A logging interceptor sits in the networking stack and observes
outgoing requests and incoming responses. With an HTTP client such as
OkHttp, an interceptor can record method, URL, timing, status code, and
selected headers for debugging.

Logging must be environment-aware. Development builds may use detailed
logs, while production should avoid sensitive data such as authorization
headers, tokens, passwords, and personal information. An interceptor can
also help measure request duration and diagnose failures without
changing application business logic.

Example :

    val client = OkHttpClient.Builder()
        .addInterceptor { chain ->
            val request = chain.request()
            val start = System.nanoTime()
            val response = chain.proceed(request)
            val elapsedMs = (System.nanoTime() - start) / 1_000_000
            logger.debug("${request.method} ${request.url} -> ${response.code} (${elapsedMs}ms)")
            response
        }
        .build()

Production logging should redact authorization headers, cookies, tokens,
and sensitive bodies.

11. [REPORTED] Question : Given coroutine code using launch, delay, and
    Thread.sleep, what output will it produce and in what order? Level :
    Mid-Level

Answer : The crucial distinction is that delay() is a coroutine
suspension point, whereas Thread.sleep() blocks the current thread.
launch starts a coroutine and returns a Job; the actual ordering depends
on the dispatcher, scheduling, and whether code is running sequentially
in the same coroutine or concurrently.

When answering an output question, do not assume that coroutine creation
automatically means parallel execution. Trace each coroutine, identify
its dispatcher/thread, mark suspension points, and account for blocking
calls. If multiple coroutines can race, state explicitly whether the
output is deterministic or scheduling-dependent.

Example :

    runBlocking {
        launch {
            delay(100)
            println("A")
        }
        launch {
            Thread.sleep(50)
            println("B")
        }
        println("C")
    }

The exact order must be reasoned from coroutine scheduling and blocking
behavior; Thread.sleep blocks its thread while delay suspends its
coroutine.

13. [REPORTED] Question : How do Kotlin Coroutines work, and how would
    you reason about structured concurrency? Level : Mid-Level

Answer : Kotlin structured concurrency means coroutines are organized in
a hierarchy of scopes so their lifetimes, cancellation, and failures are
predictable. A parent scope owns its child coroutines; when the parent
is cancelled, children are cancelled.

Android commonly uses viewModelScope and lifecycleScope so work is tied
to a lifecycle owner. Structured concurrency prevents orphaned
background work and makes cancellation easier to reason about.
coroutineScope propagates child failure, while supervisorScope isolates
sibling failures.

20. [REPORTED TOPIC] Question : How do you use StateFlow and SharedFlow,
    and why would you choose one over the other? Level : Mid-Level

Answer : StateFlow represents observable state and always has a current
value. New collectors receive the latest state immediately. It is
therefore well suited to persistent UI state such as loading, content,
or error state.

SharedFlow represents a hot stream of shared emissions and is useful
when consumers need events rather than a single current state—for
example, navigation commands or one-time UI notifications. The choice
should follow semantics: use StateFlow for state, and SharedFlow for
broadcast-style events where replay/buffering behavior is configured
deliberately.

Example :

    private val _uiState = MutableStateFlow(UiState.Loading)
    val uiState: StateFlow<UiState> = _uiState

    private val _events = MutableSharedFlow<UiEvent>()
    val events = _events.asSharedFlow()

uiState represents current screen state; events can represent transient
broadcasts such as navigation or a snackbar request.

21. [REPORTED] Question : What are the four Compose side-effect APIs?
    Level : Senior / Advanced

Answer : Compose side-effect APIs allow work that has effects outside
pure UI composition to be tied to the composition lifecycle. Four
commonly discussed APIs are LaunchedEffect, DisposableEffect,
SideEffect, and rememberCoroutineScope.

LaunchedEffect starts a coroutine when its keys enter composition and
cancels/restarts it when keys change. DisposableEffect is for
registering an effect that requires cleanup. SideEffect publishes
Compose state to non-Compose code after successful recomposition.
rememberCoroutineScope provides a composition-aware scope for launching
work from event handlers.

The correct API depends on ownership and cleanup requirements; side
effects should not be performed arbitrarily inside the Composable body.

Example :

    LaunchedEffect(userId) {
        viewModel.load(userId)
    }

    DisposableEffect(observer) {
        observer.start()
        onDispose { observer.stop() }
    }

    SideEffect {
        analytics.setScreen("Details")
    }

    val scope = rememberCoroutineScope()
    Button(onClick = { scope.launch { save() } }) { Text("Save") }

22. [REPORTED] Question : If a ViewModel uses SupervisorJob, how do
    failures propagate? Level : Senior / Advanced

Answer : A SupervisorJob changes sibling failure behavior. With a normal
parent Job, an uncaught child failure can cancel the parent and its
other children. With a SupervisorJob, failure of one child does not
automatically cancel its sibling children.

This is useful when independent operations should continue even if one
fails. However, supervisor semantics do not mean errors disappear: an
uncaught exception still needs appropriate handling, and the supervisor
itself can still be cancelled by its parent.

Example :

    val scope = CoroutineScope(SupervisorJob() + Dispatchers.IO)

    scope.launch {
        throw RuntimeException("first task failed")
    }

    scope.launch {
        // This sibling can continue because the parent is supervised.
    }

23. [REPORTED] Question : How would you create your own CoroutineScope
    inside an Android Service? Level : Senior / Advanced

lifetime matches the Service and cancel that scope when the Service is

    class SyncService : Service() {

        override fun onDestroy() {
            serviceScope.cancel()
            super.onDestroy()
