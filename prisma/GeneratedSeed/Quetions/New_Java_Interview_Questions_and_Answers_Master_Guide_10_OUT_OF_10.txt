Question: Explain the difference between object-oriented and object-based programming.
Answer: Object-based programming uses objects to encapsulate state and behavior but is often used to describe languages or styles that do not provide the full set of class-based object-oriented features. Object-oriented programming is broader and commonly emphasizes encapsulation, abstraction, inheritance, and polymorphism. Java supports these OOP features through classes, interfaces, inheritance, overriding, and dynamic dispatch. JavaScript should not be used as a simple example of a language with no inheritance: it has prototype-based inheritance and polymorphism, even though its object model differs from Java’s class-based model.
Example: In Java, you can create a class "Vehicle" and extend it with "Car" and "Bike" subclasses that inherit and override behavior (polymorphism). In an object-based language, you could create a "Vehicle" object, but you could not derive a "Car" object from it using inheritance — you'd have to duplicate or manually copy properties.

Question: What is object cloning in Java?
Answer: Object cloning is the process of creating an exact copy of an existing object's state in a new object, without invoking a constructor. Java supports this through the Cloneable marker interface and the clone() method defined in the Object class. By default, calling clone() performs a shallow copy — primitive fields are copied by value, but reference fields (objects, arrays) are copied by reference, so both the original and the clone point to the same nested objects. To achieve a deep copy, you must override clone() and explicitly clone the nested mutable objects as well.
Example:
class Employee implements Cloneable { String name; Address address; // mutable reference type public Object clone() throws CloneNotSupportedException { return super.clone(); // shallow copy - address is shared } } For a deep copy, inside clone() you'd write: Employee copy = (Employee) super.clone(); copy.address = new Address(this.address); return copy;

Question: Implement binary search in Java and explain your approach.
Answer: Binary search is an efficient O(log n) algorithm for finding an element in a sorted array. The approach repeatedly divides the search interval in half: compare the target with the middle element; if equal, return the index; if the target is smaller, search the left half; if larger, search the right half. This continues until the element is found or the search space is empty. It requires the array to be sorted beforehand.
Example:
public static int binarySearch(int[] arr, int target) { int low = 0, high = arr.length - 1; while (low <= high) { int mid = low + (high - low) / 2; if (arr[mid] == target) return mid; else if (arr[mid] < target) low = mid + 1; else high = mid - 1; } return -1; // not found } For arr = {2, 5, 8, 12, 16, 23, 38} and target = 23, the algorithm narrows the range in about 3 comparisons instead of scanning all 7 elements linearly.

Question: What is the Java Stream API?
Answer: The Stream API, introduced in Java 8, provides a functional-style way to process a sequence of elements with operations such as filter, map, sorted, reduce, and collect. A stream is not a collection or data structure; it represents a pipeline for processing data. Intermediate operations such as filter(), map(), and sorted() are generally lazy, while a terminal operation such as collect(), reduce(), or forEach() starts the pipeline. Streams can also be parallel, but parallelStream() should not be assumed to be faster; it is most useful when the workload is large enough and the operations are suitable for parallel execution.
Example:
List<String> names = List.of("Alice", "Bob", "Charlie", "Dave"); List<String> result = names.stream() .filter(n -> n.length() > 3) .map(String::toUpperCase) .sorted() .collect(Collectors.toList()); // result = [ALICE, CHARLIE, DAVE]

Question: Using Streams, find employee names that start with a particular prefix.
Answer: This is a common Stream filtering task. You use the filter() intermediate operation with a predicate that checks String.startsWith(prefix), then map to extract the name field, and collect the results into a List using Collectors.toList(). This pattern demonstrates functional-style data processing instead of traditional for-loops with if-conditions.
Example:
List<Employee> employees = List.of( new Employee("Sam", 50000), new Employee("Sara", 60000), new Employee("Tom", 45000)); List<String> namesStartingWithSa = employees.stream() .map(Employee::getName) .filter(name -> name.startsWith("Sa")) .collect(Collectors.toList()); // Output: [Sam, Sara]

Question: Given static and instance members, explain which method can change which values.
Answer: Static methods belong to the class itself and can directly access and modify only static members (class-level fields) because static members exist independent of any object instance. Static methods cannot directly access instance (non-static) fields or call instance methods, because at the point a static method runs, no specific object may exist yet. Instance methods, on the other hand, can access and modify both instance members and static members, since an instance method is always invoked in the context of a particular object, and the class (and its static members) is already loaded.
Example:
class Counter { static int totalCount = 0; // static int id; // instance Counter() { id = ++totalCount; // instance method updating both static and instance field - allowed } static void resetTotal() { totalCount = 0; // OK // id = 0; // COMPILE ERROR - cannot access instance field from static context } }

Question: Write a SQL query to find the highest-paid employee.
Answer: If you only need one highest-paid employee and your database supports LIMIT or FETCH FIRST, sort salary in descending order and return the first row. If the question should also handle ties and remain broadly portable, compare salary with the maximum salary using MAX(). That second approach returns every employee who shares the highest salary. In an interview, mention that the exact "top 1" syntax varies by database.
Example:
-- Approach 1 SELECT * FROM Employee ORDER BY salary DESC LIMIT 1; -- Approach 2 (handles ties, portable across databases) SELECT * FROM Employee WHERE salary = (SELECT MAX(salary) FROM Employee);

Question: What is Hibernate?
Answer: Hibernate is a Java ORM framework and a widely used implementation of the JPA specification. It maps Java entities and relationships to relational database tables, manages a persistence context and entity lifecycle, performs dirty checking, supports lazy loading, and can provide first- and second-level caching. Hibernate also has its own APIs and query language (HQL), while JPA provides standardized APIs such as EntityManager and JPQL. In modern applications, it is important to understand both the JPA concepts and the Hibernate-specific behavior used by the application.
Example:
@Entity @Table(name = "employees") public class Employee { @Id @GeneratedValue private Long id; private String name; private double salary; } // Saving without writing SQL: session.save(new Employee("John", 50000)); // Hibernate generates: INSERT INTO employees (name, salary) VALUES ('John', 50000);

Question: What is Spring Boot Actuator?
Answer: Spring Boot Actuator is a sub-project that adds production-ready monitoring and management features to a Spring Boot application with minimal configuration. It exposes a set of built-in HTTP (or JMX) endpoints that reveal internal application state — health status, metrics, environment properties, active beans, thread dumps, HTTP trace, and more — which is invaluable for operations teams monitoring apps in production. Endpoints can be selectively enabled/exposed and secured, and Actuator also integrates well with monitoring tools like Prometheus, Grafana, and Micrometer.
Example:
// In application.properties: management.endpoints.web.exposure.include=health,metrics,info // Then hitting: GET /actuator/health // Returns: {"status":"UP"} // And GET /actuator/metrics/jvm.memory.used shows current JVM memory usage.

Question: Name design patterns commonly used in Spring.
Answer: Spring makes extensive use of classic Gang-of-Four design patterns internally and encourages their use in application code. Key patterns include: Singleton (Spring beans are singleton-scoped by default, one instance per container), Factory/FactoryBean (BeanFactory and ApplicationContext act as factories that create and manage beans), Proxy (used for AOP — Spring wraps beans in dynamic proxies to add cross-cutting behavior like transactions or security), Template Method (JdbcTemplate, RestTemplate abstract away boilerplate steps), Dependency Injection / Inversion of Control (the core Spring pattern, where dependencies are provided externally rather than created internally), Observer (ApplicationEvent and ApplicationListener), and Decorator/Adapter for wrapping and adapting components like HandlerAdapter in Spring MVC.
Example:
@Service public class OrderService { private final PaymentGateway paymentGateway; // dependency injected, not "newed" internally public OrderService(PaymentGateway paymentGateway) { // Dependency Injection pattern this.paymentGateway = paymentGateway; } } // Spring's IoC container (a Factory pattern) creates and wires OrderService automatically.
Question: What is the difference between Exception and RuntimeException?
Answer: Exception is the superclass for all checked exceptions (plus it's also the parent of RuntimeException). Checked exceptions (like IOException, SQLException) must be either caught with a try-catch or declared in the method signature using "throws" — the compiler enforces this at compile time, because they represent recoverable conditions the caller should anticipate (like a missing file). RuntimeException and its subclasses (like NullPointerException, IllegalArgumentException, ArrayIndexOutOfBoundsException) are unchecked exceptions — the compiler does not force you to handle or declare them, because they usually indicate programming bugs rather than recoverable external conditions.
Example:
// Checked - must declare or catch public void readFile(String path) throws IOException { FileReader fr = new FileReader(path); // throws checked IOException } // Unchecked - compiler doesn't force handling public int divide(int a, int b) { return a / b; // may throw unchecked ArithmeticException at runtime, no declaration needed }

Question: How would you rate-limit a REST API to 1000 requests in five minutes?
Answer: A common approach is the sliding window or fixed window counter algorithm backed by a fast in-memory store like Redis, since rate limiting must work correctly across multiple application instances in a distributed system. Each client (identified by API key, user ID, or IP) gets a counter key with a 5-minute expiry (TTL). On each request, you atomically increment the counter (Redis INCR is atomic); if the counter exceeds 1000 within that window, you reject the request with HTTP 429 Too Many Requests. A more accurate variant is the sliding-window-log or token-bucket algorithm, which avoids the "burst at window boundary" problem of fixed windows. In Spring Boot, this can be implemented with a custom filter/interceptor combined with Redis, or by using a library like Bucket4j or Resilience4j RateLimiter.
Example:
String key = "rate_limit:" + clientId; Long count = redisTemplate.opsForValue().increment(key); if (count == 1) { redisTemplate.expire(key, Duration.ofMinutes(5)); } if (count > 1000) { throw new ResponseStatusException(HttpStatus.TOO_MANY_REQUESTS); }

Question: What is a functional interface?
Answer: A functional interface is an interface that contains exactly one abstract method, making it eligible to be implemented using a lambda expression or method reference. It may contain any number of default or static methods, but only one abstract method. Java provides the @FunctionalInterface annotation (optional but recommended) which causes the compiler to flag an error if more than one abstract method is accidentally added. The java.util.function package provides many built-in functional interfaces like Function, Predicate, Supplier, and Consumer.
Example:
@FunctionalInterface interface Calculator { int operate(int a, int b); } Calculator addition = (a, b) -> a + b; // lambda implementing the single abstract method System.out.println(addition.operate(3, 4)); // prints 7

Question: How is a functional interface different from a normal interface?
Answer: A normal interface can declare any number of abstract methods that an implementing class must override. A functional interface is restricted (by convention and optionally enforced by @FunctionalInterface) to exactly one abstract method — this single-method constraint is what makes it compatible with lambda expressions, since a lambda's body maps directly onto that one method's signature. Normal interfaces with multiple abstract methods cannot be implemented via a lambda; they require a full class or anonymous inner class implementation.
Example:
// Normal interface - needs a class implementation interface Shape { double area(); double perimeter(); } // Functional interface - can use a lambda interface AreaCalculator { double area(double side); } AreaCalculator square = side -> side * side; // works because only 1 abstract method

Question: How would you design a secure REST API?
Answer: Designing a secure REST API involves multiple layers: (1) Authentication — verify identity using OAuth2/JWT tokens rather than sending credentials on every call; (2) Authorization — enforce role/permission-based access control at the endpoint level (e.g., Spring Security method-level @PreAuthorize); (3) Transport security — enforce HTTPS/TLS everywhere to prevent man-in-the-middle attacks; (4) Input validation — validate and sanitize all inputs to prevent injection attacks (SQL injection, XSS); (5) Rate limiting and throttling to prevent abuse/DoS; (6) Proper error handling that doesn't leak stack traces or sensitive internals; (7) CORS configuration to control which origins can call the API; (8) Secrets management — never hardcode API keys or DB passwords, use vaults like AWS Secrets Manager or environment-injected secrets; (9) Logging and auditing of security-relevant events without logging sensitive data like passwords or tokens; (10) Versioning to allow safe evolution of contracts.
Example:
@RestController @RequestMapping("/api/v1/accounts") public class AccountController { @PreAuthorize("hasRole('ADMIN')") // authorization @GetMapping("/{id}") public ResponseEntity<Account> getAccount(@PathVariable @Positive Long id) { // input validation // JWT filter already validated authentication before reaching here return ResponseEntity.ok(accountService.findById(id)); } }

Question: How is Hibernate connection-pool sizing determined?
Answer: Connection-pool sizing is a capacity-planning problem rather than a fixed Java or Hibernate formula. In a Spring Boot application, HikariCP is commonly the default pool when it is available, but the pool is provided by the application stack rather than being a "Hibernate default." Start with a deliberately small pool, then tune it using database connection limits, CPU/I/O capacity, query latency, expected concurrency, and measurements from load tests. HikariCP's commonly cited sizing guidance can be a useful starting point, but it should not be treated as a universal formula. Monitor active, idle, pending, and timed-out connections and make sure the total pool sizes across all application instances stay within the database's safe capacity.
Example:
# HikariCP configuration in application.properties spring.datasource.hikari.maximum-pool-size=15 spring.datasource.hikari.minimum-idle=5 spring.datasource.hikari.connection-timeout=30000 spring.datasource.hikari.idle-timeout=600000 spring.datasource.hikari.max-lifetime=1800000 // You'd load-test and watch pool metrics (via Actuator) to tune the exact number.

Question: What are @Embeddable and @Embedded used for?
Answer: These JPA annotations let you model a value object (a group of fields with no independent identity/lifecycle of its own) as part of a parent entity's table, instead of creating a separate entity and table. @Embeddable marks a class as embeddable — it has no @Id of its own. @Embedded is placed on the field in the owning entity to include that embeddable object's fields inline within the owning entity's table. This is useful for grouping logically related fields (like an Address made of street, city, zip) without the overhead of a full separate table and join.
Example:
@Embeddable public class Address { private String street; private String city; private String zip; } @Entity public class Employee { @Id @GeneratedValue private Long id; @Embedded private Address address; // street, city, zip columns get added directly to the Employee table }

Question: How would you centralize exception handling in a large application?
Answer: In Spring applications, centralized exception handling is achieved using @ControllerAdvice (or @RestControllerAdvice for REST APIs) combined with @ExceptionHandler methods. This lets you define exception-to-response mappings in one place instead of scattering try-catch blocks across every controller. You typically create a hierarchy of custom exceptions (e.g., ResourceNotFoundException, ValidationException, BusinessRuleException), map each to an appropriate HTTP status and a consistent error response structure (error code, message, timestamp, trace ID), and have a catch-all handler for unexpected exceptions that logs details internally but returns a generic message to the client.
Example:
@RestControllerAdvice public class GlobalExceptionHandler { @ExceptionHandler(ResourceNotFoundException.class) public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) { return ResponseEntity.status(HttpStatus.NOT_FOUND) .body(new ErrorResponse("NOT_FOUND", ex.getMessage())); } @ExceptionHandler(Exception.class) public ResponseEntity<ErrorResponse> handleGeneric(Exception ex) { log.error("Unhandled exception", ex); return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR) .body(new ErrorResponse("INTERNAL_ERROR", "Something went wrong")); } }

Question: What are interceptors used for?
Answer: Interceptors in Spring MVC (implementing HandlerInterceptor) let you execute custom logic before, after, or around the handling of an HTTP request by a controller — without modifying the controller code itself. Common use cases include logging request/response details, checking authentication tokens, measuring request execution time, modifying the model before rendering a view, or auditing. They differ from Filters (Servlet-level, run outside the Spring context and see raw requests) in that interceptors run within the Spring MVC dispatcher lifecycle and have access to handler-specific information like the target controller method.
Example:
public class LoggingInterceptor implements HandlerInterceptor { public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) { System.out.println("Incoming request: " + req.getRequestURI()); return true; // continue to controller } public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) { System.out.println("Request completed: " + req.getRequestURI()); } }

Question: How do profilers help diagnose Java applications?
Answer: Profilers are tools that attach to a running JVM (or analyze a captured snapshot) to reveal what the application is doing internally — CPU time spent per method (CPU profiling), memory allocation and object retention (memory/heap profiling), thread states and lock contention (thread profiling), and garbage collection behavior. They help diagnose performance bottlenecks (which method consumes the most CPU), memory leaks (objects that keep growing and are never garbage collected, visible via heap dumps and dominator trees), and concurrency issues (threads blocked waiting on locks). Common Java profilers include JProfiler, YourKit, VisualVM, Java Flight Recorder (JFR) with JDK Mission Control, and async-profiler.
Example:
// Using Java Flight Recorder to capture a profile: java -XX:+FlightRecorder -XX:StartFlightRecording=duration=60s,filename=recording.jfr -jar app.jar // Then open recording.jfr in JDK Mission Control to see a flame graph of hot methods, // and find that 40% of CPU time is spent inside a poorly optimized JSON serialization call.

Question: What is try-with-resources and why use it?
Answer: try-with-resources is a Java 7+ syntax that automatically closes resources (any object implementing AutoCloseable, such as streams, connections, or readers) at the end of the try block, even if an exception occurs — eliminating the need for manual finally blocks to close resources. This prevents resource leaks (like unclosed file handles or database connections) that are easy to forget with manual try-finally, and it also correctly handles suppressed exceptions if both the resource's close() and the try block throw exceptions.
Example:
// Old way - verbose and error-prone BufferedReader br = null; try { br = new BufferedReader(new FileReader("file.txt")); // read file } finally { if (br != null) br.close(); } // try-with-resources - cleaner, automatic close try (BufferedReader br = new BufferedReader(new FileReader("file.txt"))) { System.out.println(br.readLine()); } // br.close() called automatically here, even if an exception is thrown

Question: How would you implement an asynchronous REST API?
Answer: In Spring, asynchronous REST endpoints can be implemented by having the controller method return a DeferredResult, Callable, or CompletableFuture instead of a direct response object. This frees up the servlet container's request-handling thread while the actual work (e.g., a slow downstream call) happens on a separate thread pool, improving throughput under high concurrency. You enable async support with @EnableAsync and annotate the service method with @Async, or directly return a CompletableFuture composed with supplyAsync/thenApply.
Example:
@RestController public class ReportController { @Autowired ReportService reportService; @GetMapping("/reports/{id}") public CompletableFuture<ResponseEntity<Report>> getReport(@PathVariable String id) { return reportService.generateReportAsync(id) .thenApply(ResponseEntity::ok); // runs on a separate thread, doesn't block the request thread } } @Service class ReportService { @Async public CompletableFuture<Report> generateReportAsync(String id) { Report report = // slow computation return CompletableFuture.completedFuture(report); } }

Question: What is the purpose of @Transactional?
Answer: @Transactional lets Spring define transaction boundaries declaratively. Operations performed within the transaction can commit together or roll back together when the transaction fails. Spring commonly applies this through an AOP proxy. By default, Spring rolls back for RuntimeException and Error, but not for checked exceptions; rollback rules can be customized with attributes such as rollbackFor. The exact behavior also depends on transaction propagation, isolation, the transaction manager, and whether the call actually passes through the Spring proxy.
Example:
@Service public class BankService { @Transactional public void transferMoney(Long fromId, Long toId, double amount) { accountRepo.debit(fromId, amount); accountRepo.credit(toId, amount); // if this throws, the debit above is also rolled back } }

Question: How would you implement pagination with Hibernate?
Answer: Hibernate supports pagination through the Query/Criteria API's setFirstResult() (offset) and setMaxResults() (page size) methods, which translate to database-level LIMIT/OFFSET (or equivalent) clauses so that only the needed rows are fetched rather than loading the entire table into memory. In Spring Data JPA, this is simplified using the Pageable interface passed to repository methods, which returns a Page<T> object containing the data plus metadata like total pages and total elements.
Example:
// Native Hibernate API Query query = session.createQuery("FROM Employee ORDER BY id"); query.setFirstResult(20); // skip first 20 rows (offset) query.setMaxResults(10); // fetch 10 rows (page size) List<Employee> page3 = query.list(); // Spring Data JPA Pageable pageable = PageRequest.of(2, 10, Sort.by("id")); // page index 2, size 10 Page<Employee> employeePage = employeeRepository.findAll(pageable);
Question: Explain IS-A and HAS-A relationships.
Answer: These describe the two fundamental ways classes relate to each other in OOP. IS-A represents inheritance — a subclass "is a" type of its superclass, implemented in Java using "extends" (for classes) or "implements" (for interfaces). HAS-A represents composition/aggregation — a class contains a reference to another class as a field, meaning it "has a" relationship rather than being a specialized type of it. IS-A promotes polymorphism, while HAS-A promotes code reuse through delegation and is generally favored over deep inheritance hierarchies ("favor composition over inheritance") because it's more flexible and avoids tight coupling.
Example:
// IS-A class Animal {} class Dog extends Animal {} // Dog IS-A Animal // HAS-A class Engine {} class Car { private Engine engine; // Car HAS-A Engine (composition) }

Question: Explain loose coupling and tight coupling.
Answer: Coupling refers to the degree of dependency between two classes/modules. Tight coupling means a class directly creates or depends heavily on the concrete implementation of another class, so changes in one force changes in the other, and the classes are hard to test or reuse independently. Loose coupling means classes depend on abstractions (interfaces) rather than concrete implementations, typically achieved via dependency injection, so implementations can be swapped without modifying the dependent class — this makes systems more maintainable, testable (easy to mock dependencies), and extensible.
Example:
// Tight coupling class NotificationService { private EmailSender sender = new EmailSender(); // hardcoded, tightly coupled } // Loose coupling class NotificationService { private MessageSender sender; // depends on an interface NotificationService(MessageSender sender) { this.sender = sender; } // injected - can be EmailSender, SMSSender, etc. }

Question: Compare interfaces and abstract classes.
Answer: An abstract class can have both abstract methods (no body) and concrete methods (with implementation), can maintain state via instance fields, can have constructors, and supports single inheritance only (a class extends one abstract class). An interface (pre-Java 8) could only declare abstract methods and constants; since Java 8+, interfaces can also have default and static methods with bodies, but they still cannot hold instance state (no instance fields other than implicit public static final constants), and a class can implement multiple interfaces, giving more flexibility for multiple-inheritance-like behavior. Use an abstract class when classes share a common base implementation and state; use an interface when you need to define a contract that unrelated classes can implement, or when you need multiple inheritance of type.
Example:
abstract class Shape { abstract double area(); // must be implemented by subclass void describe() { System.out.println("This is a shape"); } // concrete, shared } interface Drawable { void draw(); // contract default void highlight() { System.out.println("Highlighted"); } // default method } class Circle extends Shape implements Drawable { double area() { return 3.14 * 5 * 5; } public void draw() { System.out.println("Drawing circle"); } }

Question: What is a class-level lock versus an object-level lock?
Answer: An object-level lock (acquired via synchronized on an instance method or a synchronized(this) block) locks the specific object instance, so different threads working on different instances of the class don't block each other — only threads accessing the same instance are serialized. A class-level lock (acquired via a static synchronized method, or synchronized(ClassName.class)) locks the Class object itself, which is shared across all instances, meaning it prevents concurrent execution of that synchronized static logic across ALL instances and even across different threads regardless of which object they're using.
Example:
class Counter { private int count = 0; private static int totalInstancesCreated = 0; public synchronized void increment() { count++; } // object-level lock, per-instance public static synchronized void incrementTotal() { totalInstancesCreated++; } // class-level lock, shared across all instances }

Question: Why are wait(), notify(), and notifyAll() methods defined on Object?
Answer: These methods are defined on Object (rather than on Thread) because every object in Java can potentially act as a monitor/lock for synchronization — any object can be the target of a synchronized block, and the wait/notify mechanism is intrinsically tied to that object's intrinsic lock (monitor). Since synchronization is a property of objects (not threads), and wait/notify coordinate threads that are waiting on a specific object's monitor, it makes architectural sense for these methods to live on Object itself, so they're available on any object used as a lock, not just Thread instances.
Example:
class SharedBuffer { private final Object lock = new Object(); public void produce() throws InterruptedException { synchronized (lock) { // ... produce item lock.notify(); // wakes up a thread waiting on 'lock' } } public void consume() throws InterruptedException { synchronized (lock) { lock.wait(); // releases lock and waits until notified // ... consume item } } }

Question: What is join() used for in multithreading?
Answer: Thread.join() causes the calling thread to pause execution until the thread on which join() was called finishes execution (or a specified timeout elapses). It's used when one thread's work depends on the completion of another thread — for example, a main thread that spawns several worker threads and needs to wait for all of them to finish before aggregating their results.
Example:
Thread worker = new Thread(() -> { // do some long computation }); worker.start(); worker.join(); // main thread blocks here until 'worker' completes System.out.println("Worker finished, continuing main thread");

Question: What is synchronization?
Answer: Synchronization is Java's mechanism for controlling access to shared resources by multiple threads to prevent race conditions and ensure data consistency. When a method or block is marked synchronized, only one thread can execute that code (on the same lock/monitor) at a time — other threads must wait until the lock is released. This is essential when multiple threads read and write shared mutable state concurrently, as unsynchronized access can lead to inconsistent or corrupted data due to interleaved execution.
Example:
class BankAccount { private double balance = 1000; public synchronized void withdraw(double amount) { if (balance >= amount) { balance -= amount; // without synchronized, two threads could both pass the check // before either deducts, causing an incorrect final balance } } }

Question: Explain deadlock with an example.
Answer: A deadlock occurs when two or more threads are each waiting for a lock held by the other, so none of them can ever proceed — they're stuck in a permanent standoff. This typically happens when multiple locks are acquired in inconsistent order across different threads. Deadlocks can be avoided by always acquiring locks in a consistent global order, using timeouts (tryLock with a timeout), or using higher-level concurrency utilities that avoid manual lock management.
Example:
Object lockA = new Object(); Object lockB = new Object(); // Thread 1 synchronized (lockA) { synchronized (lockB) { /* work */ } } // Thread 2 (acquires in opposite order - causes deadlock) synchronized (lockB) { synchronized (lockA) { /* work */ } } // If Thread 1 holds lockA and waits for lockB, while Thread 2 holds lockB and waits for lockA, // both threads block forever.

Question: Explain HashMap internal working and collision handling.
Answer: HashMap stores key-value pairs in an internal array of "buckets." When you call put(key, value), Java computes key.hashCode(), then applies an internal hash-spreading function to reduce collisions, and uses (n-1) & hash (where n is the array length, a power of 2) to determine the bucket index. If two keys hash to the same bucket (a collision), Java (since Java 8) stores multiple entries in that bucket as a linked list; if a single bucket accumulates 8 or more entries (and the table has at least 64 buckets), that bucket converts into a balanced red-black tree for O(log n) worst-case lookup instead of O(n) with a linked list. When retrieving a value, HashMap computes the hash, finds the bucket, then uses equals() to find the exact matching key within that bucket (since multiple different keys can share the same bucket).
Example:
Map<String, Integer> map = new HashMap<>(); map.put("apple", 1); map.put("grape", 2); // suppose "apple" and "grape" hash to the same bucket index // Both entries are stored in that bucket's linked list (or tree if bucket grows large); // map.get("grape") walks the bucket and uses "grape".equals(storedKey) to find the right entry.

Question: Compare ArrayList and LinkedList complexity.
Answer: ArrayList is backed by a dynamically resizable array, giving O(1) average time for random access (get(index)) since it's direct array indexing, but O(n) for insertions/deletions in the middle because subsequent elements must be shifted. LinkedList is a doubly-linked list, giving O(n) time for random access (must traverse from head or tail) but O(1) time for insertion/deletion at the beginning or end (and O(1) once you already have a reference/iterator to the node, though finding that node is still O(n)). ArrayList also has better cache locality (contiguous memory) making it faster in practice for most use cases, which is why ArrayList is generally preferred unless you specifically need frequent insertions/deletions at the ends (like a queue or deque).
Example:
List<Integer> arrayList = new ArrayList<>(); arrayList.add(0, 5); // O(n) - must shift all existing elements right arrayList.get(3); // O(1) - direct index access List<Integer> linkedList = new LinkedList<>(); linkedList.addFirst(5); // O(1) - just update head pointer linkedList.get(3); // O(n) - must traverse from head

Question: How would you print duplicate strings from a sentence?
Answer: A common approach is to split the sentence into words, then use a HashMap<String, Integer> to count occurrences of each word, and finally iterate over the map and print words whose count is greater than 1. This runs in O(n) time overall.
Example:
public static void printDuplicates(String sentence) { String[] words = sentence.toLowerCase().split("\\s+"); Map<String, Integer> freq = new HashMap<>(); for (String w : words) { freq.put(w, freq.getOrDefault(w, 0) + 1); } for (Map.Entry<String, Integer> entry : freq.entrySet()) { if (entry.getValue() > 1) { System.out.println(entry.getKey() + " -> " + entry.getValue()); } } } // Input: "the quick fox jumps over the lazy the fox" // Output: the -> 3, fox -> 2

Question: What is Throwable?
Answer: Throwable is the root type of Java's throwable hierarchy. Its two direct subclasses are Error and Exception. Exception includes checked exceptions as well as RuntimeException and its subclasses. Error represents serious JVM or system-level conditions such as OutOfMemoryError and StackOverflowError; applications generally should not catch Error as ordinary business logic. Technically, Error is also unchecked because the compiler does not require it to be caught or declared.
Example:
try { recursiveMethodWithNoBaseCase(); } catch (Throwable t) { // catches both Errors (like StackOverflowError) and Exceptions System.out.println("Caught: " + t.getClass().getSimpleName()); } // Output: Caught: StackOverflowError

Question: What are checked and unchecked exceptions?
Answer: Checked exceptions are subclasses of Exception other than RuntimeException and its subclasses. The compiler requires them to be caught or declared with throws. IOException is a common example. Unchecked exceptions include RuntimeException and its subclasses, and Error; the compiler does not require them to be caught or declared. The distinction is about compile-time checking, not a guarantee that one category is always recoverable and the other is always a programming bug.
Example:
// Checked - must handle public void readConfig() throws FileNotFoundException { new FileReader("config.txt"); } // Unchecked - optional to handle public int divide(int a, int b) { return a / b; // ArithmeticException possible but not required to declare }

Question: Write a custom exception.
Answer: A custom exception is created by extending Exception (for a checked exception) or RuntimeException (for an unchecked exception), typically adding constructors that accept a message and/or a cause, so it integrates cleanly with standard exception chaining and logging. Custom exceptions are useful for representing domain-specific error conditions (like InsufficientFundsException) that are more meaningful to callers than generic exceptions.
Example:
public class InsufficientFundsException extends RuntimeException { public InsufficientFundsException(String message) { super(message); } } // Usage: public void withdraw(double amount, double balance) { if (amount > balance) { throw new InsufficientFundsException("Cannot withdraw " + amount + "; balance is " + balance); } }

Question: What garbage collectors are you familiar with?
Answer: The JVM offers several garbage collector implementations, each with different trade-offs between throughput, latency, and memory footprint. Serial GC is a simple single-threaded collector suited for small applications with limited memory. Parallel GC (throughput collector) uses multiple threads for garbage collection to maximize throughput, at the cost of longer pause times, and was the default in older JVM versions. CMS (Concurrent Mark Sweep) aimed to minimize pause times by doing most collection work concurrently with the application, but is deprecated. G1 (Garbage-First) GC, the default since Java 9, divides the heap into regions and prioritizes collecting regions with the most garbage first, balancing throughput and pause time for medium-to-large heaps. ZGC and Shenandoah are newer low-latency collectors designed to keep pause times extremely short (sub-millisecond to a few milliseconds) even on very large heaps (multi-terabyte), by doing almost all work concurrently with application threads.
Example:
# Selecting a garbage collector via JVM flags java -XX:+UseG1GC -jar app.jar # G1, default modern choice java -XX:+UseZGC -jar app.jar # ZGC, for ultra-low-latency needs java -XX:+UseParallelGC -jar app.jar # Parallel, for batch/throughput-oriented jobs

Question: What is a daemon thread?
Answer: A daemon thread is a background thread that does not prevent the JVM from exiting. When all non-daemon threads finish, the JVM can terminate even if daemon threads are still running, so daemon threads should not be used for work that must be completed or for critical cleanup. "Daemon" describes the thread's JVM shutdown behavior, not its priority. You must call setDaemon(true) before start().
Example:
Thread backgroundLogger = new Thread(() -> { while (true) { System.out.println("Logging heartbeat..."); try { Thread.sleep(1000); } catch (InterruptedException e) {} } }); backgroundLogger.setDaemon(true); // JVM won't wait for this thread to finish backgroundLogger.start(); // Main thread finishes its work and exits - JVM terminates, killing backgroundLogger too

Question: What is ORM?
Answer: ORM (Object-Relational Mapping) is a programming technique that maps objects in an object-oriented language to rows in relational database tables, and object fields to table columns, letting developers interact with the database using familiar object-oriented code instead of writing raw SQL. ORM frameworks (like Hibernate, JPA) handle the translation of CRUD operations, manage relationships (one-to-many, many-to-many) as object references, provide caching, and abstract away database-specific SQL dialect differences, though they can introduce their own learning curve and, if misused, cause performance issues like the N+1 query problem.
Example:
// Without ORM (raw JDBC) String sql = "SELECT * FROM employees WHERE id = ?"; // ... manual ResultSet mapping to an Employee object // With ORM (Hibernate/JPA) Employee emp = entityManager.find(Employee.class, 1L); // object returned directly, SQL generated automatically

Question: What is dependency injection?
Answer: Dependency Injection (DI) is a design pattern where an object's dependencies (the other objects it needs to function) are provided ("injected") from an external source rather than the object creating them itself. This is a specific implementation of the broader Inversion of Control (IoC) principle. DI can happen via constructor injection (dependencies passed through the constructor — generally preferred because it makes dependencies explicit and allows fields to be final/immutable), setter injection (dependencies set via setter methods, useful for optional dependencies), or field injection (dependencies injected directly into fields, common but discouraged for testability reasons). Spring's IoC container manages this automatically based on annotations like @Autowired or constructor-based wiring.
Example:
// Without DI - tightly coupled, hard to test class OrderService { private PaymentGateway gateway = new StripeGateway(); // hardcoded dependency } // With DI (constructor injection) - loosely coupled, testable class OrderService { private final PaymentGateway gateway; public OrderService(PaymentGateway gateway) { // Spring injects the implementation this.gateway = gateway; } }

Question: How does dependency injection help achieve loose coupling?
Answer: DI helps achieve loose coupling because the dependent class no longer needs to know the concrete class of its dependency — it only depends on an abstraction (interface or superclass) and receives an actual implementation from an external container or caller at runtime. This means you can swap implementations (e.g., swap a real PaymentGateway for a mock in tests, or swap a database implementation) without touching the dependent class's code at all, since the wiring/decision of "which implementation to use" lives outside the class, typically in configuration or the DI container.
Example:
interface PaymentGateway { void pay(double amount); } class StripeGateway implements PaymentGateway { public void pay(double amount) { /* real API call */ } } class MockGateway implements PaymentGateway { public void pay(double amount) { /* no-op for tests */ } } class OrderService { private final PaymentGateway gateway; OrderService(PaymentGateway gateway) { this.gateway = gateway; } // OrderService doesn't know or care which implementation it gets } // In production: new OrderService(new StripeGateway()); // In tests: new OrderService(new MockGateway());

Question: What is circular dependency?
Answer: A circular dependency occurs when two or more beans depend on each other, directly or indirectly, forming a cycle (Bean A needs Bean B, and Bean B needs Bean A). In Spring, this can cause a BeanCurrentlyInCreationException at startup, especially with constructor injection, because Spring cannot fully construct A without B already existing, and vice versa. Spring can sometimes resolve circular dependencies automatically for setter/field injection (via a mechanism using early bean references from the singleton cache), but constructor-based circular dependencies fail outright. The recommended fix is to redesign the classes to break the cycle — often by introducing a third class/interface that both depend on, using setter injection instead of constructor injection, or using @Lazy to defer initialization.
Example:
@Service class ServiceA { @Autowired ServiceB serviceB; // A depends on B } @Service class ServiceB { @Autowired ServiceA serviceA; // B depends on A - circular! } // Fix: extract shared logic into a ServiceC that both A and B depend on instead of depending on each other, // or use @Lazy on one of the @Autowired fields to defer resolution.

Question: What does @Entity do?
Answer: @Entity marks a Java class as a JPA entity whose instances can be managed by a persistence provider such as Hibernate. An entity needs a primary key mapped with @Id and must have a no-argument constructor that is at least protected or public, so the persistence provider can instantiate it. Its fields or properties can then be mapped to database columns and relationships. Schema generation is possible with provider/configuration support, but @Entity itself does not mean that the database schema will automatically be created in every application.
Example:
@Entity @Table(name = "products") public class Product { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; private String name; private double price; // getters and setters } // JPA maps this class to a "products" table with columns id, name, price
Question: Design tables and class relationships for a doctor appointment scheduling system.
Answer: A doctor appointment system typically needs at minimum these entities: Patient (id, name, contact info), Doctor (id, name, specialization), Appointment (id, patient_id FK, doctor_id FK, appointment_time, status), and optionally Slot/Availability (doctor_id FK, date, time_range, is_booked) to track which time slots a doctor offers. The relationships are: a Doctor has many Appointments (one-to-many), a Patient has many Appointments (one-to-many), and Appointment acts as a junction/associative entity connecting Doctor and Patient (effectively representing a many-to-many relationship between them, enriched with appointment-specific data like time and status). In Java classes, this maps to Doctor and Patient each holding a List<Appointment>, and Appointment holding references to a single Doctor and single Patient.
Example:
CREATE TABLE doctor (id INT PRIMARY KEY, name VARCHAR(100), specialization VARCHAR(50)); CREATE TABLE patient (id INT PRIMARY KEY, name VARCHAR(100), phone VARCHAR(20)); CREATE TABLE appointment ( id INT PRIMARY KEY, doctor_id INT REFERENCES doctor(id), patient_id INT REFERENCES patient(id), appointment_time DATETIME, status VARCHAR(20) -- SCHEDULED, COMPLETED, CANCELLED ); @Entity class Doctor { @Id Long id; String name; @OneToMany(mappedBy="doctor") List<Appointment> appointments; } @Entity class Patient { @Id Long id; String name; @OneToMany(mappedBy="patient") List<Appointment> appointments; } @Entity class Appointment { @Id Long id; @ManyToOne Doctor doctor; @ManyToOne Patient patient; LocalDateTime time; String status; }

Question: Compare Factory and Abstract Factory.
Answer: The Factory Method pattern defines a single method (often in a base class or interface) that subclasses override to create objects of a specific type — it deals with creating one family/hierarchy of related objects through inheritance. The Abstract Factory pattern is a "factory of factories" — it provides an interface for creating families of related or dependent objects without specifying their concrete classes, typically composing multiple factory methods together. Abstract Factory is used when you need to create groups of related objects that must be used together (e.g., a UI toolkit needing matching Button, Checkbox, and ScrollBar for either a Windows or Mac theme), while Factory Method is simpler and focuses on one product type at a time.
Example:
// Factory Method - creates one product type interface ShapeFactory { Shape createShape(); } class CircleFactory implements ShapeFactory { public Shape createShape() { return new Circle(); } } // Abstract Factory - creates families of related products interface UIFactory { Button createButton(); Checkbox createCheckbox(); } class WindowsUIFactory implements UIFactory { public Button createButton() { return new WindowsButton(); } public Checkbox createCheckbox() { return new WindowsCheckbox(); } } class MacUIFactory implements UIFactory { public Button createButton() { return new MacButton(); } public Checkbox createCheckbox() { return new MacCheckbox(); } }

Question: Compare setter injection and constructor injection.
Answer: Constructor injection provides dependencies through a class's constructor at object creation time; it makes dependencies mandatory and explicit, allows fields to be declared "final" (immutable), and ensures the object is always in a fully valid state right after construction — this is why the Spring team recommends it as the default choice. Setter injection provides dependencies through public setter methods after object construction; it's useful for optional dependencies or when you need to change a dependency later, but it means the object could exist temporarily in an incomplete/invalid state before all setters are called, and fields can't be final.
Example:
// Constructor injection class OrderService { private final PaymentGateway gateway; // can be final - immutable after construction public OrderService(PaymentGateway gateway) { this.gateway = gateway; } } // Setter injection class OrderService { private PaymentGateway gateway; // cannot be final public void setGateway(PaymentGateway gateway) { this.gateway = gateway; } // optional, can be reassigned }

Question: Write SQL using GROUP BY.
Answer: GROUP BY is used to aggregate rows that share a common value in specified columns, typically combined with aggregate functions like COUNT, SUM, AVG, MAX, or MIN to compute per-group statistics. A common example is finding the total salary paid per department, or the count of employees per department. The HAVING clause is used to filter groups after aggregation (unlike WHERE, which filters rows before grouping).
Example:
SELECT department, COUNT(*) AS employee_count, AVG(salary) AS avg_salary FROM employees GROUP BY department HAVING COUNT(*) > 5 ORDER BY avg_salary DESC; -- This groups employees by department, calculates count and average salary per department, -- then only shows departments with more than 5 employees, sorted by average salary.

Question: Find the number of occurrences of a pattern in a circular linked list.
Answer: A circular linked list is one where the last node points back to the first node instead of null. To find occurrences of a pattern (a sequence of values), you traverse the list starting from the head, comparing consecutive nodes against the pattern sequence, and because the list is circular, you must track how many nodes you've visited (or detect when you've returned to the starting node) to avoid infinite looping. For each starting position within one full cycle, you check whether the pattern matches starting there, incrementing a counter on each match.
Example:
public static int countPatternOccurrences(Node head, int[] pattern) { if (head == null) return 0; int count = 0; int totalNodes = countNodes(head); // count nodes once to know cycle length Node current = head; for (int i = 0; i < totalNodes; i++) { if (matchesPatternFrom(current, pattern)) count++; current = current.next; } return count; } private static boolean matchesPatternFrom(Node start, int[] pattern) { Node temp = start; for (int val : pattern) { if (temp.data != val) return false; temp = temp.next; } return true; }

Question: Write Java code to count unique words and their frequencies.
Answer: This is solved using a HashMap<String, Integer> where each word is a key and its count is the value. You split the text into words (handling case and punctuation), then iterate and use getOrDefault or merge to increment counts. Alternatively, this can be elegantly done using the Stream API with Collectors.groupingBy and Collectors.counting().
Example:
public static Map<String, Long> wordFrequency(String text) { return Arrays.stream(text.toLowerCase().split("\\W+")) .filter(w -> !w.isEmpty()) .collect(Collectors.groupingBy(w -> w, Collectors.counting())); } // Input: "Java is great. Java is powerful." // Output: {java=2, is=2, great=1, powerful=1}
Question: What are Java access specifiers?
Answer: Access specifiers (also called access modifiers) control the visibility/accessibility of classes, methods, and fields from other parts of a program. Java has four levels: private (accessible only within the same class), default/package-private (no keyword — accessible within the same package only), protected (accessible within the same package plus subclasses even in different packages), and public (accessible from anywhere). Choosing the right access level supports encapsulation by exposing only what's necessary and hiding implementation details.
Example:
public class BankAccount { private double balance; // only this class can access directly protected String accountType; // this class, package, and subclasses String branchCode; // default - same package only public String accountNumber; // accessible from anywhere }

Question: What is a Spring Boot starter dependency?

Question: What is Hibernate caching?
Answer: Hibernate's first-level cache is tied to the current persistence context/Session and is enabled by default. If the same entity is loaded by identifier within that context, Hibernate can return the already-managed instance without another database lookup. A second-level cache is optional and shared across persistence contexts through a configured Hibernate-compatible cache solution; it can help with data that is read frequently and changes infrequently. Hibernate also has a query-cache feature, but it should be enabled deliberately because cache invalidation and query-result staleness can make it unsuitable for many workloads.
Example:
// First-level cache (automatic) Employee e1 = session.get(Employee.class, 1L); // hits DB Employee e2 = session.get(Employee.class, 1L); // returns from session cache, no DB hit // Second-level cache (requires config) @Entity @Cacheable @org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE) public class Country { // rarely-changing reference data - good candidate for L2 cache @Id Long id; String name; }

Question: Find the Nth-highest salary in an Employee table.
Answer: A common SQL approach uses a window function like DENSE_RANK() (which handles ties correctly without skipping ranks) to rank salaries in descending order, then filters for the desired rank in an outer query. An older, more portable approach (works on databases without window function support) uses a correlated subquery counting distinct higher salaries.
Example:
-- Using window function (modern SQL, e.g. PostgreSQL, MySQL 8+) SELECT salary FROM ( SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees ) ranked WHERE rnk = 3; -- 3rd highest salary -- Portable subquery approach SELECT DISTINCT salary FROM employees e1 WHERE 2 = (SELECT COUNT(DISTINCT salary) FROM employees e2 WHERE e2.salary >= e1.salary); -- Also finds the 3rd highest by counting how many distinct salaries are >= each salary

Question: What is @ComponentScan used for?
Answer: @ComponentScan tells Spring which packages to scan for classes annotated with stereotype annotations like @Component, @Service, @Repository, and @Controller, so it can automatically detect and register them as beans in the application context, without needing to manually declare each bean in XML or Java config. By default, @SpringBootApplication (which includes @ComponentScan) scans the package of the main application class and all its sub-packages, which is why Spring Boot projects are conventionally structured with the main class at the root package.
Example:
@SpringBootApplication // includes @ComponentScan(basePackages = "com.example.myapp") implicitly @ComponentScan(basePackages = {"com.example.myapp", "com.example.sharedlib"}) // explicit, scans extra package too public class MyApplication { public static void main(String[] args) { SpringApplication.run(MyApplication.class, args); } }
Question: How would you optimize database queries?
Answer: Query optimization involves several strategies: (1) Add proper indexes on columns used in WHERE, JOIN, and ORDER BY clauses, since indexes let the database avoid full table scans; (2) Avoid SELECT * — fetch only needed columns to reduce I/O; (3) Use EXPLAIN/EXPLAIN ANALYZE to inspect the query execution plan and identify full table scans, missing indexes, or inefficient joins; (4) Avoid N+1 query problems in ORMs by using JOIN FETCH or batch fetching; (5) Use pagination (LIMIT/OFFSET or keyset pagination) instead of loading entire large tables; (6) Denormalize selectively or use materialized views for read-heavy reporting queries; (7) Use connection pooling to avoid connection setup overhead; (8) Cache frequently-read, rarely-changed data; (9) Rewrite correlated subqueries as joins where possible, since joins are often optimized better by the query planner.
Example:
-- Before: full table scan, slow SELECT * FROM orders WHERE customer_email = 'john@example.com'; -- After: add an index, select only needed columns CREATE INDEX idx_orders_customer_email ON orders(customer_email); SELECT order_id, order_date, total FROM orders WHERE customer_email = 'john@example.com'; -- Use EXPLAIN to confirm the index is now used instead of a sequential scan.

Question: How can one Spring Boot application connect to multiple databases?
Answer: To connect a single Spring Boot app to multiple databases, you define separate DataSource beans, EntityManagerFactory beans, and TransactionManager beans for each database, and use @Primary on one of them to resolve ambiguity for the default injection point. You also typically split your entity/repository packages by database and point Spring Data JPA repositories at the correct EntityManagerFactory using @EnableJpaRepositories with basePackages and entityManagerFactoryRef parameters.

@Configuration @EnableJpaRepositories(basePackages = "com.example.db1.repo", entityManagerFactoryRef = "db1EntityManagerFactory", transactionManagerRef = "db1TransactionManager") public class Db1Config { @Primary @Bean public DataSource db1DataSource() { return DataSourceBuilder.create().url("jdbc:mysql://host1/db1").build(); } // ... entityManagerFactory and transactionManager beans referencing db1DataSource } @Configuration @EnableJpaRepositories(basePackages = "com.example.db2.repo", entityManagerFactoryRef = "db2EntityManagerFactory", transactionManagerRef = "db2TransactionManager") public class Db2Config { @Bean public DataSource db2DataSource() { return DataSourceBuilder.create().url("jdbc:postgresql://host2/db2").build(); } }

Question: How would you test a private-method-related code path?
Answer: The general best practice is to NOT test private methods directly — instead, test them indirectly through the public methods that call them, since private methods are implementation details and the public API is the actual contract you care about. If a private method is complex enough to need direct/isolated testing, that's often a sign it should be extracted into its own class or made package-private so it can be unit tested directly. In rare cases where direct testing of a private method is unavoidable (e.g., legacy code you can't refactor), reflection can be used to invoke it, though this is generally discouraged.
Example:
class Calculator { public int computeDiscountedPrice(int price, int quantity) { return applyDiscount(price * quantity); // private method exercised indirectly } private int applyDiscount(int total) { return total > 100 ? (int)(total * 0.9) : total; } } // Test the public method, which exercises the private method's logic: @Test void testComputeDiscountedPrice() { Calculator calc = new Calculator(); assertEquals(90, calc.computeDiscountedPrice(20, 10)); // indirectly verifies applyDiscount logic }

Question: How would you monitor and troubleshoot production bugs?
Answer: A systematic approach includes: (1) Centralized logging (e.g., ELK stack, Splunk) with structured logs and correlation/trace IDs to follow a request across services; (2) Application Performance Monitoring (APM) tools like New Relic, Dynatrace, or Datadog to see latency, error rates, and traces; (3) Metrics dashboards (Prometheus + Grafana) tracking key indicators like error rate, response time, throughput; (4) Alerting on anomalies (spike in 5xx errors, latency degradation); (5) Distributed tracing (e.g., Zipkin, Jaeger, OpenTelemetry) to pinpoint which microservice or call in a chain is failing or slow; (6) Reproducing the issue in a staging environment using the same inputs; (7) Reviewing recent deployments/changes as the first suspect (most production incidents follow a recent change); (8) Using heap/thread dumps for memory or concurrency-related issues.
Example:
// Adding a correlation/trace ID to logs for tracing a request across microservices MDC.put("traceId", UUID.randomUUID().toString()); log.info("Processing order {}", orderId); // Then in Kibana/Splunk, search by traceId to see the full request lifecycle across all services, // pinpointing exactly where in the chain an error or slowdown occurred.

Question: Design a database for a student attendance system.

Question: Design a login-lockout system after repeated incorrect passwords.
Answer: The system tracks failed login attempts per user, typically with a failed_attempts counter and a locked_until timestamp column on the User table (or a separate LoginAttempt tracking table for auditing). On each failed login, increment the counter; if it reaches a threshold (e.g., 5 attempts), set locked_until to a future time (e.g., now + 15 minutes) and reject further login attempts until that time passes. On a successful login, reset the counter to zero. For scalability and to avoid abuse across many users, this is often combined with rate limiting per IP address as well, and using a fast store like Redis with TTL keys is common for high-traffic systems instead of hitting the main database on every attempt.
Example:
public boolean attemptLogin(String username, String password) { User user = userRepo.findByUsername(username); if (user.getLockedUntil() != null && user.getLockedUntil().isAfter(Instant.now())) { throw new AccountLockedException("Account locked. Try again later."); } if (!passwordEncoder.matches(password, user.getPasswordHash())) { user.setFailedAttempts(user.getFailedAttempts() + 1); if (user.getFailedAttempts() >= 5) { user.setLockedUntil(Instant.now().plus(15, ChronoUnit.MINUTES)); } userRepo.save(user); return false; } user.setFailedAttempts(0); // reset on success userRepo.save(user); return true; }

Question: Explain @SpringBootApplication.
Answer: @SpringBootApplication is a convenience "meta-annotation" that combines three annotations into one: @Configuration (marks the class as a source of bean definitions), @EnableAutoConfiguration (tells Spring Boot to automatically configure beans based on the JAR dependencies found on the classpath — e.g., if it finds spring-webmvc, it auto-configures a DispatcherServlet), and @ComponentScan (scans the current package and sub-packages for components to register as beans). It's typically placed on the main class that contains the main() method that bootstraps the application via SpringApplication.run().
Example:
@SpringBootApplication // equivalent to @Configuration + @EnableAutoConfiguration + @ComponentScan public class MyApp { public static void main(String[] args) { SpringApplication.run(MyApp.class, args); } }

Question: Compare @RestController and @Controller.
Answer: @Controller is the traditional Spring MVC annotation used for classes whose methods typically return view names (like JSP or Thymeleaf template names) that get resolved and rendered as HTML pages — if you want a method in a @Controller to return raw data (like JSON) instead of a view, you must additionally annotate that method with @ResponseBody. @RestController is a convenience annotation that combines @Controller and @ResponseBody at the class level, so every method's return value is automatically serialized (typically to JSON) and written directly to the HTTP response body — this is the standard choice for building REST APIs.
Example:
@Controller public class WebController { @GetMapping("/home") public String home() { return "home"; } // returns a view name "home.html" to render @GetMapping("/data") @ResponseBody // needed here to return raw JSON instead of a view public User getData() { return new User("Alice"); } } @RestController // every method behaves like it has @ResponseBody public class ApiController { @GetMapping("/api/user") public User getUser() { return new User("Alice"); } // serialized directly to JSON }

Question: Why use Hibernate?
Answer: Hibernate is used to eliminate repetitive JDBC boilerplate (manual SQL, ResultSet mapping, connection management), provide database portability (HQL and Hibernate's dialect abstraction let you switch databases with minimal code change), manage object relationships and lazy loading automatically, provide caching to reduce database load, handle transaction management integration, support automatic dirty checking (Hibernate detects changed fields on managed entities and generates UPDATE statements automatically without explicit save calls), and integrate seamlessly with Spring via Spring Data JPA for even less boilerplate. It significantly increases developer productivity for data-access-heavy applications, though it requires understanding its behavior (like the N+1 problem) to use effectively.
Example:
// Without Hibernate - manual JDBC String sql = "UPDATE employees SET salary = ? WHERE id = ?"; PreparedStatement ps = connection.prepareStatement(sql); ps.setDouble(1, newSalary); ps.setLong(2, empId); ps.executeUpdate(); // With Hibernate - automatic dirty checking, no explicit UPDATE needed Employee emp = session.get(Employee.class, empId); emp.setSalary(newSalary); // just modify the object // Hibernate automatically issues the UPDATE SQL when the transaction commits

Question: Explain Spring bean scopes and when they are useful.
Answer: Bean scope defines the lifecycle and visibility of a bean instance within the Spring container. The main scopes are: singleton (default) — exactly one shared instance per Spring container, used for stateless services; prototype — a new instance is created every time the bean is requested, useful for stateful, non-thread-safe objects; request — one instance per HTTP request (web-aware scope, useful for web apps); session — one instance per HTTP session, useful for storing user-specific state across multiple requests; and application — one instance per ServletContext (similar to singleton but scoped to the web application). Choosing the right scope matters for thread-safety and memory: a stateful bean incorrectly declared singleton could leak data between users/threads.
Example:
@Service @Scope("singleton") // default - one instance shared by everyone public class ConfigService { } @Component @Scope("prototype") // new instance each time it's injected/requested public class ShoppingCart { private List<Item> items = new ArrayList<>(); } @Component @Scope(value = WebApplicationContext.SCOPE_SESSION, proxyMode = ScopedProxyMode.TARGET_CLASS) public class UserSessionData { private String preferredLanguage; } // one instance per logged-in user session
Question: How do Spring MVC request-mapping annotations work?
Answer: Spring MVC "mappings" refer to annotations that map incoming HTTP requests to specific controller handler methods based on URL path, HTTP method, headers, or parameters. @RequestMapping is the general-purpose base annotation (can specify method=RequestMethod.GET, etc.), while Spring provides more concise shortcut annotations for common HTTP verbs: @GetMapping, @PostMapping, @PutMapping, @DeleteMapping, and @PatchMapping. You can also bind parts of the URL or request to method parameters using @PathVariable (for URI template variables), @RequestParam (for query string parameters), and @RequestBody (for deserializing the JSON/XML request body into a Java object).
Example:
@RestController @RequestMapping("/api/users") // base path for all methods in this controller public class UserController { @GetMapping("/{id}") // maps GET /api/users/5 public User getUser(@PathVariable Long id) { ... } @GetMapping // maps GET /api/users?active=true public List<User> getUsers(@RequestParam boolean active) { ... } @PostMapping // maps POST /api/users with JSON body public User createUser(@RequestBody User user) { ... } }

Question: Which Hibernate concepts should a backend developer know for interviews?

// N+1 problem List<Department> departments = departmentRepo.findAll(); // 1 query for (Department d : departments) { d.getEmployees().size(); // N additional queries, one per department, if lazily fetched } // Fix using JOIN FETCH @Query("SELECT d FROM Department d JOIN FETCH d.employees") List<Department> findAllWithEmployees(); // single query using a JOIN instead of N+1

Question: How do you generate all permutations of a string in Java?
Answer: Generating all permutations of a string is a classic backtracking problem. The idea is to fix one character at a time at the current position, recursively permute the remaining characters, then swap back (backtrack) to try the next character at that position. For a string of length n, there are n! permutations, so this approach has exponential time complexity, which is expected for this class of problem.
Example:
public static void permute(char[] arr, int start) { if (start == arr.length - 1) { System.out.println(new String(arr)); return; } for (int i = start; i < arr.length; i++) { swap(arr, start, i); permute(arr, start + 1); // recurse on the rest swap(arr, start, i); // backtrack } } private static void swap(char[] arr, int i, int j) { char temp = arr[i]; arr[i] = arr[j]; arr[j] = temp; } // permute("ABC".toCharArray(), 0) prints: ABC, ACB, BAC, BCA, CBA, CAB
Question: How would you build a simple CRUD REST API in Spring Boot?
Answer: A basic Spring Boot REST API demo involves creating a @RestController class with mapped endpoints for standard CRUD operations, backed by a @Service layer for business logic and a @Repository (Spring Data JPA interface) for data access. This layered architecture (Controller -> Service -> Repository) separates concerns: the controller handles HTTP specifics, the service holds business rules, and the repository handles persistence.

@RestController @RequestMapping("/api/books") public class BookController { @Autowired private BookService bookService; @GetMapping public List<Book> getAll() { return bookService.findAll(); } @GetMapping("/{id}") public Book getById(@PathVariable Long id) { return bookService.findById(id); } @PostMapping public Book create(@RequestBody Book book) { return bookService.save(book); } @DeleteMapping("/{id}") public void delete(@PathVariable Long id) { bookService.delete(id); } } @Repository interface BookRepository extends JpaRepository<Book, Long> {} // CRUD methods provided automatically

Question: Explain common HTTP status codes.
Answer: HTTP status codes are grouped by their first digit. 2xx (Success): 200 OK (successful GET/PUT), 201 Created (successful POST that created a resource), 204 No Content (successful request with no response body, common for DELETE). 3xx (Redirection): 301 Moved Permanently, 304 Not Modified (used with caching). 4xx (Client Error): 400 Bad Request (malformed request), 401 Unauthorized (missing/invalid authentication), 403 Forbidden (authenticated but not authorized), 404 Not Found, 409 Conflict (e.g., duplicate resource), 429 Too Many Requests (rate limiting). 5xx (Server Error): 500 Internal Server Error (unhandled exception), 502 Bad Gateway, 503 Service Unavailable (server overloaded or down for maintenance).
Example:
// Returning proper status codes in Spring @PostMapping("/users") public ResponseEntity<User> createUser(@RequestBody User user) { User saved = userService.save(user); return ResponseEntity.status(HttpStatus.CREATED).body(saved); // 201 Created } @GetMapping("/users/{id}") public ResponseEntity<User> getUser(@PathVariable Long id) { return userService.findById(id) .map(ResponseEntity::ok) // 200 OK .orElse(ResponseEntity.notFound().build()); // 404 Not Found }

Question: Compare 401 Unauthorized and 403 Forbidden.
Answer: 401 Unauthorized means the request lacks valid authentication credentials altogether — the server doesn't know who you are (or your credentials are invalid/expired), so it's asking you to authenticate (log in, provide a valid token). 403 Forbidden means the server DOES know who you are (you're successfully authenticated), but you don't have permission to access the requested resource — it's an authorization failure, not an authentication one. A helpful mnemonic: 401 = "who are you?", 403 = "I know who you are, but you can't do that."
Example:
// 401 - no/invalid token provided GET /api/admin/reports Authorization: (missing or expired token) --> 401 Unauthorized // 403 - valid token, but user role lacks permission GET /api/admin/reports Authorization: Bearer <valid-token-for-a-regular-user> --> 403 Forbidden (this user is authenticated but is not an ADMIN)

Question: Explain database indexing.
Answer: An index is a separate on-disk data structure (commonly a B-tree or B+tree) that the database maintains alongside a table, allowing it to look up rows matching a condition (like WHERE column = value) much faster than scanning every row (a full table scan). Indexes dramatically speed up SELECT queries, JOINs, and ORDER BY operations on indexed columns, but they come at a cost: every INSERT, UPDATE, or DELETE must also update the index structures, so excessive indexing slows down writes and consumes additional disk space. Best practice is to index columns frequently used in WHERE clauses, JOIN conditions, and foreign keys, but avoid indexing every column blindly.
Example:
-- Without an index: full table scan across millions of rows SELECT * FROM orders WHERE customer_id = 12345; -- With an index: fast lookup via B-tree traversal CREATE INDEX idx_orders_customer_id ON orders(customer_id); SELECT * FROM orders WHERE customer_id = 12345; -- now uses the index, much faster

Question: Explain JWT authentication and authorization flow.
Answer: JWT (JSON Web Token) is a compact, self-contained, digitally signed token used for stateless authentication. The flow: (1) the user logs in with credentials; (2) the server verifies credentials and generates a JWT containing claims (user ID, roles, expiration) signed with a secret key or private key; (3) the server returns this JWT to the client; (4) the client stores the JWT (e.g., in memory or secure storage) and includes it in the Authorization header (Bearer <token>) on subsequent requests; (5) the server verifies the JWT's signature and expiration on each request (without needing to query a session store, since all needed info is embedded in the token itself — this is what makes it "stateless"); (6) if valid, the server extracts the user's identity/roles from the token's claims and uses them for authorization decisions.
Example:
// Server generates JWT on login String token = Jwts.builder() .setSubject(user.getUsername()) .claim("roles", user.getRoles()) .setExpiration(new Date(System.currentTimeMillis() + 3600000)) .signWith(SignatureAlgorithm.HS256, secretKey) .compact(); // Client sends it on every request GET /api/orders Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9... // Server validates and extracts claims without a database session lookup Claims claims = Jwts.parser().setSigningKey(secretKey).parseClaimsJws(token).getBody(); String username = claims.getSubject();

Question: Compare SQL and NoSQL.
Answer: SQL (relational) databases like PostgreSQL and MySQL store data in structured tables with predefined schemas, enforce ACID transactions, and use SQL for querying with strong support for complex joins and relationships — they're ideal when data integrity, relationships, and consistency are critical (e.g., financial systems). NoSQL databases (like MongoDB, Cassandra, DynamoDB) use flexible schemas (document, key-value, column-family, or graph models), typically prioritize horizontal scalability and high write/read throughput over strict consistency (often following the BASE model and eventual consistency rather than ACID), and are well-suited for unstructured/semi-structured data, rapidly evolving schemas, and massive scale (e.g., social media feeds, IoT data, catalogs).
Example:
-- SQL - fixed schema, relational CREATE TABLE users (id INT PRIMARY KEY, name VARCHAR(100), email VARCHAR(100)); // NoSQL (MongoDB) - flexible schema, document-based db.users.insertOne({ name: "Alice", email: "alice@example.com", preferences: { theme: "dark", notifications: true } // nested structure, no fixed schema });

Question: Compare PostgreSQL and MongoDB.
Answer: PostgreSQL is a relational (SQL) database with a fixed schema, strong ACID transaction guarantees, rich support for complex joins, and advanced features like window functions, full-text search, and even native JSONB columns for semi-structured data — making it a versatile choice for most general-purpose applications. MongoDB is a document-oriented NoSQL database that stores data as flexible, schema-less BSON documents, which is well-suited for rapidly evolving data models, nested/hierarchical data, and horizontal scaling (sharding) across many servers, but traditionally offered weaker multi-document transaction guarantees than PostgreSQL (though modern MongoDB versions have added multi-document ACID transactions too). Choose PostgreSQL for structured, relational data with complex queries; choose MongoDB when your data is naturally document-shaped and your schema needs to evolve quickly, or when you need to scale writes horizontally across many nodes easily.
Example:
-- PostgreSQL: strict schema, relational integrity enforced CREATE TABLE orders (id SERIAL PRIMARY KEY, customer_id INT REFERENCES customers(id), total NUMERIC); // MongoDB: document can have varying fields per record, no enforced schema db.orders.insertOne({ customerId: "abc123", items: [{sku:"X1", qty:2}], total: 49.99, giftWrap: true }); db.orders.insertOne({ customerId: "xyz456", items: [{sku:"Y2", qty:1}], total: 19.99 }); // no giftWrap field - totally fine

Question: Compare ACID and CAP.
Answer: ACID (Atomicity, Consistency, Isolation, Durability) is a set of guarantees traditional relational databases provide for transactions: a transaction fully completes or fully fails (Atomicity), the database moves from one valid state to another (Consistency), concurrent transactions don't interfere with each other (Isolation), and committed changes survive crashes (Durability). CAP theorem, on the other hand, is about distributed systems and states that a distributed data store can only guarantee two of the following three at the same time: Consistency (every read gets the latest write), Availability (every request gets a response, even if not the latest data), and Partition tolerance (the system continues to function despite network partitions between nodes). Since network partitions are unavoidable in real distributed systems, the practical trade-off is usually between Consistency and Availability (CP vs AP systems) — for example, traditional relational databases in single-node mode prioritize ACID consistency, while many NoSQL databases are designed as AP systems that favor availability with eventual consistency.
Example:
// ACID example - bank transfer either fully happens or not at all BEGIN TRANSACTION; UPDATE accounts SET balance = balance - 100 WHERE id = 1; UPDATE accounts SET balance = balance + 100 WHERE id = 2; COMMIT; -- Atomicity ensures both updates succeed together or neither does // CAP trade-off example // A CP system (like a strongly-consistent config store, e.g. ZooKeeper/etcd) will refuse to serve // reads/writes during a network partition rather than risk returning stale data. // An AP system (like Cassandra in its default config) will keep serving requests during a partition, // possibly returning slightly stale data until the partition heals and nodes reconcile.

Question: Why would you use sharding?
Answer: Sharding is a horizontal scaling technique where a large dataset is partitioned across multiple database servers (shards), with each shard holding a subset of the data (commonly split by a shard key, like customer_id ranges or a hash of the key). It's used when a single database server can no longer handle the data volume or the read/write throughput required — sharding distributes the load across many machines, allowing the system to scale beyond what a single, even very powerful, server could handle. Trade-offs include increased complexity (cross-shard queries and joins become harder, transactions spanning shards are complex, and rebalancing shards as data grows requires careful planning).
Example:
// Sharding by customer_id hash across 4 database shards int shardIndex = Math.abs(customerId.hashCode()) % 4; // determines which of 4 shard servers to use DataSource shardDataSource = shardRouter.getDataSource(shardIndex); // Customer data for IDs hashing to 0 always goes to Shard 0, hashing to 1 goes to Shard 1, etc. // This distributes the total dataset and query load across 4 independent database servers.

Question: Explain inversion of control and dependency injection.
Answer: Inversion of Control (IoC) is a broad design principle where the control of object creation, configuration, and lifecycle is transferred from the application code itself to an external framework/container — instead of your code calling "new" to create dependencies and controlling the flow, the framework calls your code and provides what it needs ("Don't call us, we'll call you"). Dependency Injection is the most common technique used to implement IoC specifically for supplying an object's dependencies: rather than a class creating its own dependencies, the IoC container constructs and injects them. In Spring, the ApplicationContext acts as the IoC container, and DI is achieved via annotations like @Autowired or constructor injection.
Example:
// Without IoC - class controls its own dependency creation class OrderService { private PaymentGateway gateway = new StripeGateway(); // OrderService is in control, tightly coupled } // With IoC + DI - Spring container is in control @Service class OrderService { private final PaymentGateway gateway; @Autowired // Spring's IoC container creates and injects the dependency - control is inverted public OrderService(PaymentGateway gateway) { this.gateway = gateway; } }

Question: Compare getter/setter injection with other injection styles.
Answer: Setter injection (using setter methods to supply dependencies after object construction) is best suited for optional dependencies that have a sensible default and might be reconfigured later, since it allows the dependency to be changed after the object is created. This contrasts with constructor injection, which is preferred for mandatory dependencies since it guarantees the object can never exist in an incomplete state and allows immutable (final) fields, and field injection (using @Autowired directly on a field), which is the most concise but is generally discouraged because it hides dependencies (they're not visible in the constructor signature), makes unit testing harder (you can't easily pass mocks without reflection or a DI framework), and doesn't support immutability.
Example:
// Setter injection - good for optional dependency class ReportService { private Logger logger; // optional - has internal default behavior if not set public void setLogger(Logger logger) { this.logger = logger; } } // Constructor injection - good for mandatory dependency, testable, immutable class ReportService { private final DataSource dataSource; // mandatory - service can't function without it public ReportService(DataSource dataSource) { this.dataSource = dataSource; } } // Field injection - concise but discouraged for testability reasons class ReportService { @Autowired private DataSource dataSource; // hard to unit test without a Spring context or reflection }

Question: Explain the Singleton pattern.
Answer: The Singleton pattern ensures that a class has only one instance throughout the application's lifetime and provides a single global access point to that instance. It's implemented by making the constructor private (so no other code can instantiate it directly) and providing a static method (commonly named getInstance()) that returns the single shared instance, creating it lazily or eagerly. In multi-threaded environments, care must be taken to make instance creation thread-safe (using synchronized, double-checked locking, or the "initialization-on-demand holder" idiom), or simply using an enum, which the JVM guarantees to be a thread-safe singleton by design. In Spring, beans are singleton-scoped by default, so the framework manages this pattern for you automatically without manual boilerplate.
Example:
// Classic thread-safe singleton using double-checked locking public class ConfigManager { private static volatile ConfigManager instance; private ConfigManager() {} // private constructor prevents external instantiation public static ConfigManager getInstance() { if (instance == null) { synchronized (ConfigManager.class) { if (instance == null) { instance = new ConfigManager(); } } } return instance; } } // Simplest thread-safe singleton using an enum public enum ConfigManagerEnum { INSTANCE; public void doSomething() { /* ... */ } }
Question: What is the difference between == and equals()?
Answer: == compares references for objects (checks whether two variables point to the exact same memory location/object) and compares actual values for primitives. equals() is a method (inherited from Object, often overridden) meant to compare the logical/content equality of two objects — for example, two different String objects with the same characters. If a class doesn't override equals(), it inherits Object's default implementation, which just does a == reference comparison, so == and equals() behave identically until equals() is overridden.
Example:
String a = new String("hello"); String b = new String("hello"); System.out.println(a == b); // false - different objects in memory System.out.println(a.equals(b)); // true - same content, because String overrides equals()

Question: Why is String immutable in Java?
Answer: String is immutable (its internal character data cannot change after creation) for several important reasons: (1) Security — strings are often used for sensitive data like file paths, network connections, and class names in classloading, so immutability prevents malicious code from changing a string after it's been validated; (2) String pool optimization — since strings can't change, the JVM can safely share single instances of identical string literals across the whole application via the string pool, saving memory; (3) Thread-safety — immutable objects are inherently thread-safe since no thread can modify their state, so multiple threads can share String objects without synchronization; (4) HashMap key reliability — since String is commonly used as a HashMap key, immutability guarantees its hashCode() never changes after insertion, preventing the key from becoming "lost" in the wrong bucket.
Example:
String s = "hello"; s.concat(" world"); // does NOT modify s - concat() returns a NEW String object System.out.println(s); // still prints "hello" s = s.concat(" world"); // must reassign to capture the new String System.out.println(s); // now prints "hello world"

Question: What is the String pool?
Answer: The String pool (also called the intern pool) is a special memory region within the JVM heap (in the Metaspace area since Java 7+, previously PermGen) where the JVM stores unique String literal values to avoid creating duplicate String objects. When you create a string using a literal (e.g., String s = "hello";), the JVM first checks the pool: if an identical string already exists there, it reuses that reference instead of creating a new object; if not, it adds the new literal to the pool. Strings created using "new String(...)" bypass the pool and always create a new object on the heap, though you can manually add them to the pool using the intern() method.
Example:
String s1 = "hello"; // added to string pool (or reused if already present) String s2 = "hello"; // reuses the SAME pooled object as s1 System.out.println(s1 == s2); // true - same reference from the pool String s3 = new String("hello"); // forces a new object on the heap, bypassing the pool System.out.println(s1 == s3); // false - different object

Question: Why should hashCode() be consistent with equals()?
Answer: Java's contract requires that if two objects are equal according to equals(), they MUST return the same hashCode() value (though the reverse isn't required — unequal objects can share a hash code, called a "collision"). This consistency is critical because hash-based collections like HashMap and HashSet use hashCode() to determine which bucket to place/look for an object in, and then use equals() to confirm an exact match within that bucket. If you override equals() without correspondingly overriding hashCode(), two "equal" objects could end up in different buckets, meaning a HashMap/HashSet would fail to recognize them as duplicates or fail to retrieve a value you just inserted.
Example:
class Point { int x, y; public boolean equals(Object o) { if (!(o instanceof Point)) return false; Point p = (Point) o; return x == p.x && y == p.y; } // BUG: if you forget to override hashCode() here consistently with equals(), // two Points with the same x,y could get DIFFERENT default hash codes (based on memory address), // so a HashSet<Point> could store "duplicate" points because they land in different buckets. @Override public int hashCode() { return Objects.hash(x, y); } // must be overridden together with equals() }

Question: How does HashMap work at a high level?
Answer: HashMap stores entries in an array of buckets. For each key, it computes hashCode(), applies an internal spreading/mixing function to reduce clustering, then maps the result to a bucket index using (n-1) & hash where n is the current array capacity (always a power of two). Each bucket holds entries whose keys hashed to that index, structured as a linked list (or a red-black tree if the bucket becomes large, 8+ entries with table size >= 64). Lookups (get) compute the same hash, jump to the bucket, then linearly compare keys with equals() to find the exact entry. The map automatically "resizes" (doubles its capacity and rehashes all entries) once the number of entries exceeds capacity * loadFactor (default load factor 0.75) to keep operations close to O(1) average time.
Example:
Map<String, Integer> ages = new HashMap<>(); ages.put("Tom", 25); // hash("Tom") determines bucket index, entry stored there ages.put("Jerry", 30); // hash("Jerry") likely lands in a different bucket int age = ages.get("Tom"); // recompute hash("Tom"), jump to same bucket, equals() confirms match -> 25

Question: Why can HashMap keys be mutable?
Answer: Technically, Java allows any object to be used as a HashMap key, including mutable objects — there's no compiler restriction. However, doing so is dangerous and considered bad practice: if you mutate a key object's fields AFTER inserting it into the map (in a way that changes its hashCode()), the entry becomes "lost" — the map will look for it in the bucket corresponding to its NEW hash code, but the entry is still physically sitting in the bucket corresponding to its OLD hash code, so get() will fail to find it even though it's still in the map (visible only via full iteration). This is why immutable types (like String, Integer, or custom immutable classes) are strongly recommended as map keys.
Example:
class MutableKey { int id; MutableKey(int id) { this.id = id; } public int hashCode() { return id; } public boolean equals(Object o) { return o instanceof MutableKey && ((MutableKey)o).id == id; } } Map<MutableKey, String> map = new HashMap<>(); MutableKey key = new MutableKey(1); map.put(key, "value"); key.id = 2; // mutated AFTER insertion - hashCode changes! System.out.println(map.get(key)); // likely prints null - the entry is "lost" in the wrong bucket

Question: HashMap vs Hashtable?
Answer: HashMap is not synchronized (not thread-safe) and allows one null key and multiple null values, making it faster for single-threaded use. Hashtable is a legacy class (from Java 1.0) that IS synchronized at the method level (every method like put/get is synchronized), making it thread-safe but slower due to lock contention, and it does not allow null keys or null values (throws NullPointerException). In modern code, Hashtable is essentially obsolete — if you need thread-safety, ConcurrentHashMap is strongly preferred since it offers much better concurrent performance through finer-grained locking.
Example:
Map<String, String> hashMap = new HashMap<>(); hashMap.put(null, "allowed"); // OK - HashMap permits a null key Hashtable<String, String> hashtable = new Hashtable<>(); hashtable.put(null, "value"); // throws NullPointerException

Question: HashMap vs ConcurrentHashMap?
Answer: HashMap is not thread-safe — concurrent modification by multiple threads can corrupt its internal structure or cause a ConcurrentModificationException, and it requires external synchronization (like wrapping with Collections.synchronizedMap()) for safe concurrent use, which serializes ALL access with one lock. ConcurrentHashMap is specifically designed for high-concurrency scenarios: it achieves thread-safety without locking the entire map by using a finer-grained locking strategy (in modern Java, it uses CAS operations and locks only individual bins/buckets during writes), allowing many threads to read and write to different parts of the map simultaneously with minimal contention, while reads are generally lock-free.
Example:
Map<String, Integer> unsafeMap = new HashMap<>(); // Multiple threads calling unsafeMap.put(...) concurrently can corrupt internal state or infinite-loop (older JDKs) ConcurrentHashMap<String, Integer> safeMap = new ConcurrentHashMap<>(); // Multiple threads can safely call safeMap.put(...) concurrently; // internally only the specific bucket being modified is locked, not the whole map. safeMap.compute("counter", (k, v) -> (v == null) ? 1 : v + 1); // atomic update, thread-safe

Question: HashSet vs TreeSet vs LinkedHashSet?
Answer: HashSet is backed by a HashMap internally, offers O(1) average time for add/remove/contains, but provides no guaranteed iteration order. TreeSet is backed by a red-black tree (implements NavigableSet), keeps elements in sorted order (natural ordering or a custom Comparator) at all times, but operations are O(log n) instead of O(1). LinkedHashSet is backed by a HashMap plus a linked list running through all entries, giving O(1) average operations like HashSet while additionally preserving insertion order during iteration — a useful middle ground when you need both fast lookups and predictable iteration order.
Example:
Set<String> hashSet = new HashSet<>(List.of("banana", "apple", "cherry")); System.out.println(hashSet); // order not guaranteed, e.g. [banana, cherry, apple] Set<String> treeSet = new TreeSet<>(List.of("banana", "apple", "cherry")); System.out.println(treeSet); // always sorted: [apple, banana, cherry] Set<String> linkedHashSet = new LinkedHashSet<>(List.of("banana", "apple", "cherry")); System.out.println(linkedHashSet); // preserves insertion order: [banana, apple, cherry]

Question: Comparable vs Comparator?
Answer: Comparable is implemented by the class whose instances you want to compare — it defines a single natural ordering via the compareTo() method, and a class can only implement Comparable once (one natural order). Comparator is a separate object that defines an ordering externally, via the compare() method, allowing you to define multiple different sorting strategies for the same class without modifying the class itself (useful when you don't own the class, or need several different sort orders for different contexts, like sorting Employees by name in one place and by salary in another).
Example:
class Employee implements Comparable<Employee> { String name; double salary; public int compareTo(Employee other) { return this.name.compareTo(other.name); } // natural order: by name } List<Employee> employees = ...; Collections.sort(employees); // uses compareTo() - sorted by name // Comparator - alternate/external ordering, by salary Comparator<Employee> bySalary = (e1, e2) -> Double.compare(e1.salary, e2.salary); employees.sort(bySalary); // sorted by salary instead, without touching the Employee class

Question: What is a lambda expression?
Answer: A lambda expression is a concise, anonymous block of code (essentially an anonymous function) that can be passed around as a value and used to implement a functional interface without the verbosity of an anonymous inner class. Its syntax is (parameters) -> expression_or_block. Lambdas capture variables from their enclosing scope (they can read "effectively final" local variables), and they make functional-style programming (passing behavior as data) much more concise in Java compared to pre-Java-8 anonymous classes.
Example:
// Before Java 8 - verbose anonymous class Runnable oldStyle = new Runnable() { public void run() { System.out.println("Running..."); } }; // Java 8+ - lambda expression, much more concise Runnable newStyle = () -> System.out.println("Running..."); // Lambda with parameters and a block body Comparator<String> byLength = (a, b) -> { return Integer.compare(a.length(), b.length()); };

Question: map() vs filter() vs flatMap() in Streams?
Answer: map() transforms each element in a stream into another value (one-to-one transformation) and returns a new stream of the transformed elements. filter() selects elements that match a given predicate (boolean-returning function), removing elements that don't match, without transforming the remaining ones. flatMap() is used when each element itself produces a stream (or collection) of elements — it "flattens" a stream of streams into a single, flat stream, combining transformation and flattening in one step (useful for nested collections, like a List<List<String>> that you want to process as one flat List<String>).
Example:
List<String> words = List.of("hello", "world"); // map - one-to-one transformation List<Integer> lengths = words.stream().map(String::length).collect(Collectors.toList()); // [5, 5] // filter - selection without transformation List<String> longWords = words.stream().filter(w -> w.length() > 4).collect(Collectors.toList()); // [hello, world] // flatMap - flattening nested structures List<List<Character>> nested = List.of(List.of('a','b'), List.of('c','d')); List<Character> flat = nested.stream().flatMap(List::stream).collect(Collectors.toList()); // [a, b, c, d]

Question: How would you find duplicates in a list using Streams?
Answer: A common technique is to use a Set to track already-seen elements and filter the stream for elements that fail to be newly added to that set (Set.add() returns false if the element was already present) — this identifies duplicates in a single pass. Alternatively, you can use Collectors.groupingBy combined with Collectors.counting() to build a frequency map, then filter entries where the count is greater than 1.
Example:
List<Integer> numbers = List.of(1, 2, 3, 2, 4, 3, 5); Set<Integer> seen = new HashSet<>(); List<Integer> duplicates = numbers.stream() .filter(n -> !seen.add(n)) // add() returns false if n was already in the set - marks it a duplicate .distinct() .collect(Collectors.toList()); System.out.println(duplicates); // [2, 3] // Alternative using groupingBy + counting Map<Integer, Long> counts = numbers.stream() .collect(Collectors.groupingBy(n -> n, Collectors.counting())); List<Integer> dupes2 = counts.entrySet().stream() .filter(e -> e.getValue() > 1) .map(Map.Entry::getKey) .collect(Collectors.toList());

Question: What is Optional and when should it not be used?
Answer: Optional<T> is a container object introduced in Java 8 that may or may not hold a non-null value, designed to make the possibility of "absence of a value" explicit in a method's return type, reducing accidental NullPointerExceptions and forcing callers to consciously handle the absent case (via isPresent(), orElse(), map(), ifPresent(), etc.) rather than silently receiving a null. However, Optional should NOT be used as a field type in a class (it's not Serializable and adds unnecessary wrapping overhead for internal state), should NOT be used as a method parameter type (it complicates the API — better to overload methods or use a default value instead), and should not be used for collections (an empty List is preferable to Optional<List<T>>). Its intended, idiomatic use is specifically as a return type for methods that might not have a result to give back.
Example:
// Good use - as a return type public Optional<User> findUserById(Long id) { User user = database.lookup(id); return Optional.ofNullable(user); // caller must consciously handle the "not found" case } Optional<User> result = findUserById(5L); result.ifPresentOrElse( user -> System.out.println("Found: " + user.getName()), () -> System.out.println("User not found") ); // Bad use - as a class field (avoid this) class User { private Optional<String> middleName; // NOT recommended - use a plain nullable String field instead }

Question: final vs finally vs finalize?
Answer: These three are unrelated keywords/methods despite similar spelling. final is a modifier applied to variables (makes them constants, unreassignable after initialization), methods (prevents overriding in subclasses), or classes (prevents the class from being subclassed at all, like the String class). finally is a block used with try-catch that always executes after the try (and any catch) block completes, whether or not an exception occurred, typically used for cleanup like closing resources (though try-with-resources is now preferred for that specific purpose). finalize() is a method (from Object, now deprecated since Java 9 and removed/discouraged in modern Java) that the garbage collector was supposed to call before reclaiming an object's memory, intended for last-chance cleanup, but its unpredictable timing and performance issues make it obsolete — resource cleanup should use try-with-resources or explicit close() methods instead.
Example:
final int MAX = 100; // final variable - cannot be reassigned class Base { final void show() {} } // final method - cannot be overridden final class Constants {} // final class - cannot be extended try { riskyOperation(); } catch (Exception e) { handleError(e); } finally { System.out.println("This always runs, exception or not"); // finally block }

Question: How does Java garbage collection work at a high level?
Answer: Java's garbage collector automatically reclaims memory occupied by objects that are no longer reachable from any active thread, local variable, static field, or other "GC root" — meaning the program can no longer possibly use them. The most common approach is generational garbage collection: the heap is divided into a Young Generation (where new objects are allocated, further split into Eden and two Survivor spaces) and an Old Generation (for long-lived objects that have survived several collections). Minor GCs happen frequently and quickly in the Young Generation (since most objects die young — the "weak generational hypothesis"), while Major/Full GCs on the Old Generation happen less often but take longer. Objects surviving multiple minor GCs get "promoted" to the Old Generation. Modern collectors like G1 use a mark-and-sweep (or mark-compact) approach within regions to identify and reclaim unreachable objects, and can run mostly concurrently with the application to minimize pause times.
Example:
Object obj = new Object(); // allocated in the Young Generation (Eden space) obj = null; // no more references to the original object - it becomes eligible for garbage collection // On the next minor GC cycle, since nothing reaches this object anymore, its memory is reclaimed.

Question: Stack vs heap?
Answer: The Stack is a region of memory that stores method call frames, including local variables and primitive values, and it's organized as a LIFO (last-in, first-out) structure — each thread has its own stack, and memory is automatically reclaimed as soon as a method returns (its stack frame is popped). The Heap is a shared region of memory (shared across all threads) where all objects (and arrays) are allocated via "new", and objects live there until the garbage collector determines they're no longer reachable and reclaims them — heap memory management is far more complex and slower than stack memory, but necessary because objects often need to outlive the method that created them.
Example:
public void method() { int x = 5; // primitive local variable - stored on the Stack Person p = new Person(); // 'p' (the reference) is on the Stack, but the actual Person OBJECT is on the Heap } // when method() returns, x and the reference p are popped off the stack; // the Person object on the heap becomes eligible for GC only if nothing else references it

Question: What does volatile guarantee?
Answer: The volatile keyword guarantees visibility and ordering, but NOT atomicity, for a variable across multiple threads. Specifically: (1) Visibility — any write to a volatile variable by one thread is immediately visible to all other threads reading it (writes go directly to main memory rather than being cached in a CPU register or a thread-local cache); (2) Ordering — the JVM won't reorder instructions around a volatile read/write (it establishes a "happens-before" relationship), preventing certain subtle reordering bugs in multi-threaded code. However, volatile does NOT make compound operations (like increment, i++) atomic — a race condition can still occur if multiple threads read-modify-write a volatile variable concurrently, because the read and write are still two separate steps.
Example:
class Flag { private volatile boolean running = true; // visibility guaranteed - all threads see updates immediately public void stop() { running = false; } // change visible to other threads right away public void run() { while (running) { /* do work */ } // without volatile, this thread might never see 'running' become false // (it could keep reading a stale cached copy) } } // volatile does NOT fix this - it's not atomic: private volatile int counter = 0; public void increment() { counter++; } // NOT thread-safe even with volatile - read+increment+write is 3 steps

Question: volatile vs synchronized?
Answer: volatile only guarantees visibility and ordering for reads/writes of a single variable — it's lightweight (no locking overhead) but doesn't provide mutual exclusion, so it cannot make compound operations (like i++) atomic. synchronized provides mutual exclusion (only one thread can execute a synchronized block/method on the same lock at a time) AND visibility (changes made inside a synchronized block are guaranteed visible to other threads that later synchronize on the same lock), making it suitable for protecting compound operations and larger critical sections, but at the cost of higher overhead (thread contention, potential for blocking/deadlock). Use volatile for simple flags/status variables where only visibility matters; use synchronized (or higher-level concurrency utilities like AtomicInteger, locks) when you need atomicity for compound operations.
Example:
// volatile - sufficient for a simple flag, no compound operation involved private volatile boolean shutdownRequested = false; // synchronized - needed because increment is a compound (read-modify-write) operation private int count = 0; public synchronized void increment() { count++; } // atomic AND visible, thanks to the lock

Question: What is a race condition?
Answer: A race condition occurs when the correctness of a program depends on the relative timing or interleaving of multiple threads accessing shared mutable state, and different interleavings produce different (and often incorrect) results. It typically happens with compound operations (read-check-write patterns) on shared data that aren't properly synchronized — for example, two threads both reading a shared counter's current value before either writes back the incremented result, causing one increment to be "lost."
Example:
class Counter { private int count = 0; public void increment() { count++; } // NOT atomic: read count, add 1, write count back - 3 separate steps } // If Thread A and Thread B both call increment() at nearly the same time: // Both might read count=5 before either writes back, both write count=6, // resulting in count=6 instead of the correct count=7 - one increment was "lost" due to the race.

Question: What is deadlock and how do you avoid it?
Answer: A deadlock happens when two or more threads each hold a lock the other needs and wait indefinitely for each other, so none can proceed. To avoid deadlock: (1) always acquire multiple locks in a fixed, consistent global order across all threads; (2) use tryLock() with a timeout instead of blocking indefinitely, so a thread can back off and retry if it can't acquire all needed locks; (3) minimize the scope and number of locks held simultaneously; (4) use higher-level concurrency utilities (like java.util.concurrent classes) that are designed to avoid manual lock ordering issues; (5) use lock-free/non-blocking data structures (like Atomic classes) where possible.
Example:
// Avoiding deadlock via consistent lock ordering void transfer(Account from, Account to, double amount) { Account first = from.getId() < to.getId() ? from : to; // always lock lower ID first Account second = from.getId() < to.getId() ? to : from; synchronized (first) { synchronized (second) { from.debit(amount); to.credit(amount); } } } // Because every thread locks accounts in the same consistent order (by ID), // two threads transferring in opposite directions can never deadlock on each other.

Question: ExecutorService vs creating threads manually?
Answer: Manually creating threads (new Thread(...).start()) for every task is inefficient and risky at scale — thread creation has overhead, unbounded thread creation can exhaust system resources, and there's no built-in mechanism for reusing threads, managing task queues, or collecting results. ExecutorService (from java.util.concurrent) provides a managed thread pool abstraction: you submit tasks (Runnable or Callable) to the executor, and it handles scheduling them onto a reusable pool of worker threads, queuing excess tasks when all threads are busy, and provides lifecycle management (shutdown, awaitTermination) and result-handling via Future objects. This is the recommended, production-grade way to manage concurrency in Java rather than manual thread management.
Example:
// Manual - inefficient, no pooling, no result handling built-in for (int i = 0; i < 1000; i++) { new Thread(() -> doWork()).start(); // creates 1000 raw threads - very wasteful } // ExecutorService - managed, reusable thread pool ExecutorService executor = Executors.newFixedThreadPool(10); // only 10 threads handle all 1000 tasks for (int i = 0; i < 1000; i++) { executor.submit(() -> doWork()); } executor.shutdown(); // gracefully stop accepting new tasks, finish queued ones

Question: Future vs CompletableFuture?
Answer: Future represents the result of an asynchronous computation but has limited capabilities — you can only check if it's done (isDone()) or block and wait for the result (get()), with no way to chain further actions, combine multiple futures, or be notified/callback when it completes without blocking. CompletableFuture (Java 8+) is a much richer implementation of Future that supports composing and chaining asynchronous operations declaratively (thenApply, thenCompose, thenCombine), combining multiple futures, adding callbacks for completion/exception (whenComplete, exceptionally) without blocking, and manually completing a future from outside. It essentially brings a full functional, non-blocking asynchronous programming model to Java.
Example:
// Future - can only block and wait, no chaining ExecutorService executor = Executors.newSingleThreadExecutor(); Future<Integer> future = executor.submit(() -> computeValue()); int result = future.get(); // blocks the calling thread until done // CompletableFuture - can chain non-blocking operations CompletableFuture<Integer> cf = CompletableFuture.supplyAsync(() -> computeValue()) .thenApply(value -> value * 2) // transform the result once ready .thenApply(value -> value + 10); // chain another transformation cf.thenAccept(result -> System.out.println("Final result: " + result)); // callback, non-blocking

Question: How would you make a Singleton thread-safe?
Answer: Options include: synchronizing the entire getInstance() method (simple but slower due to lock contention on every call); double-checked locking with a volatile instance field (checks null twice, only synchronizing on the first-ever creation, avoiding lock overhead on subsequent calls); the "Initialization-on-demand holder" idiom (using a static nested class that the JVM guarantees is loaded lazily and thread-safely only when first accessed); or simply declaring the singleton as an enum with one constant, which the JVM inherently guarantees is instantiated exactly once, thread-safely, even handling serialization correctly.
Example:
// Initialization-on-demand holder idiom - lazy, thread-safe, no explicit synchronization needed public class ConfigManager { private ConfigManager() {} private static class Holder { private static final ConfigManager INSTANCE = new ConfigManager(); // loaded only when Holder is first accessed } public static ConfigManager getInstance() { return Holder.INSTANCE; // JVM class-loading guarantees are thread-safe by specification } }

Question: What is class loading?
Answer: Class loading is the JVM process of finding bytecode and creating the runtime Class representation needed to use a type. The JVM specification describes loading, linking, and initialization; linking includes verification and preparation, with resolution performed as needed. Modern JDK terminology uses the bootstrap, platform, and application/system class loaders; "extension class loader" is older terminology from pre-Java 9 releases. The parent-delegation model normally asks a parent loader to load a class before the child tries, which helps keep core platform classes from being replaced by application classes with the same name.
Example:
public class MyApp { static int counter = 10; // initialized during the Initialization phase of class loading public static void main(String[] args) { System.out.println(counter); // by the time main() runs, MyApp's class loading is fully complete } } // You can inspect the loader: System.out.println(MyApp.class.getClassLoader()); // typically prints something like "jdk.internal.loader.ClassLoaders$AppClassLoader"

Question: What is the JIT compiler?
Answer: The Just-In-Time (JIT) compiler is a component of the JVM that improves runtime performance by compiling frequently executed bytecode ("hot" methods/loops) into optimized native machine code on the fly, rather than continuing to interpret bytecode line-by-line every single time. The JVM initially runs bytecode through an interpreter for quick startup, but profiles execution to detect "hot spots" (hence "HotSpot" JVM), and then invokes the JIT compiler to compile those hot methods into native code, applying advanced optimizations like inlining, loop unrolling, and dead code elimination that aren't possible with pure interpretation. This gives Java the fast startup of an interpreted language combined with near-native performance for long-running, CPU-intensive code paths.
Example:
// A method called millions of times in a loop for (int i = 0; i < 10_000_000; i++) { result += compute(i); // after the JVM detects this is a "hot" method, // the JIT compiles compute() into optimized native machine code, // making later iterations run much faster than the initial interpreted execution }

Question: How would you investigate an OutOfMemoryError?
Answer: The investigation approach: (1) Capture a heap dump at (or just before) the crash, either automatically via the JVM flag -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path, or manually using jmap; (2) Analyze the heap dump with a tool like Eclipse MAT (Memory Analyzer Tool) or VisualVM, looking at the "dominator tree" or "leak suspects report" to identify which objects are consuming the most retained memory and what's holding references to them (preventing garbage collection); (3) Check for common leak patterns: static collections that grow unbounded, unclosed resources (listeners, streams, connections not released), caches without eviction policies, or ThreadLocal variables not cleaned up in thread-pooled environments; (4) Review GC logs (enabled via -Xlog:gc) to see if the heap is genuinely growing over time (a leak) versus just needing a larger heap size (-Xmx) for legitimate memory needs; (5) Reproduce under load in a controlled environment with monitoring enabled to correlate the growth with specific application actions.
Example:
# JVM flags to auto-capture a heap dump on OOM java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps/app.hprof -jar app.jar // After loading app.hprof into Eclipse MAT, you might discover: // "com.example.CacheManager" holds a HashMap with 2 million entries that's never evicted, // consuming 1.2 GB of retained heap - the root cause of the OutOfMemoryError.
Question: What is JDBC and what are the normal steps to execute a query?
Answer: JDBC (Java Database Connectivity) is a standard Java API that provides a vendor-neutral way to connect to and interact with relational databases using SQL. The normal steps are: (1) Load the database driver (mostly automatic in modern JDBC via ServiceLoader, previously required Class.forName()); (2) Establish a Connection using DriverManager.getConnection(url, user, password); (3) Create a Statement or PreparedStatement from the connection; (4) Execute the query (executeQuery() for SELECT, executeUpdate() for INSERT/UPDATE/DELETE); (5) Process the ResultSet if applicable, iterating with next() and extracting column values; (6) Close all resources (ResultSet, Statement, Connection) in reverse order, ideally using try-with-resources to guarantee cleanup even on exceptions.
Example:
String sql = "SELECT name, salary FROM employees WHERE id = ?"; try (Connection conn = DriverManager.getConnection(url, user, password); PreparedStatement ps = conn.prepareStatement(sql)) { ps.setInt(1, 101); try (ResultSet rs = ps.executeQuery()) { while (rs.next()) { System.out.println(rs.getString("name") + ": " + rs.getDouble("salary")); } } } // all resources auto-closed here

Question: Statement vs PreparedStatement?
Answer: Statement executes a static SQL string as-is every time — it must be re-parsed and re-compiled by the database on every execution, and it's vulnerable to SQL injection if you build queries by concatenating user input directly into the SQL string. PreparedStatement is precompiled with placeholders (?) for parameters, which the database can cache and reuse the execution plan for across multiple calls (better performance for repeated queries), and crucially, it safely binds parameter values separately from the SQL structure, so user input can never be interpreted as SQL code — eliminating SQL injection risk for those parameters.
Example:
// Statement - vulnerable to SQL injection, string concatenation String userInput = "101 OR 1=1"; // malicious input Statement stmt = conn.createStatement(); ResultSet rs = stmt.executeQuery("SELECT * FROM employees WHERE id = " + userInput); // DANGEROUS // PreparedStatement - safe, parameterized PreparedStatement ps = conn.prepareStatement("SELECT * FROM employees WHERE id = ?"); ps.setString(1, userInput); // treated strictly as a literal value, not executable SQL - safe

Question: How does PreparedStatement help against SQL injection?
Answer: PreparedStatement separates the SQL command structure from the data values. The SQL query template (with ? placeholders) is sent to and compiled by the database first, and parameter values are bound afterward through typed setter methods (setString, setInt, etc.) — the database driver ensures these values are always treated purely as literal data, never as executable SQL syntax, no matter what characters they contain (like quotes or semicolons). This structurally prevents an attacker from injecting SQL commands through user input, unlike string concatenation, where malicious input could alter the query's logic entirely.
Example:
// Vulnerable: string concatenation lets an attacker inject SQL String query = "SELECT * FROM users WHERE username = '" + userInput + "'"; // If userInput = "' OR '1'='1", the final query becomes: // SELECT * FROM users WHERE username = '' OR '1'='1' -- returns ALL users, bypassing the filter! // Safe: PreparedStatement PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE username = ?"); ps.setString(1, userInput); // even "' OR '1'='1" is treated as a literal string value to match against, not SQL logic

Question: What is connection pooling?
Answer: Connection pooling is a technique where a set of pre-established, reusable database connections is maintained in a "pool" so that application code borrows a connection from the pool when needed and returns it when done, instead of opening a brand-new physical connection for every database operation and closing it afterward. Establishing a raw database connection is relatively expensive (TCP handshake, authentication, session setup), so reusing existing connections dramatically improves performance and reduces resource strain on the database server, especially under high concurrency.
Example:
// Without pooling - expensive, creates a new physical connection every time Connection conn = DriverManager.getConnection(url, user, pass); // slow, repeated for every request // ... use and close // With pooling (e.g. HikariCP) - reuses existing connections from a managed pool HikariDataSource dataSource = new HikariDataSource(hikariConfig); try (Connection conn = dataSource.getConnection()) { // borrowed instantly from the pool, no new TCP handshake // ... use connection } // returned to the pool here, not physically closed

Question: What is HikariCP used for?
Answer: HikariCP is a high-performance JDBC connection pooling library, widely regarded as the fastest and most lightweight connection pool for Java, and it's the default connection pool used by Spring Boot when you include the JDBC or JPA starter. It manages a pool of reusable database connections with careful attention to minimizing overhead (using techniques like bytecode-level optimizations and avoiding unnecessary synchronization), and exposes configuration options for pool size, connection timeout, idle timeout, and maximum connection lifetime to tune it for a given workload.
Example:
# application.properties - HikariCP is auto-configured by Spring Boot spring.datasource.hikari.maximum-pool-size=20 spring.datasource.hikari.minimum-idle=5 spring.datasource.hikari.connection-timeout=20000 spring.datasource.hikari.pool-name=MyAppHikariPool // Spring Boot automatically wires this into every DataSource-consuming bean (JdbcTemplate, JPA, etc.)

Question: What is the Servlet lifecycle?
Answer: A Servlet's lifecycle is managed by the Servlet container (like Tomcat) and consists of three main phases: (1) init() — called exactly once when the servlet is first loaded into memory (either at container startup or on first request), used for one-time setup like initializing resources; (2) service() — called for every incoming request, and internally it dispatches to doGet(), doPost(), doPut(), doDelete(), etc. based on the HTTP method, handling the actual request/response logic; (3) destroy() — called exactly once when the servlet is being taken out of service (container shutdown or servlet unloading), used for cleanup like releasing resources. A single servlet instance is typically reused across many requests/threads, which is why servlets should generally be stateless or carefully synchronized if they hold instance state.
Example:
public class MyServlet extends HttpServlet { @Override public void init() { System.out.println("Servlet initialized - runs once"); } @Override protected void doGet(HttpServletRequest req, HttpServletResponse resp) { // runs on every GET request, potentially from multiple threads concurrently } @Override public void destroy() { System.out.println("Servlet destroyed - runs once at shutdown"); } }

Question: How does HTTP session management work?
Answer: Since HTTP is inherently stateless (each request is independent, with no memory of previous requests), sessions provide a way to maintain state across multiple requests from the same client. When a client first interacts with a server, the server creates a session object (identified by a unique Session ID) and sends this ID back to the client, typically stored as a cookie (JSESSIONID in Java web apps) or, if cookies are disabled, appended to URLs (URL rewriting). On subsequent requests, the client automatically sends this session ID back, and the server uses it to look up and retrieve the associated session data (stored server-side, e.g., in memory, a database, or a distributed cache like Redis for scalability across multiple server instances). Sessions typically expire after a period of inactivity (timeout) or can be explicitly invalidated (e.g., on logout).
Example:
// Server-side, storing data in a session (Java Servlet API) HttpSession session = request.getSession(); // creates one if it doesn't exist session.setAttribute("username", "alice"); // On a later request, retrieving it HttpSession session = request.getSession(false); // false = don't create a new one if absent String username = (String) session.getAttribute("username"); // "alice" // Behind the scenes, the browser sent a "Cookie: JSESSIONID=ABC123..." header // that the server used to find this exact session object.

Question: What is dependency injection in Spring?
Answer: In Spring specifically, dependency injection is implemented via the IoC container (ApplicationContext), which reads bean definitions (from annotations like @Component/@Service/@Repository, or explicit @Bean methods in @Configuration classes) and automatically wires dependencies between beans — resolving which implementation to inject based on type (and qualifiers/names when multiple candidates exist) — via constructor injection, setter injection, or field injection using @Autowired.
Example:
@Repository class UserRepository { /* data access logic */ } @Service class UserService { private final UserRepository userRepository; @Autowired // Spring resolves and injects the UserRepository bean automatically public UserService(UserRepository userRepository) { this.userRepository = userRepository; } }

Question: Why is constructor injection generally preferred?
Answer: Constructor injection is preferred because: (1) it makes dependencies explicit and mandatory — you cannot create the object without supplying all required dependencies, preventing incomplete/invalid object states; (2) it allows fields to be declared "final", enforcing immutability and thread-safety; (3) it makes unit testing straightforward — you can instantiate the class directly with mock dependencies via the constructor, without needing a Spring container or reflection; (4) it clearly surfaces a class's dependencies in one place (the constructor signature), making the code easier to read and reason about — if a class needs too many constructor parameters, it's an early warning sign the class may be violating the single responsibility principle; (5) Spring's own documentation explicitly recommends it as the default approach, reserving setter injection for genuinely optional dependencies.
Example:
@Service public class OrderService { private final PaymentGateway paymentGateway; // final - guaranteed set once, immutable private final InventoryService inventoryService; public OrderService(PaymentGateway paymentGateway, InventoryService inventoryService) { this.paymentGateway = paymentGateway; this.inventoryService = inventoryService; } } // Easy to unit test without Spring: OrderService service = new OrderService(new MockPaymentGateway(), new MockInventoryService());

Question: What does @SpringBootApplication combine?
Answer: It combines @Configuration, @EnableAutoConfiguration, and @ComponentScan into a single convenience annotation, typically applied to the main class that bootstraps a Spring Boot application.
Example:
@SpringBootApplication public class Application { public static void main(String[] args) { SpringApplication.run(Application.class, args); } }

Question: How does Spring Boot auto-configuration work?
Answer: Spring Boot's auto-configuration mechanism automatically configures beans based on what's present on the application's classpath and any existing bean definitions, dramatically reducing manual configuration. It works via classes annotated with @Configuration and @Conditional-family annotations (like @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty) listed in a special metadata file (in modern Spring Boot, META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports). At startup, Spring Boot evaluates each of these conditional configuration classes: for example, if it detects the H2 database driver on the classpath and no DataSource bean already manually defined, it auto-configures an embedded H2 DataSource bean for you. This "convention over configuration" approach means adding a dependency (like spring-boot-starter-data-jpa) can automatically wire up an EntityManagerFactory, TransactionManager, and more, with sensible defaults you can still override.
Example:
// If spring-boot-starter-web is on the classpath, Spring Boot's auto-configuration // automatically registers a DispatcherServlet, an embedded Tomcat server, and Jackson JSON converters // without you writing any explicit configuration for them. @ConditionalOnMissingBean(DataSource.class) // simplified illustration of how autoconfig conditions work @Bean public DataSource embeddedDataSource() { return new EmbeddedDatabaseBuilder().setType(EmbeddedDatabaseType.H2).build(); } // This bean is only created if YOU haven't already defined your own DataSource bean.

Question: @Component vs @Service vs @Repository?
Answer: All three are specializations of the same underlying @Component "stereotype" annotation, and functionally, Spring treats them identically for the purpose of component scanning and bean registration — the distinction is primarily semantic/organizational, indicating a class's role in the application's architecture, though @Repository does add one extra piece of real behavior: it enables automatic translation of persistence-related exceptions (like SQLException subtypes) into Spring's unchecked DataAccessException hierarchy. @Component is the generic base annotation for any Spring-managed bean. @Service marks a class as containing business logic (the service layer). @Repository marks a class responsible for data access (the DAO/repository layer).
Example:
@Component class EmailValidator { /* generic reusable utility, not tied to a specific layer */ } @Service class OrderService { /* business logic layer */ } @Repository class OrderRepository { /* data access layer - gets automatic exception translation */ // A raw SQLException thrown here gets wrapped into a Spring DataAccessException automatically }

Question: @RequestParam vs @PathVariable?
Answer: @PathVariable extracts values embedded directly within the URI path itself, based on a URI template pattern (e.g., /users/{id} where {id} is a path variable) — used for identifying a specific resource. @RequestParam extracts values from the query string (e.g., ?active=true&page=2) or form data, typically used for optional filters, pagination parameters, or search criteria, and supports default values and marking parameters as optional.
Example:
@GetMapping("/users/{id}") // {id} is a path variable - identifies a specific resource public User getUser(@PathVariable Long id) { ... } // Matches: GET /users/42 @GetMapping("/users") // query parameters filter/modify the request, not identify a specific resource public List<User> searchUsers(@RequestParam(defaultValue = "true") boolean active, @RequestParam(required = false) String name) { ... } // Matches: GET /users?active=false&name=john

Question: @ConfigurationProperties vs @Value?
Answer: @Value is used to inject a single configuration property (from application.properties/yml, environment variables, or system properties) into a single field, using SpEL-like syntax (${property.name}) — it's simple but becomes cumbersome and error-prone when you have many related properties to inject (repetitive, no type-safety across a group, no built-in validation). @ConfigurationProperties binds an entire group of related, hierarchical properties (with a common prefix) into a single strongly-typed Java class (a POJO) all at once, supporting nested objects, lists, and maps, and integrates well with Bean Validation (@Validated) for validating configuration at startup — making it the better choice for anything beyond a couple of standalone values.
Example:
# application.properties app.mail.host=smtp.example.com app.mail.port=587 app.mail.from-address=noreply@example.com // @Value - injecting one property at a time (repetitive for multiple related properties) @Value("${app.mail.host}") private String mailHost; // @ConfigurationProperties - binds the whole group into one typed object @ConfigurationProperties(prefix = "app.mail") @Component public class MailProperties { private String host; private int port; private String fromAddress; // getters and setters - Spring binds all three properties automatically }

Question: What are Spring profiles?
Answer: Spring profiles allow you to define different sets of beans and configuration values for different environments (like "dev", "test", "staging", "prod") within the same codebase, and activate only the relevant profile at runtime. Beans can be tagged with @Profile("dev") to indicate they should only be created when that profile is active, and property files can be environment-specific (application-dev.properties, application-prod.properties), automatically layered on top of the base application.properties. This avoids hardcoding environment-specific values or duplicating configuration classes for each environment.
Example:
@Configuration @Profile("dev") public class DevConfig { @Bean public DataSource dataSource() { return embeddedH2DataSource(); } // fast local dev database } @Configuration @Profile("prod") public class ProdConfig { @Bean public DataSource dataSource() { return realPostgresDataSource(); } // production database } # Activating a profile java -jar app.jar --spring.profiles.active=prod

Question: Why might @Transactional appear not to work?
Answer: @Transactional relies on Spring's proxy-based AOP mechanism, so it silently fails to apply in several common scenarios: (1) Self-invocation — calling an @Transactional method from another method WITHIN the same class (this.someTransactionalMethod()) bypasses the proxy entirely, since the call doesn't go through the Spring-managed proxy object; (2) the method is private (proxies can only intercept public method calls, since the proxy needs to override/wrap the method); (3) the exception thrown is a checked exception without configuring rollbackFor (by default only unchecked/RuntimeExceptions trigger rollback); (4) the class isn't a Spring-managed bean at all (e.g., you instantiated it manually with "new" instead of letting Spring inject it); (5) using CGLIB proxies on a final class or final method, which can't be proxied/overridden.
Example:
@Service public class OrderService { public void placeOrder(Order order) { this.saveOrder(order); // BUG: self-invocation bypasses the proxy - @Transactional below won't apply! } @Transactional public void saveOrder(Order order) { orderRepo.save(order); } } // Fix: inject OrderService into itself (via a separate bean/interface) or restructure // so the transactional method is called from a DIFFERENT bean, going through the proxy.

Question: What is Spring AOP?
Answer: Spring AOP (Aspect-Oriented Programming) allows you to modularize cross-cutting concerns — behavior that applies across many parts of an application, like logging, transaction management, security checks, or caching — into separate reusable units called "aspects," instead of scattering that logic throughout every business method. Key concepts: an Aspect (a module containing cross-cutting logic), Advice (the action taken — @Before, @After, @Around, etc.), a Pointcut (an expression defining WHERE the advice should apply, e.g., "all methods in the service package"), and a Join Point (a specific point during execution, like a method call, where advice can be applied). Spring implements AOP using proxies (either JDK dynamic proxies for interface-based beans, or CGLIB proxies for concrete classes).
Example:
@Aspect @Component public class LoggingAspect { @Around("execution(* com.example.service.*.*(..))") // pointcut: all methods in the service package public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable { long start = System.currentTimeMillis(); Object result = joinPoint.proceed(); // actually invoke the real method long duration = System.currentTimeMillis() - start; System.out.println(joinPoint.getSignature() + " executed in " + duration + "ms"); return result; } } // This single aspect automatically logs execution time for EVERY method in every service class, // without adding any logging code inside those service classes themselves.

Question: JDK proxy vs CGLIB proxy?
Answer: Both are mechanisms Spring uses under the hood to create proxy objects for AOP and @Transactional support. A JDK dynamic proxy is created using Java's built-in java.lang.reflect.Proxy and can only proxy classes that implement at least one interface — the proxy implements the same interface(s) and delegates calls to the real object, adding advice around them. A CGLIB proxy is used when the target class does NOT implement any interface — CGLIB works by generating a subclass of the target class at runtime (bytecode manipulation), overriding its methods to insert the AOP advice, which is why CGLIB proxies cannot work on "final" classes or "final" methods (which can't be overridden/subclassed). Spring Boot defaults to using CGLIB proxies for all beans (even ones with interfaces) since Spring Boot 2.0 for consistency, unless configured otherwise.
Example:
// JDK dynamic proxy - requires an interface interface PaymentService { void pay(double amount); } class PaymentServiceImpl implements PaymentService { public void pay(double amount) {...} } // Spring can create a JDK proxy implementing PaymentService // CGLIB proxy - works even without an interface, by subclassing class ReportGenerator { public void generate() {...} } // no interface // Spring creates a CGLIB proxy that is a runtime-generated SUBCLASS of ReportGenerator // NOTE: if generate() were declared 'final', CGLIB could NOT override/proxy it - AOP advice would silently not apply

Question: What is Spring Security?
Answer: Spring Security is a comprehensive framework for handling authentication (verifying who a user is) and authorization (determining what an authenticated user is allowed to do) in Spring applications. It's built around a chain of Servlet Filters that intercept every incoming request before it reaches your controllers, checking credentials, validating tokens (JWT, OAuth2), enforcing access rules, and protecting against common web vulnerabilities (CSRF, session fixation, clickjacking) out of the box. It supports numerous authentication mechanisms (form login, HTTP Basic, OAuth2/OIDC, JWT, LDAP) and fine-grained authorization via role-based (hasRole) or expression-based (@PreAuthorize with SpEL) access control at the URL or method level.
Example:
@Configuration @EnableWebSecurity public class SecurityConfig { @Bean public SecurityFilterChain filterChain(HttpSecurity http) throws Exception { http.authorizeHttpRequests(auth -> auth .requestMatchers("/api/public/**").permitAll() // no auth needed .requestMatchers("/api/admin/**").hasRole("ADMIN") // requires ADMIN role .anyRequest().authenticated()) // everything else needs login .oauth2ResourceServer(oauth -> oauth.jwt()); // validates incoming JWTs automatically return http.build(); } }

Question: How does JWT-based authentication work?
Answer: In summary: the server issues a signed, self-contained token after successful login, containing the user's identity and claims; the client sends this token with every subsequent request (typically in the Authorization: Bearer header); the server verifies the token's signature and expiration on each request without needing to consult a server-side session store, making JWT authentication inherently stateless and horizontally scalable.
Example:
// Spring Security automatically validates and parses incoming JWTs on protected endpoints, // exposing the authenticated user's identity via SecurityContextHolder.getContext().getAuthentication() // once the OAuth2 resource server / JWT filter has verified the token.

Question: What is JPA?
Answer: JPA (Java Persistence API) is a specification (not an implementation) that defines a standard set of interfaces and annotations for object-relational mapping in Java — how Java objects (entities) map to database tables, how relationships between entities are defined, and how queries are written (via JPQL, an object-oriented query language similar to SQL). Being a specification, JPA itself doesn't do any actual work; it needs a concrete implementation (a "JPA provider") to function — the most popular implementation is Hibernate, though EclipseLink and OpenJPA also exist. Coding against the JPA interfaces (rather than Hibernate-specific APIs directly) makes your persistence code more portable across different JPA providers.
Example:
// This code uses only standard JPA annotations/interfaces - not Hibernate-specific classes @Entity public class Product { @Id @GeneratedValue private Long id; private String name; } // EntityManager is the standard JPA interface for persistence operations (implemented internally by Hibernate) EntityManager em = entityManagerFactory.createEntityManager(); Product p = em.find(Product.class, 1L);

Question: JPA vs Hibernate?
Answer: JPA is the specification/standard (a set of interfaces and rules defined by Jakarta EE, formerly Java EE) describing HOW object-relational mapping should work in Java, without providing any actual implementation. Hibernate is a concrete implementation (a "JPA provider") of that specification — it's the actual library that does the real work of generating SQL, managing sessions, caching, and so on. You can think of JPA as an interface/contract and Hibernate as one of several classes that implement that contract. Hibernate also offers additional features beyond the JPA specification (like its own native Criteria API, custom annotations, and specific caching strategies), so if you use Hibernate-specific features directly, your code becomes tied to Hibernate rather than being portable to other JPA providers.
Example:
// Pure JPA - portable across any provider (Hibernate, EclipseLink, etc.) @PersistenceContext private EntityManager entityManager; // standard JPA interface // Hibernate-specific - ties your code to Hibernate specifically Session session = entityManager.unwrap(Session.class); // Hibernate's native Session API session.saveOrUpdate(product); // a Hibernate-specific method, not part of the JPA spec

Question: What is an entity lifecycle?
Answer: In JPA/Hibernate, every entity object passes through defined lifecycle states: Transient — a newly created object (via "new") that isn't yet associated with any persistence context/session and has no corresponding database row; Persistent (Managed) — the object is associated with an active persistence context (session), and any changes to it are tracked and automatically synchronized to the database (dirty checking) when the transaction commits or the session flushes; Detached — the object was previously persistent, but its persistence context/session has since been closed, so changes to it are no longer automatically tracked (though it can be reattached via merge()); Removed — the object has been marked for deletion (via remove()/delete()), and its corresponding database row will be deleted upon transaction commit.
Example:
Product p = new Product("Laptop", 999.99); // Transient - not yet known to Hibernate em.persist(p); // now Persistent/Managed - tracked by the persistence context p.setPrice(899.99); // automatically detected by dirty checking, will be saved on commit, no explicit save() call needed em.detach(p); // now Detached - changes no longer tracked p.setPrice(799.99); // this change is silently ignored by Hibernate unless you call merge() Product managedAgain = em.merge(p); // re-attaches a copy, now Persistent again, changes will be saved

Question: LAZY vs EAGER fetching?
Answer: These are fetching strategies that control WHEN related/associated entities are loaded from the database relative to the owning entity. LAZY fetching defers loading the associated entity/collection until it's actually accessed in code (e.g., calling a getter for the first time triggers an additional query) — this improves initial query performance by avoiding unnecessary data loading, but can cause a LazyInitializationException if accessed after the session/persistence context has closed. EAGER fetching loads the associated entity/collection immediately, as part of the initial query (often via a JOIN), guaranteeing the data is always available even outside the original session, but at the cost of potentially loading much more data than needed, especially for large collections, and contributing to over-fetching or the N+1 problem if not managed carefully. JPA defaults: @ManyToOne and @OneToOne are EAGER by default; @OneToMany and @ManyToMany are LAZY by default.
Example:
@Entity class Department { @OneToMany(mappedBy = "department", fetch = FetchType.LAZY) // default for collections private List<Employee> employees; // not loaded from DB until .getEmployees() is actually called @ManyToOne(fetch = FetchType.EAGER) // default for single associations private Company company; // loaded immediately along with the Department itself }

Question: What causes LazyInitializationException?
Answer: This exception occurs when code tries to access a lazily-loaded association or collection AFTER the Hibernate Session (persistence context) that originally loaded the parent entity has already been closed. Since lazy loading works by fetching the associated data on-demand via an additional query, and that query needs an active session/connection to execute, trying to trigger this lazy load when there's no active session anymore fails. This commonly happens when an entity is loaded inside a @Transactional service method, returned to a controller, and the lazy collection is accessed later in the view layer or after the transaction (and thus the session) has already closed.
Example:
@Transactional public Department getDepartment(Long id) { return departmentRepo.findById(id).get(); // session is open here, entity is loaded but employees not yet fetched } // transaction/session closes here when the method returns // Later, outside the transaction (e.g., in a controller or view template): Department dept = departmentService.getDepartment(1L); dept.getEmployees().size(); // BOOM - LazyInitializationException, no active session to fetch employees now // Fixes: use JOIN FETCH in the original query, use an @EntityGraph, // convert to a DTO within the transactional method, or use FetchType.EAGER (carefully).

Question: What is the N+1 query problem?
Answer: The N+1 problem occurs when fetching a list of N parent entities triggers exactly 1 initial query for the parents, followed by N additional queries — one per parent — to lazily fetch each parent's related child collection/association, instead of a single efficient query. This is a very common and serious performance issue in ORM-based applications, especially as N grows large (100 parents = 101 total queries instead of ideally 1 or 2).
Example:
List<Department> departments = departmentRepo.findAll(); // Query 1: fetch all departments for (Department d : departments) { System.out.println(d.getEmployees().size()); // triggers 1 SEPARATE query PER department (lazy loading) } // For 50 departments, this results in 1 + 50 = 51 total queries instead of 1 efficient joined query.

Question: How would you diagnose and fix N+1 queries?
Answer: Diagnosis: enable SQL logging (spring.jpa.show-sql=true, or better, use a tool like p6spy or Hibernate statistics/datasource-proxy to count actual queries executed per request) and watch for a suspicious pattern of one query followed by many nearly-identical queries differing only by an ID parameter. Fixes: (1) Use JOIN FETCH in a JPQL/HQL query to eagerly load the association in the SAME query as the parent; (2) Use @EntityGraph to declaratively specify which associations to fetch eagerly for a specific query method, without changing the entity's default fetch type globally; (3) Use batch fetching (@BatchSize annotation or hibernate.default_batch_fetch_size) so that instead of N individual queries, Hibernate groups them into fewer queries using an IN clause; (4) For read-heavy/reporting scenarios, consider projecting directly to DTOs with a single custom query instead of loading full entity graphs at all.
Example:
// Diagnosis - enabling SQL logging reveals the repeated query pattern spring.jpa.show-sql=true spring.jpa.properties.hibernate.generate_statistics=true // Fix 1: JOIN FETCH @Query("SELECT d FROM Department d JOIN FETCH d.employees") List<Department> findAllWithEmployees(); // single query using a SQL JOIN instead of N+1 // Fix 2: @EntityGraph @EntityGraph(attributePaths = {"employees"}) List<Department> findAll(); // Spring Data JPA fetches employees eagerly just for this method

Question: First-level vs second-level Hibernate cache?
Answer: First-level cache is enabled by default, scoped to a single Session, and caches entities by their identifier for the duration of that session — you get it for free with no configuration. Second-level cache is optional, application/SessionFactory-wide (shared across all sessions), requires an external cache provider (Ehcache, Redis, Caffeine, Infinispan), and is best used for reference/lookup data that's read often but rarely modified.
Example:
// First-level (automatic, per-session) Employee e1 = session.get(Employee.class, 1L); // hits DB Employee e2 = session.get(Employee.class, 1L); // same session - returns cached instance, no DB hit // Second-level (requires setup) - shared across ALL sessions/application-wide @Cacheable @org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_ONLY) class Country { @Id Long id; String name; } // e.g., a static list of countries - great L2 cache candidate

Question: What are cascade types in JPA?
Answer: Cascade types define how operations performed on a parent entity should automatically "cascade" (propagate) to its related/associated entities, so you don't have to manually persist, update, or delete each related entity separately. The main cascade types are: PERSIST (saving the parent also saves new related entities), MERGE (updating/merging the parent also merges related entities), REMOVE (deleting the parent also deletes related entities), REFRESH (refreshing the parent also refreshes related entities from the DB), DETACH (detaching the parent also detaches related entities), and ALL (applies all of the above). Choosing cascade types carefully matters — for example, cascading REMOVE on a shared/reference entity (like cascading delete from Order down to a shared Product) could unintentionally delete data still needed elsewhere.
Example:
@Entity class Order { @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true) private List<OrderItem> items; // saving/deleting an Order automatically saves/deletes its OrderItems too } Order order = new Order(); order.getItems().add(new OrderItem("Widget", 2)); entityManager.persist(order); // CascadeType.PERSIST automatically also persists the new OrderItem - no separate save needed

Question: What does orphanRemoval do?
Answer: orphanRemoval = true, set on a @OneToMany or @OneToOne relationship, tells JPA/Hibernate to automatically delete a child entity from the database when it's removed from its parent's collection (or the reference is set to null) — even if you never explicitly call remove()/delete() on that child directly. This is useful for true parent-child "ownership" relationships, where a child entity has no meaningful existence independent of its parent (like OrderItems belonging exclusively to one Order) — removing it from the parent's list should mean it's genuinely deleted, not just "unlinked."
Example:
@Entity class Order { @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true) private List<OrderItem> items; } Order order = orderRepository.findById(1L).get(); order.getItems().remove(0); // simply removing from the in-memory list... // ...causes Hibernate to automatically DELETE that specific OrderItem row from the database on flush/commit, // because orphanRemoval=true - no explicit orderItemRepository.delete(item) call needed.

Question: JPQL vs native SQL?
Answer: JPQL (Java Persistence Query Language) is an object-oriented query language defined by the JPA specification — it queries against entity names and their fields (not table/column names directly), making it database-portable across different underlying databases (since JPA translates JPQL into the appropriate SQL dialect automatically) and letting you navigate entity relationships directly in the query. Native SQL is actual, raw SQL specific to your database engine, used via @Query(nativeQuery = true) or entityManager.createNativeQuery() — you'd use it when you need database-specific features JPQL doesn't support (like specific functions, complex window functions, or vendor-specific optimizer hints), at the cost of losing database portability.
Example:
// JPQL - queries the Employee ENTITY and its fields, portable across databases @Query("SELECT e FROM Employee e WHERE e.department.name = :deptName") List<Employee> findByDepartmentName(@Param("deptName") String deptName); // Native SQL - queries actual TABLE and COLUMN names, database-specific @Query(value = "SELECT * FROM employees e WHERE e.dept_name = :deptName", nativeQuery = true) List<Employee> findByDepartmentNameNative(@Param("deptName") String deptName);

Question: What is a derived query method in Spring Data JPA?
Answer: A derived query method lets you define a repository query simply by following a naming convention in the method signature — Spring Data JPA parses the method name, extracts the property names and keywords (like findBy, And, Or, GreaterThan, OrderBy), and automatically generates the corresponding JPQL/SQL query at runtime, without you writing any query code at all. This works well for simple to moderately complex queries; for more complex logic, you'd fall back to @Query with JPQL or native SQL, or the Criteria API/Specifications.
Example:
public interface EmployeeRepository extends JpaRepository<Employee, Long> { List<Employee> findByLastNameAndDepartment(String lastName, String department); // Spring Data JPA automatically generates: // SELECT e FROM Employee e WHERE e.lastName = ?1 AND e.department = ?2 List<Employee> findBySalaryGreaterThanOrderBySalaryDesc(double minSalary); // Generates: SELECT e FROM Employee e WHERE e.salary > ?1 ORDER BY e.salary DESC }

Question: How do Pageable and Sort work?
Answer: Pageable is a Spring Data interface representing pagination information (page number, page size, and optionally sort order) that you pass into a repository method; Spring Data JPA translates it into the appropriate LIMIT/OFFSET SQL clauses under the hood and returns a Page<T> object, which includes not just the data for that page but also metadata like total elements and total pages, useful for building paginated UIs. Sort is a related class specifying ordering criteria (which fields, ascending/descending) that can be used standalone or combined with a Pageable (via PageRequest.of(page, size, sort)).
Example:
public interface ProductRepository extends JpaRepository<Product, Long> { Page<Product> findByCategory(String category, Pageable pageable); } // Usage: Pageable pageable = PageRequest.of(0, 20, Sort.by("price").descending()); // page 0, 20 items per page, sorted Page<Product> page = productRepository.findByCategory("Electronics", pageable); System.out.println("Total pages: " + page.getTotalPages()); System.out.println("Current page items: " + page.getContent());

Question: What is @Modifying?
Answer: @Modifying is used alongside @Query in Spring Data JPA repository methods to indicate that the query performs an UPDATE or DELETE operation (rather than a SELECT) — without it, Spring Data JPA would attempt to interpret the query as expecting a result set to be returned, which would fail for a bulk update/delete. It's often combined with @Transactional (since modifying operations must run within a transaction) and, optionally, clearAutomatically = true to clear the persistence context afterward (since bulk updates bypass the normal entity lifecycle/dirty checking, leaving the in-memory persistence context potentially stale).
Example:
public interface EmployeeRepository extends JpaRepository<Employee, Long> { @Modifying @Transactional @Query("UPDATE Employee e SET e.salary = e.salary * 1.1 WHERE e.department = :dept") int giveRaise(@Param("dept") String department); // returns the number of rows affected }

Question: How would you investigate a slow Spring Boot API?
Answer: A systematic approach: (1) Check APM/tracing tools (New Relic, Datadog, Zipkin) to identify which layer (controller, service, database, external call) is consuming the most time; (2) Enable and inspect SQL logs / Hibernate statistics to spot slow or excessive queries (particularly N+1 problems); (3) Use a profiler (JFR, async-profiler) to capture a CPU/allocation profile under load and identify hot methods; (4) Check for blocking I/O calls to external services without timeouts, which can tie up threads; (5) Review thread pool and connection pool configuration/metrics (via Actuator) for exhaustion or contention; (6) Load test with tools like JMeter or Gatling to reproduce the slowdown in a controlled environment and correlate metrics; (7) Check for unnecessary serialization/deserialization overhead or overly large response payloads.
Example:
// Adding timing instrumentation via an AOP aspect to quickly pinpoint slow methods @Around("execution(* com.example.service.*.*(..))") public Object timeIt(ProceedingJoinPoint pjp) throws Throwable { long start = System.nanoTime(); Object result = pjp.proceed(); long durationMs = (System.nanoTime() - start) / 1_000_000; if (durationMs > 500) { // flag anything over 500ms log.warn("{} took {}ms", pjp.getSignature(), durationMs); } return result; }

Question: Unit test vs integration test in Spring?
Answer: A unit test verifies a single class or method in isolation, typically mocking out all its dependencies (using Mockito, for example), so it runs extremely fast and pinpoints exactly which unit of code has a bug — it does NOT load the Spring context. An integration test verifies that multiple components work correctly together, often loading a (full or partial) Spring application context, an embedded/test database, and exercising real interactions across layers (e.g., an actual HTTP request through the full controller-service-repository-database stack) — it's slower but catches issues that unit tests, with all their mocked boundaries, cannot (like incorrect wiring, real SQL query bugs, or serialization issues).
Example:
// Unit test - no Spring context, dependencies mocked @Test void testCalculateDiscount() { OrderService service = new OrderService(mockPricingRepo); // mocked dependency when(mockPricingRepo.getDiscount(anyString())).thenReturn(0.1); assertEquals(90.0, service.calculateDiscountedPrice(100.0, "SUMMER10")); } // Integration test - loads real Spring context and embedded database @SpringBootTest @AutoConfigureMockMvc class OrderControllerIntegrationTest { @Autowired private MockMvc mockMvc; @Test void testCreateOrder() throws Exception { mockMvc.perform(post("/api/orders").contentType(MediaType.APPLICATION_JSON) .content("{\"product\":\"Widget\",\"qty\":2}")) .andExpect(status().isCreated()); // exercises the full real stack } }

Question: How would you test transactional behavior?
Answer: In Spring, you can test that @Transactional methods correctly commit or roll back by writing an integration test (typically @SpringBootTest or @DataJpaTest) that deliberately triggers both success and failure scenarios and asserts on the resulting database state. Spring Test's @Transactional annotation on the TEST method itself wraps each test in its own transaction that's automatically rolled back after the test completes (keeping tests isolated from each other), which is convenient — but if you specifically want to verify that YOUR application code's rollback behavior works correctly (e.g., that an exception mid-method really does undo a partial database change), you often need TestTransaction utilities or a separate, non-rolled-back verification step, since the test's own wrapping transaction can otherwise mask whether your method's internal rollback actually worked.
Example:
@SpringBootTest class BankServiceTransactionTest { @Autowired BankService bankService; @Autowired AccountRepository accountRepo; @Test void testTransferRollsBackOnFailure() { double initialBalance = accountRepo.findById(1L).get().getBalance(); assertThrows(RuntimeException.class, () -> { bankService.transferMoney(1L, 999L, 100); // 999L doesn't exist - should fail and roll back }); double balanceAfter = accountRepo.findById(1L).get().getBalance(); assertEquals(initialBalance, balanceAfter); // confirms the debit was rolled back, not partially applied } }

Question: How would you monitor a Spring Boot service in production?
Answer: (See related answer under UST Global "monitor and troubleshoot production bugs".) Key elements: expose and scrape Actuator health/metrics endpoints via Prometheus, visualize them in Grafana dashboards (latency percentiles, error rates, JVM memory/GC metrics, thread pool utilization); centralize application logs (ELK/Splunk) with structured, correlated logging; set up alerting rules on key SLIs (error rate spikes, latency degradation, pod restarts); use distributed tracing (OpenTelemetry/Zipkin/Jaeger) for microservice architectures to see end-to-end request flow; and configure liveness/readiness probes (via Actuator's health groups) so orchestrators like Kubernetes can automatically restart or stop routing traffic to unhealthy instances.
Example:
management.endpoints.web.exposure.include=health,metrics,prometheus management.endpoint.health.probes.enabled=true // Kubernetes deployment then references: // livenessProbe: httpGet path: /actuator/health/liveness // readinessProbe: httpGet path: /actuator/health/readiness // And Prometheus scrapes /actuator/prometheus for metrics like http_server_requests_seconds

Question: Which Actuator endpoints are useful in production?
Answer: Some of the most valuable Actuator endpoints include: /actuator/health (overall and component-level application health, essential for load balancer/orchestrator health checks); /actuator/metrics (detailed metrics like JVM memory, GC pauses, HTTP request counts/latencies, thread pool stats, exposed in a format Prometheus/Micrometer can scrape); /actuator/env (current environment properties, useful for verifying configuration, though should be secured since it can expose sensitive values); /actuator/loggers (view and dynamically CHANGE log levels at runtime without redeploying — extremely useful for debugging a live production issue); /actuator/threaddump and /actuator/heapdump (for diagnosing concurrency issues or memory leaks on demand); /actuator/httptrace or tracing integrations (recent request/response trace details). Sensitive endpoints should always be secured (via Spring Security) and only selectively exposed, not all enabled by default in production.
Example:
# Dynamically raising a specific logger's verbosity in a live production instance, no redeploy needed curl -X POST http://localhost:8080/actuator/loggers/com.example.payment \ -H "Content-Type: application/json" \ -d '{"configuredLevel": "DEBUG"}' // Now you can observe detailed DEBUG logs for that specific troublesome package in real time.

Question: How would you diagnose a sudden increase in HTTP 5xx errors?
Answer: Start by checking what changed recently — most production incidents correlate with a recent deployment, configuration change, or infrastructure event, so check deployment timelines first. Then: (1) check centralized logs/APM for the actual exception stack traces behind the 5xx responses to identify the root cause (NullPointerException, database connection failure, downstream timeout, etc.); (2) check dependency health — is a downstream service, database, or cache down or degraded?; (3) check resource exhaustion — connection pool exhausted, thread pool saturated, memory pressure causing excessive GC pauses or OOM; (4) check for a traffic spike beyond capacity (correlate with request rate metrics); (5) if it correlates precisely with a deploy, consider rolling back immediately while investigating further, since restoring service quickly often takes priority over root-causing during an active incident.
Example:
// Correlating error spikes with a specific exception type via Actuator metrics or log aggregation GET /actuator/metrics/http.server.requests?tag=status:500 // Cross-referencing this timestamp with application logs might reveal: // "java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available, // request timed out after 30000ms" - pointing to connection pool exhaustion as the root cause.

Question: How would you design a production-ready Java backend?
Answer: A production-ready Java backend typically incorporates: (1) Layered architecture (controller/service/repository) with clear separation of concerns; (2) Robust error handling with centralized exception handling and meaningful, consistent error responses; (3) Input validation at the API boundary (Bean Validation annotations); (4) Security — authentication/authorization (Spring Security, JWT/OAuth2), HTTPS, secrets management, input sanitization; (5) Observability — structured logging with correlation IDs, metrics (Micrometer/Prometheus), distributed tracing, health checks; (6) Resilience — timeouts, retries with backoff, circuit breakers (Resilience4j) for calls to external dependencies, graceful degradation; (7) Performance — connection pooling, caching where appropriate, pagination for large datasets, avoiding N+1 queries; (8) Testing — unit tests, integration tests, and possibly contract tests, run in CI/CD; (9) Scalability — stateless services (session state externalized to Redis if needed) so instances can be scaled horizontally behind a load balancer; (10) Configuration management — externalized, environment-specific config (Spring profiles, environment variables, or a config server), never hardcoded secrets.
Example:
// A simplified but illustrative production-conscious endpoint combining several of these principles @RestController @RequestMapping("/api/v1/orders") public class OrderController { private final OrderService orderService; public OrderController(OrderService orderService) { this.orderService = orderService; } // DI @PostMapping @PreAuthorize("hasRole('CUSTOMER')") // authorization public ResponseEntity<OrderResponse> createOrder(@Valid @RequestBody OrderRequest request) { // validation Order order = orderService.createOrder(request); // wrapped with @Transactional + retry/circuit breaker internally return ResponseEntity.status(HttpStatus.CREATED).body(OrderMapper.toResponse(order)); } // Global @RestControllerAdvice handles all exceptions centrally and consistently }
Question: How would you diagnose HikariCP connection timeouts?
Answer: A HikariCP connection timeout (SQLTransientConnectionException: "Connection is not available, request timed out") means all connections in the pool were busy and no connection became free within the configured connectionTimeout. Diagnosis: (1) enable HikariCP's leak detection (leakDetectionThreshold) to log a warning with a stack trace when a connection is held longer than expected, revealing code that isn't closing/returning connections properly; (2) check the pool metrics via Actuator/Micrometer (active vs idle vs pending connections) to see if the pool is genuinely saturated under load or if connections are leaking; (3) check for long-running queries or transactions holding connections far longer than necessary (often the real root cause — a slow query or a transaction spanning an external API call); (4) verify pool size is appropriately sized (see HikariCP sizing formula) relative to actual concurrent demand; (5) check for connection leaks in code paths that don't use try-with-resources or that acquire a connection outside the managed Spring transaction boundary.
Example:
spring.datasource.hikari.leak-detection-threshold=30000 # warns if a connection is held > 30 seconds # Example log output revealing the culprit: # "Connection leak detection triggered for connection ... on thread report-generator-3, # stack trace: com.example.ReportService.generateReport(ReportService.java:45)" // This immediately reveals ReportService is not closing its connection/resultset properly.

Question: How would you make a POST endpoint idempotent when clients retry requests?
Answer: Idempotency means multiple identical requests produce the same result as a single request (no duplicate side effects like double-charging a customer). A common pattern: require the client to send a unique Idempotency-Key header with each logically-distinct request; on the server, before processing, check if that key has already been seen (stored in a fast store like Redis or a database table with a unique constraint on the key) — if yes, return the previously stored response instead of re-executing the operation; if no, process the request normally and store the key alongside the response for future duplicate checks (with an appropriate expiration).
Example:
@PostMapping("/payments") public ResponseEntity<PaymentResponse> createPayment( @RequestHeader("Idempotency-Key") String idempotencyKey, @RequestBody PaymentRequest request) { Optional<PaymentResponse> existing = idempotencyStore.get(idempotencyKey); if (existing.isPresent()) { return ResponseEntity.ok(existing.get()); // return the SAME response, don't re-charge the customer } PaymentResponse response = paymentService.process(request); idempotencyStore.save(idempotencyKey, response, Duration.ofHours(24)); return ResponseEntity.ok(response); }

Question: How would you secure sensitive configuration?
Answer: Sensitive configuration (database passwords, API keys, encryption keys) should never be hardcoded in source code or committed to version control. Best practices: (1) use a dedicated secrets manager (AWS Secrets Manager, HashiCorp Vault, Azure Key Vault, GCP Secret Manager) that securely stores and rotates secrets, injecting them into the application at runtime; (2) if using environment variables, ensure they're set through a secure deployment pipeline (not stored in plaintext files that get committed); (3) encrypt sensitive values at rest and in transit; (4) use Spring Cloud Config Server with encryption support if centralizing configuration across microservices; (5) apply the principle of least privilege — limit which services/roles can access which secrets; (6) rotate credentials periodically and immediately upon suspected compromise; (7) never log sensitive values, and mask them in Actuator's /env endpoint (Spring Boot does this automatically for keys matching common sensitive patterns like "password", "secret", "key").
Example:
// BAD - hardcoded secret in source code, committed to git String dbPassword = "SuperSecret123"; // NEVER do this // GOOD - fetched securely at runtime from a secrets manager @Value("${db.password}") // this property is populated from AWS Secrets Manager / Vault at deploy time, private String dbPassword; // never stored in the codebase or plaintext config files

Question: How would you investigate high CPU in a Java service?
Answer: (1) Identify which threads are consuming CPU using OS tools (top -H -p <pid> on Linux to see per-thread CPU usage); (2) take a thread dump (jstack <pid>, or via Actuator's /actuator/threaddump) at the moment of high CPU and match the high-CPU thread IDs (converted to hex) against the thread dump to see exactly what code those threads are executing; (3) alternatively, use a CPU profiler (async-profiler, JFR) to capture a flame graph over a time window, which directly shows which methods are consuming the most CPU time without manual thread-ID matching; (4) common root causes include: an infinite/tight loop (e.g., a bug causing a spin-wait instead of blocking), excessive garbage collection due to high allocation rates (visible in GC logs), regex catastrophic backtracking, or inefficient algorithms (like an O(n²) operation on a much-larger-than-expected dataset).
Example:
# Capture a quick CPU profile with async-profiler ./profiler.sh -d 30 -f flamegraph.html <pid> // Opening flamegraph.html might reveal that 60% of CPU time is spent inside // "java.util.regex.Pattern.matches" due to a poorly written regex suffering catastrophic backtracking // on certain malformed input strings - pointing directly at the fix needed.

Question: How would you investigate memory growth in a long-running service?
Answer: (See related answer under "investigate an OutOfMemoryError".) Monitor heap usage trends over time via GC logs or metrics (Actuator/Micrometer's jvm.memory.used) — a true memory leak shows a heap that keeps climbing even after full GCs, never returning to a stable baseline, whereas normal memory usage sawtooths up and down as garbage collection reclaims short-lived objects. Take periodic heap dumps (or compare two heap dumps taken hours apart) and use a tool like Eclipse MAT to see which object types are growing in count/retained size between the two snapshots — this "leak suspects" comparison quickly narrows down the exact class responsible (commonly an ever-growing static collection, an unbounded cache, or listeners/callbacks that are registered but never deregistered).
Example:
// Comparing two heap dumps taken 2 hours apart in Eclipse MAT might show: // "com.example.SessionCache$InnerMap" grew from 10,000 to 480,000 entries, // while application traffic stayed roughly constant -> confirms a cache without proper eviction, // e.g., sessions are added on login but never removed on logout/timeout.

Question: How would you troubleshoot database connection exhaustion?
Answer: Connection exhaustion (all pool connections in use, new requests time out waiting) is diagnosed by: (1) monitoring pool metrics (active, idle, pending/waiting threads) via Actuator/Micrometer to confirm the pool is indeed maxed out; (2) enabling HikariCP leak detection to catch code that acquires but never releases a connection; (3) checking for long-running transactions or queries that hold a connection far longer than expected (a slow query, or a transaction that makes a slow external API call while still holding a DB connection open, is a very common culprit); (4) reviewing recent traffic patterns for an unexpected surge beyond the pool's designed capacity; (5) checking whether the configured pool size is actually appropriate for the workload (either genuinely too small, or the database server itself can't handle more connections without proportionally increasing pool size elsewhere).
Example:
// A classic anti-pattern causing connection exhaustion: holding a DB connection open // while making a slow external HTTP call inside the same transaction @Transactional public void processOrder(Order order) { orderRepo.save(order); // holds a DB connection shippingApiClient.notifyCarrier(order); // SLOW external call - the DB connection stays checked out // from the pool the entire time, unnecessarily } // Fix: move the external call outside the transactional boundary, or make it asynchronous, // so the database connection is released back to the pool as quickly as possible.

Question: How would you implement API rate limiting?
Answer: Approaches include fixed-window counters, sliding-window counters/logs, and token-bucket algorithms, typically backed by a fast, shared store like Redis so rate limits are enforced consistently across multiple application instances in a distributed deployment. Libraries like Bucket4j or Resilience4j's RateLimiter can implement this without hand-rolling the algorithm, and API gateways (like Kong, AWS API Gateway, or Spring Cloud Gateway) can also enforce rate limiting at the infrastructure layer, before requests even reach your application code.
Example:
// Using Bucket4j for a token-bucket rate limiter Bandwidth limit = Bandwidth.classic(100, Refill.greedy(100, Duration.ofMinutes(1))); // 100 requests/minute Bucket bucket = Bucket.builder().addLimit(limit).build(); if (bucket.tryConsume(1)) { // process the request } else { // return HTTP 429 Too Many Requests }

Question: How would you design pagination for a large table?
Answer: For smaller-to-moderate datasets, standard OFFSET/LIMIT pagination is simple and sufficient. But for very large tables, OFFSET-based pagination becomes increasingly slow for deep pages, because the database must still scan and discard all the skipped rows before returning the requested page. For large-scale pagination, keyset (cursor-based) pagination is preferred: instead of an offset, you remember the last-seen row's sort key value (like the last ID or timestamp) and query "WHERE id > last_seen_id ORDER BY id LIMIT page_size" — this lets the database use an index to jump directly to the right starting point, regardless of how deep into the dataset you are, making performance consistent (O(log n) via index) rather than degrading with page depth.
Example:
-- Offset pagination - slow for deep pages (must scan and discard 1,000,000 rows first) SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000; -- Keyset/cursor pagination - fast regardless of depth, uses the index directly SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20; -- The client simply remembers the last "id" from the previous page's results as the cursor for the next page.

Question: OFFSET pagination vs keyset pagination?
Answer: OFFSET pagination (LIMIT x OFFSET y) is simple to implement and allows jumping directly to any arbitrary page number, but performance degrades as the offset grows large, since the database still must count through and discard all skipped rows even though they aren't returned — this becomes a real bottleneck on tables with millions of rows. Keyset (cursor-based) pagination uses a WHERE condition based on the last-seen sort key value instead of counting rows to skip, letting the database use an index to jump directly to the correct starting point regardless of depth — giving consistent performance — but it sacrifices the ability to jump to an arbitrary page number (you can only move forward/backward relative to a known cursor) and requires the sort key to be unique/stable.
Example:
-- OFFSET: can jump to "page 5000" directly, but gets slower and slower as offset grows SELECT * FROM products ORDER BY id LIMIT 25 OFFSET 125000; -- Keyset: consistently fast, but only supports "next page from here", not "jump to page 5000" SELECT * FROM products WHERE id > :lastSeenId ORDER BY id LIMIT 25;

Question: How would you handle optimistic locking?
Answer: Optimistic locking assumes conflicts between concurrent updates are rare, so instead of locking a row for the duration of a transaction (pessimistic locking), it allows multiple transactions to read and attempt to update the same row concurrently, but detects conflicts at commit/update time using a version number (or timestamp) column. In JPA/Hibernate, you annotate a field with @Version — every UPDATE statement includes a WHERE clause checking that the version column still matches the value that was originally read; if another transaction already updated the row (incrementing the version) in the meantime, the UPDATE affects zero rows, and Hibernate throws an OptimisticLockException, signaling the caller to retry or handle the conflict.
Example:
@Entity class Product { @Id private Long id; private int stockQuantity; @Version private Long version; // Hibernate auto-manages this } // Generated UPDATE looks like: // UPDATE product SET stock_quantity = ?, version = version + 1 WHERE id = ? AND version = ? // If another thread already changed 'version' in between, this UPDATE affects 0 rows, // and Hibernate throws an OptimisticLockException, letting the application retry the operation.

Question: How would you prevent lost updates?
Answer: A "lost update" happens when two concurrent transactions each read the same data, then both write back their own modified version, and one overwrites the other's changes without either transaction knowing about the conflict. This is prevented using either optimistic locking (a version column, as described above, detects and rejects the second conflicting write, forcing a retry) or pessimistic locking (explicitly locking the row for the duration of the transaction using SELECT ... FOR UPDATE, so a second transaction trying to read/modify the same row must wait until the first transaction commits or rolls back). Optimistic locking is preferred for low-contention scenarios (better throughput, no blocking), while pessimistic locking suits high-contention scenarios where conflicts are frequent and retries would be wasteful.
Example:
-- Pessimistic locking - the row is locked for the duration of this transaction BEGIN TRANSACTION; SELECT * FROM inventory WHERE product_id = 5 FOR UPDATE; -- other transactions trying to update this row must wait UPDATE inventory SET stock = stock - 1 WHERE product_id = 5; COMMIT; -- lock released here // Optimistic locking (JPA) - see @Version example above; conflicts are detected, not prevented upfront

Question: How would you design a resilient service calling a slow external API?
Answer: Key resilience patterns: (1) Timeouts — always set an explicit connection and read timeout on external calls, never rely on defaults (which can be infinite), to avoid threads hanging forever; (2) Retries with exponential backoff — for transient failures, retry a limited number of times with increasing delay between attempts (and ideally jitter, to avoid synchronized retry storms across many clients); (3) Circuit Breaker — using a library like Resilience4j, if calls to the external service keep failing, "open" the circuit to fail fast immediately (without even attempting the call) for a cooldown period, giving the struggling downstream service time to recover, then periodically test with a few "half-open" trial calls before fully closing the circuit again; (4) Bulkheads — isolate resources (thread pools) dedicated to a specific external dependency, so a slow/failing dependency can't exhaust shared resources needed by unrelated parts of the application; (5) Fallbacks — provide a sensible default/cached response when the external call ultimately fails, if a degraded experience is acceptable, rather than failing the entire user-facing request.
Example:
// Using Resilience4j to combine timeout, retry, and circuit breaker CircuitBreakerConfig cbConfig = CircuitBreakerConfig.custom() .failureRateThreshold(50) // open the circuit if 50% of recent calls fail .waitDurationInOpenState(Duration.ofSeconds(30)) .build(); CircuitBreaker circuitBreaker = CircuitBreaker.of("externalApi", cbConfig); Supplier<String> decoratedSupplier = CircuitBreaker.decorateSupplier(circuitBreaker, () -> externalApiClient.fetchData()); String result = Try.ofSupplier(decoratedSupplier) .recover(throwable -> "fallback default value") // graceful fallback if circuit is open or call fails .get();

Question: How would you approach caching in a Spring Boot application?
Answer: Spring provides a caching abstraction (@EnableCaching, @Cacheable, @CachePut, @CacheEvict) that works with a pluggable cache provider (an in-memory ConcurrentMapCache for simple cases, or more robust options like Caffeine for local in-JVM caching, and Redis for a distributed cache shared across multiple application instances). The key design decisions: what to cache (read-heavy, rarely-changing, or expensive-to-compute data is the best candidate), cache invalidation strategy (TTL-based expiration, explicit eviction on updates via @CacheEvict, or event-driven invalidation), and cache topology (local/in-memory caches are fastest but not shared across instances and can serve stale data after a scale-out; distributed caches like Redis are consistent across instances but add network latency and infrastructure complexity).
Example:
@Service public class ProductService { @Cacheable(value = "products", key = "#id") // caches the result keyed by 'id' public Product getProduct(Long id) { return productRepository.findById(id).orElseThrow(); // only actually runs on a cache miss } @CacheEvict(value = "products", key = "#product.id") public void updateProduct(Product product) { productRepository.save(product); // ensures the stale cached entry is removed after an update } }

Question: Redis cache vs database cache: what trade-offs matter?
Answer: A Redis (or similar dedicated in-memory) cache stores data outside the primary database in a very fast, in-memory key-value store, dramatically reducing latency for frequently accessed data and offloading read load from the primary database — but it introduces additional infrastructure to manage, potential cache staleness/consistency challenges (the cache and database can diverge if invalidation isn't handled carefully), and an additional network hop compared to purely in-process caching. A "database cache" (like a database's own query cache, buffer pool, or materialized views) keeps caching logic inside the database engine itself, requiring less additional infrastructure and often providing automatic consistency guarantees, but it's still bound by database server capacity and doesn't offload load away from the database the way an external cache does, and native query caches in many modern databases (like MySQL's now-removed query cache) have proven less effective in practice than dedicated external caching layers. In most modern high-traffic architectures, a dedicated distributed cache like Redis, placed in front of the database, is the preferred pattern for read-heavy workloads needing very low latency at scale.
Example:
// Application-level caching pattern with Redis in front of the database public Product getProduct(Long id) { String cacheKey = "product:" + id; String cached = redisTemplate.opsForValue().get(cacheKey); if (cached != null) { return deserialize(cached); // fast path - avoids hitting the database entirely } Product product = productRepository.findById(id).orElseThrow(); // slow path - database read redisTemplate.opsForValue().set(cacheKey, serialize(product), Duration.ofMinutes(10)); // populate cache with TTL return product; }

Question: How would you diagnose a deadlock involving application transactions?
Answer: Database-level transaction deadlocks (two transactions each waiting on a row lock held by the other) are typically detected and automatically resolved by the database itself, which picks one transaction as a "victim" and aborts it, throwing an error (e.g., MySQL's "Deadlock found when trying to get lock" or PostgreSQL's deadlock_detected error) that propagates up to the application. To diagnose: (1) capture and log the specific error, which usually includes the conflicting queries/transactions from the database's own deadlock detector; (2) examine the database's deadlock log (e.g., SHOW ENGINE INNODB STATUS in MySQL, or PostgreSQL's log with log_lock_waits enabled) to see the exact queries and lock order involved; (3) review the application code paths involved to identify inconsistent ordering of row/table access across different transactions — the fix is almost always to enforce a consistent order of acquiring locks/updating rows across all code paths that touch the same tables; (4) implement retry logic in the application for deadlock-related exceptions, since even with careful design, a database deadlock can occasionally still occur under highly concurrent conditions, and databases expect the losing transaction to simply retry.
Example:
// Two different code paths updating Account rows in inconsistent order can deadlock: // Path A: updates Account(id=1) then Account(id=2) // Path B: updates Account(id=2) then Account(id=1) // Fix: always acquire/update in a consistent order, e.g., always by ascending account ID: @Transactional public void transfer(Long fromId, Long toId, double amount) { Long first = Math.min(fromId, toId); Long second = Math.max(fromId, toId); Account a = accountRepo.findByIdForUpdate(first); // consistent order across ALL callers Account b = accountRepo.findByIdForUpdate(second); // ... perform the actual debit/credit logic correctly based on which is 'from' and 'to' }

Question: How would you safely change a large database schema with a zero-downtime deployment?
Answer: Zero-downtime schema changes typically follow an "expand and contract" (or "parallel change") pattern across multiple deployment phases, so the old and new application code can both work correctly during the transition: Phase 1 (Expand) — add the new column/table/index without removing or renaming anything old, and deploy application code that can read from both old and new structures if needed, writing to both; Phase 2 (Migrate/Backfill) — run a background job to backfill the new column/structure with data derived from the old one, without locking the whole table (batched updates, not one giant transaction); Phase 3 (Switch) — deploy application code that fully switches to using only the new structure for both reads and writes; Phase 4 (Contract) — once you're confident the new structure works correctly and the old one is unused, remove the old column/table/index in a final cleanup migration. Throughout this, use online schema change tools (like gh-ost or pt-online-schema-change for MySQL, or native online DDL support in PostgreSQL) that avoid taking long table-locking operations, and always make each migration step backward-compatible with the currently-running version of the application to support rolling deployments.
Example:
-- Phase 1: Expand - add new column, nullable so old code doesn't break ALTER TABLE users ADD COLUMN email_normalized VARCHAR(255) NULL; -- Phase 2: Backfill in batches (not one giant transaction on a huge table) UPDATE users SET email_normalized = LOWER(email) WHERE id BETWEEN 1 AND 10000 AND email_normalized IS NULL; -- (repeated in batches across the whole table, application still uses the OLD "email" column meanwhile) -- Phase 3: deploy new app version that reads/writes email_normalized instead -- Phase 4: Contract - once confirmed safe, drop the old column ALTER TABLE users DROP COLUMN email;
